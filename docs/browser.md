# Browser integration

The shared Flutter UI is in [`app/`](https://github.com/Boriken-Dev/canoa/tree/main/app) and is intended to run in a standalone PWA, extension full-page tab or narrow side panel.

## Chromium and Edge

Canoa's Manifest V3 Chromium binding lives at [`clients/browser/chromium/`](https://github.com/Boriken-Dev/canoa/tree/main/clients/browser/chromium). The extension has its own tab/origin/peer permission checks, browser tool catalogue and permission-gated tab actions, each of which also checks that the tab is still on the origin the grant was for. The side-panel and full-page entries package the Flutter UI. Agents are reached over a proven link, and the tools are offered as "Remote browser tools" and "A program on a paired machine" below say.

The standard extension does not request `debugger`. An elevated `manifest.debug.json` enables the Chromium `debugger` API in a separately packaged build. The extension now has an MCP JSON-RPC handler and permission-gated CDP commands, tested independently; the remote bridge is `canoa serve --program`, and a person pairs the extension with a host as for any client. Local per-tab browser grants can be managed from the extension's Browser Permissions options page. See [browser MCP and DevTools](browser-mcp.md).

## Webpage context

The extension now offers an **Ask Canoa** context-menu action for a page or user-selected text. The selected context is queued in extension session storage and claimed once by the Flutter UI through an extension-only bridge. Query strings, URL fragments and embedded credentials are stripped before attachment. The resulting note is **local only**; no content is transmitted to an agent because authenticated ACP messaging and explicit send confirmation are still pending. Websites cannot send privileged extension commands merely by being open.

## Remote browser tools

An agent that Canoa's own chat started can use the browser's tools, when its bridge runs `serve --mcp-offers`. Nothing listens in the browser, and the agent needs nothing beyond what ACP already requires of it. A program with no session is [below](#a-program-on-a-paired-machine).

1. The chat connects through the extension's service worker. For an agent whose record offers `mcp-offer/1`, the worker opens a proven link and runs ACP on one stream of it.
2. For each session, the worker opens another stream, and the bridge answers with a stdio `mcpServers` entry that the worker adds to the session. The relay still reads no ACP.
3. The agent starts that program, a small shim, as it would any stdio server. The shim shows a token on a loopback port made for that stream, and from then on carries MCP's own messages to the extension.

**What an agent has.** `browser_request_access`, and whatever that agent's peer still holds a grant for, so at first that one tool. It names a capability and a reason, and opens the extension's own window, where a page cannot draw. There the person sees the reason as the agent's own words, and picks the tab and for how long. On a yes the agent's tool list grows, and it is told so. Browser-local checks still decide every call, against the tab, its origin, the capability and the time left, however the agent is identified.

| It takes | To |
| --- | --- |
| Refusing, or no answer in two minutes | No grant, and 30 seconds before that agent can ask again |
| Loading a new page in the tab, closing it, or the time running out | End the grant. A grant the person gives after the tab moved within its site stays for that page |
| Removing it under **Canoa browser permissions** | End the grant, and tell the agent |

**Who has none of this.** A session a page started: only the extension's own chat gets the server, the worker adds it after the page's scope, and a page's connection has no streams at all. A page cannot give this grant, since it could then steer an agent into driving the browser. The debugger tools exist only in the debugger build, as their own capability, and only `http` and `https` tabs can be offered, which leaves out the extension's window and the browser's own pages.

**What stays true.** What an agent reads on a page can try to talk it into things, and a grant lets it act on that, so share a tab as you would show it to the agent yourself. A grant is by peer, so several agents behind one bridge share it. Any program running as you on the agent's machine can read the shim's token file and use what that agent holds; another user on that machine cannot. Anyone able to pair with `acp/1` can already run commands on that machine: the bridge's own documentation says so.

## A program on a paired machine

An MCP client that Canoa did not start, such as an IDE or a CLI agent, can ask for a tab the same way, with no ACP session and nothing listening in the browser. It is off unless a person turns it on, for one machine.

1. On that machine, run `canoa serve --program --mcp-offers --advertise NAME`, allowing this browser's peer id, with the agent program it asks for after `--`: none starts, since no ACP runs here. Add it under **Canoa agents**.
2. Under **Canoa browser permissions**, choose it and turn it on. The worker opens a proven link there and keeps one more stream open than are in use, with no ACP on the link.
3. On that machine, `canoa mcp-config --peer <this browser's peer id>` prints the `mcpServers` entry to paste. The permissions page shows that command, filled in. The entry holds no port and no secret: the shim finds them in a file only that user can read, so it stays good when the browser or the bridge restarts.

A program then starts the shim as it would any stdio server, and has what an agent has: `browser_request_access`, and whatever that peer still holds a grant for. The window says **A program on** the machine, and shows its key, since no agent's name can be proven and Canoa cannot tell which program it is. Everything under "Remote browser tools" holds for it too: browser-local checks decide every call, and a grant ends the same ways.

| It takes | To |
| --- | --- |
| Turning it on | End what that machine held so far, so nothing it was given before reaches its programs without a person seeing who asks |
| Turning it off | End every program's connection, and tell each with a last MCP message before its server ends. The grants that machine held go too, and a window still asking closes |
| Closing the browser | End every program's connection, and every grant. Restarting it brings the link back with no page open and no change to the entry, and a program has to start its server again to get back in. With WebTransport the bridge can take about 25 seconds to notice |
| Nothing connected | The shim says why, on standard error and as the answer to its client's first message, and exits |
| Removing the agent under **Canoa agents** | Turn it off too |

**Several programs at once.** Each has a stream of its own, up to 8, under the one peer's grant, as several agents behind one bridge have now. So what a person allows one, they allow all of them, and that peer's agents in Canoa's chat too.

**What keeps it running.** A browser ends an extension's idle worker after 30 seconds, and the socket goes with it. A WebSocket's traffic counts as activity and a WebTransport's does not, as measured in Edge, so while the link is up the worker makes an extension API call every 20 seconds, which counts on either. An alarm every 30 seconds starts the worker again if it ended anyway, or tries a machine that was off, and a heartbeat on the link notices one gone silent. No tab has to be open.

**Who has none of this.** A page: the setting answers only the extension's own permissions page, a content script cannot reach the storage holding it, and a page's connection still has no streams. Another peer of that bridge: the shim reaches only the peer its entry names, whose key the bridge proved.

**What stays true.** Any program running as that machine's user can read the shim's file, ask you for a tab, and use what that machine holds, and a program you would not trust with a tab should not run as that user there. Another user on it cannot read that file: it has an ACL for its owner alone on Windows, and owner-only modes elsewhere. A chat conversation's token file is not held to that on Windows, where it takes `%LOCALAPPDATA%`'s permissions, and off does not close that way: while a conversation is open, a program running as that user could find its server. A program can only ask, as often as the wait after a refusal lets it, and a person sees each time.

## Canoa on this computer

The extension uses the Canoa on the computer it runs on by default. A browser reaches a program on the computer only through a registered native messaging host, so `canoa native install` registers one, `dev.boriken.canoa`, for Chrome, Edge and Chromium, for this user only (the registry under `HKCU` on Windows, each browser's `NativeMessagingHosts` folder on Linux and macOS). The desktop app registers itself each time it starts. `canoa native status` shows what is registered and what **Start Canoa** would run, and `canoa native uninstall` removes all of it.

The native host is a relay, not a host. The browser starts the program once for each port the extension opens; it moves bytes between the extension and the **door** of the Canoa that holds the home (a named pipe on Windows, `native.sock` in the home elsewhere, owner-only), and exits when either end does. The extension proves the host and the host proves the extension's key over the relay exactly as over any other link, so the relay sees only sealed records and can say nothing for either side. `[host.native] enabled = false` closes the door.

| State | What the extension shows |
| --- | --- |
| The native host is not registered | "Canoa is not installed on this computer", with a link to getting started. The extension's own agents work as before |
| Registered, Canoa not running | "Canoa on this computer is not running" and **Start Canoa**. The button works only from the extension's own pages: it asks the native host to run the program `canoa native install` recorded, only when no host holds the home |
| Running, this browser not paired | A PIN pairing: the person asks Canoa for a PIN (`canoa pair --native`, or the desktop app's Hosting dialog) and types it in the extension. The key that proves itself through the PIN is the one kept, and it is bound to the extension that paired it: another extension is turned away |
| Running and paired | The panel's sources are the host's entries, its own sources and the person's own agent commands among them, its sessions the host's ledger and its settings the host's canoa.cfg, over the control channel. Agents added by hand or found nearby stay listed below |

A browser key reaches the control channel through the door with `[host.native] control` (this set replaces any grants `[host.control]` gives the key), by default `ledger.read`, `ledger.write`, `worktree`, `store.read`, `folders`, `config.read`, `config.write` and `discover`; installing, restarting the host, uploads and changing what an agent may do are never granted through the door. What the host says in `hello` (its name, its key, its entries) is a claim: it prefills a list, and a key the person did not pair is never trusted from it. "Look for agents nearby" asks Canoa on this computer, because a browser cannot browse the network: the running host answers `discover/nearby` over the paired key, and where it cannot (Canoa stopped, this browser not paired, no `discover` grant) the native host the browser started searches itself, so Canoa has to be installed and need not be running. The search reads the descriptors of agents listening on this computer's loopback and browses the link for `_acp-agent._tcp` for a few seconds; it finds an MCP server only as an agent's `offers`, since MCP has no service type of its own. What it returns is each record's claim: nothing is ticked, and the proof at connect decides. If the host refuses the key (no `discover` grant), the window says so and the native host is not asked in its place. The window also says when the folder of local agents was not read or could not be checked, or the network could not be searched. Windows may need to allow `canoa` through its firewall to hear answers from the network; Canoa never changes a rule. A link cut in the middle of a turn ends as a cut link; nothing the agent was asked is sent again.

## A web page and the Canoa on this computer

A site the person allowed to ask for their agents (**Let this site ask for my agents**) can use the agents of the Canoa on this computer through `document.acp`, as it uses any agent of the person's: it listens for `acp:ready` on `window` (and dispatches `acp:request` if it listens late), and `document.acp` exists only in a secure top-level document of a site the person allowed, so silence means no provider or not allowed. Canoa is the provider `{uuid: "dev.boriken.canoa", name: "Canoa", rdns: "dev.boriken.canoa"}` in `document.acp.providers`. The contract is [ACP in the browser](https://boriken-dev.github.io/coqui-acp/browser/); what follows is what Canoa does with it.

- **Choosing.** `agents()` returns the grants this origin holds and never prompts. `request({purpose, acpVersions: [1], mcpOrigins, permissions: false, peers})` needs a click, and the extension's window lists, beside agents added by hand and found nearby, a group **Canoa on this computer**: every entry of the running host, its built-in sources among them, with the state of the host above it. The window says plainly that the site can tell these agents what to do, that they run on this computer as the person with their settings and tools and can read their files, and that the person is asked only about what the agents' own settings ask about; the folder below is not a limit. The page's `peers` never ticks one of them (they all share the host's key), and the person grants any number. The page learns only what was granted: `source: "local"`, `identity: {peer, verified: true, method: "dev.boriken.coqui.peer-noise/v1"}`, an `id` that differs for each origin, and the `mcpOrigins` the person saw. The `peer` is a name of its own for each site (a SHA-256 of a secret of the extension, the origin and the host's key), the same each time for that site and different for another, so two sites cannot tell they were given the same computer; the window shows the real key. A grant records the host key that was paired when it was made and holds nothing of another Canoa. `verified` is true because the key was bound by the PIN the person typed and every connection proves it again. With Canoa not running, the window says so and offers **Start Canoa**, which asks the native host to run what `canoa native install` recorded (a click in that window only: the extension's own pages are the only senders heard). With this browser not paired with the host, it says that and offers nothing.
- **Connecting.** `connect(agent)` never prompts, and runs the same proof as the extension's own chat over the native host, end to end. With the host stopped a grant stays and `connect` fails with `NetworkError`, as for any agent that cannot be reached. A connection ends on navigation, tab close or revoke (`closed.reason`: `page`, `agent`, `navigation`, `revoked`, `failed`).
- **The folder.** A page names no working directory, and the extension passes on neither the folder the host reports nor anything else the host says about itself in `_meta` (the profile it applied, for one). An agent can still print its working directory, so this is not a secret. The extension tells the host the site, from the host name the browser reported for the page's origin (never a port or anything the page says), and the host gives each session `<Documents>/Canoa/scratch/<site>/<uuid>`; the `cwd` of `session/new`, `session/load` and `session/resume` is removed, `_meta` is removed from every message at every depth, and the folder the host reports is kept by the extension for resuming and not passed on. A site the host refuses (an IPv6 address, a name with capitals or a port) gets the host's `-32602`; a dotted IPv4 address is accepted, and all sites on one host name share one folder tree whatever their port. A host that has the entry's `max_sessions` open answers `-32600`.
- **What a page may ask.** `initialize`; `session/new`; `session/prompt`, `session/cancel`, `session/close`, `session/load` and `session/resume` for its own sessions; `session/set_model` and options of category `model` or `thought_level`; `session/set_mode` and other options only if the person ticked "This site can approve what the agent does for me", which never applies to agents on this computer: the host's entries, any found on a descriptor, and any at an address of this computer (all of 127/8, `0.0.0.0`, `::1`, `::`, `localhost`). The extension does not know this machine's own hostname or LAN addresses, so an agent reached by those is not recognised as local: a grant on one has no `permissions` whatever was ticked, because a site that could answer for them would be running commands as the person. Anything else, `_` extensions included, is `-32601`. The agent's permission requests are answered by the person in the extension's window and not shown to the page. A session request from a page carries only `sessionId`, `mcpServers`, `replayFrom` (it replays a session the page opened) and the host's folder: `additionalDirectories`, a system prompt and the like are removed by the extension, and the host removes `additionalDirectories` again from any request that names a site (it removes nothing else). **Changing the mode.** A page's `session/set_mode`, and `session/set_config_option` of an option that could be a mode (any the agent did not describe as a model or an effort), for one of its own sessions on a host entry, is not refused: the extension asks the person in its own window, naming the site, the option and the value by the agent's own names (from the `configOptions` and `availableModes` it reported). A value on the host's ask-list (`plan`, `manual`, `default`, `accept_edits`, `acceptEdits`, `dontAsk`) gets a plain sentence; any other value gets the warning that it may let the agent run commands and change files on this computer without asking. The person chooses **Allow for this session**, **Deny**, or **Deny, and don't ask again for this site**, which holds for the life of the grant. Deny, or no answer, is `-32601` to the page, and after a Deny the rest of that connection's mode changes are refused without a window. One window is open at a time for an origin, so a page that cannot make the person click cannot raise one on every connection. Allow sends the change itself, marked with the connection's approval token, which the host put in its sealed answer to `initialize` and nowhere else (it removes the key from every other answer), and the extension takes only from the answer to its own first `initialize` and removes before the page sees it; the page cannot send it, since the extension removes everything a page puts in `_meta`. For a session the host placed for a site, the host accepts a change to a mode that still asks (`plan`, `manual`, `default`, `accept_edits`, `acceptEdits`, `dontAsk`; `auto`, any other name and any value that is not text are not among them) or to an option of category `model` or `thought_level`, and any other change only with this connection's token. The answer is not remembered: each request asks. The extension's own pages, the app the host serves and the desktop app are not held to this: the first two mark their sessions as the person's own, the desktop app names no site.
- **Its own tools.** In `session/new`'s `mcpServers` a page may name `http` servers over `https` at its own origin or at one it listed in `mcpOrigins` and the person saw, with headers, and `acp` entries; a `command` entry, an `http://` URL or another origin refuses the whole request (`-32602`). `mcpOrigins` are `https` origins; the window marks one that looks like this computer or a private network (loopback, link-local, private, shared-address and unique-local ranges, IPv4-mapped IPv6, `.local` and single-label names), which the agent can reach and a stranger cannot. The mark is a hint: a name can resolve anywhere, and the person decides. Send one only to an agent whose `initialize` answer has `agentCapabilities.mcpCapabilities.http`. The extension keeps a bearer in the worker's memory for as long as the message is in it and writes it nowhere: the grant keeps session ids and folders, and the host's history keeps a session's folder only. The relay between the extension and the host sees only sealed records. The host hands the entry to the one agent program the page connected to, which can do with the bearer what its own configuration lets it; Claude's adapter, for one, writes the session's MCP configuration, bearer included, to a file in the temporary folder until the session ends, so the site should give the agent a short-lived, revocable token made for that conversation and never the person's own sign-in. A page's skills reach the agent as the prompts and resources of its own MCP server; it gives no overlays, hooks or files.
- **Context.** What the agent should know about the page goes in `text` content blocks at the head of the first `session/prompt` (a `resource` block only when `promptCapabilities.embeddedContext` is true); there is no `_meta` or system-prompt route for a page.
- **Errors.** `NotAllowedError` (no grant, unknown agent, refusal, nothing chosen, no user activation; it never says which), `NotFoundError` (no provider with that uuid), `NetworkError` (unreachable, such as Canoa stopped); JSON-RPC `-32601` (not allowed, or not this page's session), `-32602` (an MCP server not allowed, a site the host refuses), `-32600` (more sessions than the entry's `max_sessions`).

## Other browsers

| Browser | Planned implementation |
| --- | --- |
| Chrome/Chromium | MV3 side panel, userScripts and optional debugger/CDP build |
| Edge | Chromium-compatible extension with browser-specific validation |
| Firefox | WebExtension sidebar and DevTools integration using Firefox-specific APIs |
| Safari | Safari Web Extension and Safari-supported inspection features only |

The browser is the final authority for browsing access. A native broker, agent and website cannot override it.
