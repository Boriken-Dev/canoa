# Roadmap and implementation status

This page distinguishes tested code from planned integration work.

| Component | Status |
| --- | --- |
| Rust in-memory registry and scoped authorization model | Implemented and tested |
| Chromium permission policy and ACP request option validation | Implemented and tested |
| Browser tool catalogue, local dispatcher and site-adapter manifest validator | Implemented as an **unwired scaffold** |
| Flutter multi-session standalone UI | Offline preview by default; tested verified ACP client binding and streaming transcript support |
| Packaged Flutter extension side panel and full page | Build script and manifest, not browser integration tested |
| Browser-to-chat user-selected page or text handoff | Implemented as local-only context attachment; no remote send |
| WebTransport-preferred / WSS fallback agent message transport | Implemented in Dart; wired to ACP v2 through an injected peer-verification callback |
| MTU/path-loss recovery decision and WSS redial with injected peer proof | Implemented as an isolated, tested transport prototype; live session supervision pending |
| ACP v2 initialize, create/resume, prompt, cancel, close and streaming updates | Implemented behind verified-channel interface, tested with simulated agent |
| Browser WebCrypto coqui-peer method | Experimental canonical method in coqui-peer; vendored exact source in Canoa; UI supports pinned peer ID |
| Browser Noise coqui-peer method | Experimental (`coqui-peer-noise`, one review by another AI agent); vendored exact source; the extension and the Flutter web build prove and pair by PIN under it, chosen per agent and never negotiated |
| Native Rust Coqui WebCrypto responder and JS↔Rust proof | Implemented and cross-language CI-tested in coqui-peer; explicit accepted keys and live trust-store revocation supported |
| Authenticated WSS ACP v2 echo endpoint | Implemented and tested with live TLS WebSocket, browser-compatible Coqui proof and ACP v2 prompt lifecycle; test fixture, not AI agent |
| Production agent pairing, persistent agent services, trust-management UI | The desktop app's Hosting dialog pairs and removes the host's keys, each only on a person's click on a dialog showing the whole id, and shows a PIN for a native program; no auto-enrollment of unknown peers. Agents persist only while the app runs |
| Desktop tray and the host as the app's child | Implemented: closing the window keeps the app and its host running, a double click on the tray icon or its menu opens the chat, the host is started again after an unplanned end and ended with its agents on quit or when the app dies. Run on Windows and Linux (see [Desktop and Canoa.cfg](configuration.md)); macOS not run |
| Running an agent on this computer from the desktop app | Implemented for any ACP program: presets for Claude, Codex, Gemini and Pi (through `pi-acp`) when installed, each permission request answered in the conversation, nothing left running on close, earlier conversations listed and reopened, and text files and images sent with a message, each run against real Claude |
| Sessions kept across runs, by harness | Implemented: every session the app opens or resumes is noted with its harness (from `agentInfo` through a map Canoa.cfg extends, else the entry's name), the reported version, entry, place and peer, directory, title and times, in `sessions.json` beside Canoa.cfg or the web build's IndexedDB, bounded by `[sessions] keep`, with no message text unless turned on. The side list groups and filters by harness and reopens by `session/load` or `session/resume`, saying where neither is offered. Run with a scripted agent under two harness names across a real app restart on Windows and Linux (WSLg); IndexedDB run in Chromium on Linux. Not run: a real agent's session reopened after a restart, macOS |
| Profiles in layers | The model, merge and view are implemented: environment, initial context, skills, MCP servers and model, effort and mode defaults, layered built-in, overlays (from git, pinned by commit, or a local directory), the person's own, a trusted project's, the agent entry's and the session's, with each value's layer shown in Settings → Profiles. Overlays install and sync from git on Windows and Linux (WSL) in tests against a local repository; one schema, held by shared vectors in the app and `canoa-host`. Not yet: applying a profile to any harness, and the host serving profiles. Of what a profile holds, only Claude's adapter takes all of it per session; Codex takes context and MCP servers per session and the rest at process start; Gemini, Pi, OpenCode and Grok take environment, context and skills only at process start, and pi-acp drops MCP servers |
| Agents from the browser's provider in Canoa's web build | Implemented: the connect dialog offers them when a provider is present, and takes only an agent it reports as proven |
| `canoa-host`: agents served from Canoa.cfg | Implemented: a stdio ACP agent or a Guatiao provider per `[host]` entry, from a library or a source (a provider written in Python answers through one entry, tested on Windows and Linux) and from `settings` its schema checks, on loopback, to paired keys only, reached by the chat's own connection code in tests on Windows and Linux, and by the real extension in Edge on Windows; a client cannot have it start a program. Not yet: discovery, keeping an agent through a reconnect |
| Command-line tools with no ACP, served by `canoa-host` | Implemented: a `[host.tools]` entry maps a tool's JSON lines to ACP by rules in Canoa.cfg, a process per session or per message, with the tool's questions sent to the person and what it does unasked shown when a session opens. Pi ran real turns from one entry through the host and the chat's connection code on Windows and Linux (WSL); macOS not run. Not yet: a terminal view for a tool with no JSON output |
| Native service discovery and stdio bridge | Implemented in `coqui-acp-bridge`: `serve --advertise`, `discover` and a native companion the extension asks when the person looks nearby; a stdio agent on the network under a proven peer |
| Browser tools for an agent of Canoa's own chat | Implemented over `mcp-offer/1` on the agent's proven link: it asks, a person picks the tab, its tool list grows, and it loses them on revocation, navigation or time. A real Claude agent ran this in real Edge; none of it runs in CI's browser |
| Elevated CDP adapter and local grant UI | Implemented and JS-tested; debug-only manifest, permission options page, console/network event buffer; remote transport pending |
| MCP client outside any ACP session reaching the browser's tools | Implemented, off by default, for one paired machine: `coqui-acp-bridge mcp-config` prints one stable entry, the worker keeps a proven link and a free stream with no ACP on it, and a person allows each tab. The official SDK's client and real Claude Code ran it in real Edge, and it stayed up idle past 5 minutes there; none of it runs in CI's browser, and no other browser was tried |
| Full remote debugging and audit trail | Debug tools are requestable in the debugger build, with no test against a real agent; no audit trail |
| Actual JS/Wasm user site-adapter execution and sandbox | Planned |
| Firefox and Safari browser integrations | Planned |

The experimental ACP v2 echo fixture has an end-to-end test. This is not evidence of production agent interoperability, remote browser access or a security audit.
