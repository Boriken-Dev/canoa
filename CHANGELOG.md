## [Unreleased]

### Added
- One file per desktop platform: `python app/tool/build.py desktop --portable` builds the release app with its web app inside the host library and packages it. On Windows that is `target/canoa-windows/CanoaUI.exe`, made by the new `canoa-launch` crate: it carries the app folder as a deflated archive with a manifest of SHA-256 digests (made by `canoa-pack`, never committed), unpacks it to a temporary sibling and renames it to `%LOCALAPPDATA%\Canoa\<version>\` only when that folder is absent or differs, hashes every file again on each start (a changed file is replaced, an unlisted one removed), starts only a file the manifest lists, refuses a link, junction or foreign-owned folder, and removes the versions it made beyond the last two. On Linux it writes an AppImage with a pinned appimagetool. macOS ships `Canoa.app`. The release recipe, and what SmartScreen shows for an unsigned file, are in `docs/portable.md`.
- Overlay hooks (`hook.<ext>` and `[hooks]` in an overlay's manifest) run in the host for the overlays of a profile. Canoa fires what it sees over ACP, `pre-env` (before the agent starts), `session-start` (`new` and `resume`), `session-end`, `prompt`, `turn-end`, `pre-tool` (for the calls the agent asks permission for, so `hook-partial`) and `post-tool`, and reports `cd` and `pre-compact` as `hook-unsupported`. A hook runs only while canoa.cfg names its overlay's tree digest (`allow_hooks` in `[host.profiles.NAME]`, `[agents.NAME.hooks]` for a source of the host's own) or the person allowed it for one session when the host asked (the approval dialog lists hooks beside MCP servers, and can keep the choice in canoa.cfg). A hook runs from a copy of the files its digest covered, with a clean environment and process group, bounded in time, output and payload; it can add context, block a prompt, deny a tool call or refuse a session when it is a guard, and nothing it prints approves anything. `crates/canoa-host/AGENTS.md`, "Overlay hooks", has the per-harness table.
- **Always allow here** on a permission card: Canoa remembers, for one source (by identity), peer, folder and named tool, a command (exactly, never by prefix, and only if it is printable ASCII), an MCP tool by its structured name (never one that executes), or a change under a path inside the folder (absolute, no `.` or `..`, only for a session on this computer in a desktop build, never a hidden file or folder, a build script, a manifest, a Windows device name or an agent instruction file, with links resolved; not where the folder is or holds home or is Canoa's settings). It answers a matching request with the agent's allow-once answer, never an "always" and never where none is offered; commands and tools apply only in the agent's Manual or Plan mode, and are not kept with file changes in one folder, folders that hold each other, or one repository. The button names its scope (`Always allow here: calc`); the rule is read before it is kept and has to cover the request it comes from. A request waiting on the rules file is dropped if Stop, closing or a lost connection came meanwhile. Rules are kept in `permissions.json` beside canoa.cfg, written atomically under a lock, and a file that does not parse applies none; `permissions-log.jsonl` is appended to with the program only. Each rule and use is said in the conversation, and Settings, Permissions lists them, flags rules the app did not write and ones an earlier version wrote that no longer apply, shows a failed write, and revokes one at once; a revoke by another instance wins. When the agent changes the session's mode right after the person's own "always" answer, the conversation says so.
- Settings has **Bypass answers with allow once only** (`[permissions] allow_once_only`, default off): with it on, Canoa's Bypass answers a request only with an answer that allows once, and leaves one that offers only an "always" to the person, waiting ones included.
- The host serves the agent commands of canoa.cfg's `[agents.NAME]` (`program`, `args`; the app's `profile` and `mcp` sub-tables are let go by) as sources of its own, after the built-in ones, with `serve --local-sources` (`Config::local_agents`, each an `Entry` with `local` set). A name may be any text of up to 64 characters; a command named like a built-in source replaces it, and `agy acp` is read for its quota as an `agy` entry is. Adding or removing one in Settings restarts the host, which ends the sessions open on it: Settings says so, and asks first when any are open.
- A source of the host's own (Claude, Codex, Antigravity, Grok, Pi, and an `[agents]` command) is launched with canoa.cfg's top-level `[profile]`, the overlays `[overlays]` names, the agent's `[agents.NAME.profile]` layer and its `[agents.NAME.mcp]` choices (`true`, `false` or a `sha256:` digest), by the host: the environment, initial context, skills and MCP servers reach the agent as for a `[host.profiles]` entry, one profile named `default`, and the answers to `initialize` and `session/new` report what applied under `_meta["dev.boriken.canoa/profile"]`, with the `value` of `model`, `effort` and `mode`. `Config::local_profiles`, `LocalProfiles::for_agent`, `HostProfile::agent` and `off_mcp` are new. The app's own in-process link, when it says in `initialize` (`_meta["dev.boriken.canoa/approve"]`) that it answers the request `_canoa/profile/approve`, is asked (a paired key never is, and an agent's own `_canoa/` requests are dropped), before a session starts, which of the overlay MCP servers the configuration does not allow that session may start; the desktop app shows a dialog and can keep the choice in `[agents.NAME.mcp]`.
- The control channel's ledger holds each caller to its own records: `ledger/list` returns only the caller's (the app asks for every owner's with `all`), so a paired key's records are never taken for sessions; each owner has its own `max_records` and byte quota, the whole ledger a byte cap with room kept for the app; an unreadable `ledger.json` is moved aside and the host starts with an empty one, the file is synced before it is renamed and private on Unix; a key's silent connection ends after 15 minutes; `store/report` with `probe` or `pick` is the owner's, and a key's plan is not kept. Changing `[profile]`, `[overlays]` or `[agents]` in Settings restarts the host, as changing an agent's command does.
- The host's control channel, `@control` (`canoa_host::control`, designed in `crates/canoa-host/AGENTS.md`): JSON-RPC over a link, opened in this process by the name `@control` as the owner. It keeps the session ledger in the host's home (`control/ledger.json`): `ledger/list`, `ledger/put`, `ledger/remove` and `ledger/clear`, each record owned by whoever put it. A paired key reaches it from a network only when `[host.control]` has a `listen` and lists the key under `grants` (`ledger.read`, `ledger.write`, `worktree`); it then sees and changes only the records it owns, and a key not listed, paired or not, is turned away. `max_records` and `max_record_bytes` are the table's limits. `worktree/new`, `worktree/status` and `worktree/remove` make, read and remove a git worktree with the checks of `_canoa/worktree/*`: for the app anywhere on this computer, for a key only under the `working_roots` of the entries it may use. The app makes its local sessions' worktrees this way and no longer runs git itself. The program Store is there too: `store/list`, `store/report`, `store/latest` and `store/plan` (grant `store.read`), and for the person running the host alone `store/apply` (with `store/progress` notifications and `store/ask` questions on the link, cancelled when it closes), `store/rollback` and `store/remove`; `ServeOptions::with_programs` offers other stores than the built-in ones.
- `canoa serve --local-sources` (`ServeOptions::with_local_sources`) serves the host's own sources, Claude, Codex, Antigravity, Grok and Pi, as entries with no address (`Entry::local`, `Listening::local`): they are reached only over `Local::open`, never by a paired key or the web page, and each line `serve` prints for one says which of its programs were not found (`missing`). A name canoa.cfg already uses is left to it, so an entry of that name there replaces the built-in. The app starts its host with this flag.
- The host's own code can connect to its entries without a socket or a proof: `Serving::local()` gives a `Local`, `Local::open(entry)` a `Link`, and `canoa-ffi` (ABI 2) `canoa_ffi_link_open`, `_send`, `_read` and `_close` give the same to an application. The app reaches a session of its own host this way (`HostSupervisor.openLink`).
- An overlay with an `OVERLAY.md` applies: its front matter is the manifest (YAML, or the format a first line such as `#!toml` names; a tag, anchor, alias or merge key is refused) and its body, when it holds more than white space, is the overlay's context in place of `CONTEXT.md`, which is then ignored and listed as not applied. An overlay with both `OVERLAY.md` and `overlay.cfg` is left out. Before this an `OVERLAY.md` overlay applied as having no manifest. The store and Settings, Profiles show an `OVERLAY.md` as they showed an `overlay.cfg`.
- A prompt-cache lifetime per session. A harness entry takes `cache_lifetime = "default" | "short" | "long"` (refused naming the key for any other value, and for a `program` entry), and `canoa agent claude|codex` takes `--cache-lifetime`; the host passes it in the provider's start request, so Claude Code runs with `CLAUDE_CODE_PROMPT_CACHE_TTL` and `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` at `5m` (short) or `1h` (long), and Codex, which has no such setting, says it ignores it. A client chooses for one session in `initialize`'s `_meta` (`dev.boriken.canoa/cache_lifetime`, `CACHE_META`): the person's choice beats the entry's setting, which beats the chat's default of `long`. The new-session view has a Cache control beside Model and Effort, and shows the provider's own sentence on what it does with the choice, so "ignored" is visible; the choice is kept with the draft and the session. `canoa options` prints that sentence as `cache_lifetime` and the entry's setting as `cache_lifetime_setting`.
- An entry's `listen` may be `pipe:NAME` (a Windows named pipe, or on Unix the socket `NAME.sock` in `XDG_RUNTIME_DIR`) or `unix:PATH` (a Unix socket), for a native client on this machine. It is served as an entry on an address is: the same proof, pairing, `peers` and `max_peers`, with the operating system's access control before it (`coqui-transport-pipe`: the current user alone). `check` prints it, `serve` says it as the entry's `url`, and the served web page never lists it or lets the page connect to it. `Entry::listen` is now a `Listen` (an address or a pipe), `Listening::url` is `pipe:NAME` or `unix:PATH` for such an entry, `ServeError::Pipe` reports one that cannot be bound, and `canoa_host::pipe::PipeChannel` is a `coqui_web_channel::Channel` over a pipe for a client.
- An entry's `listen` may be `pipe:NAME` (a Windows named pipe, or on Unix the socket `NAME.sock` in `XDG_RUNTIME_DIR`) or `unix:PATH` (a Unix socket), for a native client on this machine. It is served as an entry on an address is: the same proof, pairing, `peers` and `max_peers`, with the operating system's access control before it (`coqui-transport-pipe`: the current user alone). `check` prints it, `serve` says it as the entry's `url`, and the served web page never lists it or lets the page connect to it. `Entry::listen` is now a `Listen` (an address or a pipe), `Listening::url` is `pipe:NAME` or `unix:PATH` for such an entry, `ServeError::Pipe` reports one that cannot be bound, and `canoa_host::pipe::PipeChannel` is a `coqui_web_channel::Channel` over a pipe for a client. The app's connection code dials such an entry (`connectBrowserAcpOverPipe`, `connectVerifiedAcpOverPipe`, `hostWorktreeRequestOverPipe`): a hosted source on a pipe starts, reopens and makes worktrees as one on an address does.
- The `program_store` Guatiao kind (`canoa::store`, feature `store`): a library that drives an agent program may offer a store for it, which says where the program's copies are, what its newest version is, what an install would do (every download and how it is checked, every change outside Canoa's folder) and carries the install out in a folder the host made; the host owns the folder, the downloads, the switch and every check. `canoa-host`'s `store` module holds the host's end: `Shelf` (`<programs>/<program>/{current.json, versions/, lock}`, one rename switches a version, two kept), `Footprint` (before and after snapshots of the user's PATH registry value, profile files, `PATH` directories and the registry keys an installer writes, with the undeclared difference named and the registry restored), `LocalTools` (HTTPS fetches whose every redirect stays in the store's declared origins, digests checked as the bytes are written, executable bit after the check, archives refused for absolute paths, `..`, links, device names and size or file bombs), a spawner that starts only absolute programs that are not `.cmd`, `.bat` or `.ps1`, inside the version's folder, with no credential variable, and `Programs`, which runs a plan through them. `store::contract::run` is the suite every store is held to, on a world of documents in place of the network and a stand-in program built at test time; `store::echo` is the good example, and `tests/store_suite.rs` holds stores that each break one rule and must fail the check that names it. `canoa-store-check --library FILE --provider ID --fixture FILE --standin FILE` runs the suite on a store in a library file, on a fixture that names the publisher's documents.
- Five built-in stores, `claude_store`, `codex_store`, `grok_store`, `agy_store` and `pi_store` (`canoa_host::store::registry::built_in`), each downloading the publisher's own file into the version's folder instead of running a publisher's installer: Claude Code (one binary, the manifest's SHA-256), Codex (the `codex-package` archive, the release's checksums and the channel's digest; it has no setting that stops its updater, so a copy says it updates itself), Grok (one binary; the publisher gives no checksum, so the plan says it is not verified), Antigravity (the manifest's SHA-512; only the newest build is served) and Pi (a private Node checked against nodejs.org's SHASUMS256.txt, then that Node's npm with install scripts off, whose own downloads the host does not see). Each turns the program's own updater off where it has a switch and declares nothing outside Canoa's folder. Nothing in them runs at startup, and nothing reads them yet: the host's configuration and the app are the next step. Their downloads trust the operating system's certificate verifier and store, so a TLS-intercepting proxy it trusts works, and an install compares what it changed a second time before it is refused.
- A session started with no folder chosen works in a scratch folder of its own, `${documents}/Canoa/scratch/${session}` by default, which the new-session view shows as **Scratch** and the first message makes (never before; taken away if the agent does not start). `[sessions] workspace` in canoa.cfg is the path template, with `${documents}`, `${home}`, `${session}`, `${date}`, `${time}`, `${datetime}`, `${handler}`, `${source}`, `${host}` and `${fqdn}`; each value is one path segment, and canoa.cfg is refused naming `sessions.workspace` for an unknown variable or none for `${session}`. Settings shows the template with what it makes now. The `${session}` UUID is made with the draft and kept in the session list beside the agent's own id. A new session starts in Scratch rather than in the last folder used or the home folder; recent folders are in the folder menu. `${handler}` is the provider id (`claude`, `codex`, `grok`, `antigravity`, `pi`), and `${date}`, `${time}` and `${datetime}` are fixed when the draft is made.
- `canoa options (claude | codex | NAME --entry) [--format json]` (and `canoa_host::options`, also a `canoa-ffi` job) prints a source's models before a session starts, with no session and no model turn: each model's id, name with its version (`Opus 5.5`), the model it resolves to, and its own efforts, asked of the source's `acp_harness` provider. Claude Code lists Default, Opus, Fable, Sonnet and Haiku; Codex its models with the efforts each takes. A source whose provider cannot say before it starts answers `known: false`.
- A `[host.agents.NAME]` entry may carry a `title`, and the host's line for each entry it serves (and each entry of `/canoa.json`) names the entry's provider id as `harness` (a `harness` entry only) and its `title`, each absent when there is none. The app's source picker shows the title, else the name, with an icon chosen by the provider id (Claude, Codex, Grok, Antigravity, Pi, else a generic one). `Entry` and `Listening` gain `title` and `harness` fields, and `MAX_TITLE` is 64.

### Changed
- Pi runs through `coqui-acp-pi`, coqui-acp's translator of Pi's RPC mode, inside the host (the `pi` harness, registered beside `claude` and `codex`): no `npx`, no `pi-acp`, no Node. The Pi source is ready exactly when the Store's Pi extension finds `pi` (a managed copy, `PATH`, `~/.pi/agent/bin` or `~/.local/bin`), and its readiness names `pi` alone. A managed copy runs as its Node and script; `[permissions] protected` becomes the provider's `protected` list for this source, and absent leaves the provider's recommended one. The Store's Pi install no longer fetches `pi-acp`. The ledger names `coqui-acp-pi` as Pi.
- Which paths a remembered rule never covers is a list the person edits, not names in code. `[permissions] protected` in canoa.cfg
  (text with a pattern a line, or an array) is a gitignore-style list (patterns, `!` allows, later lines win, `#` comments, `~/` at the
  home folder, a drive or `/` at the root, otherwise anywhere; a pattern that matches a folder covers what is under it): the syntax of
  coqui-acp-pi's `protected` setting. Without the key the recommended list applies, which is the old names (every name that starts
  with a dot, build scripts and manifests, `*.config.*`, agent instruction files, `node_modules` and the like); a list the person
  writes replaces it. Settings, Permissions shows the list in a text field, marks the recommended lines, and has **Restore
  recommended**; Save puts the list to use for the rules already made. `*.config.*` now covers every `.config.` file, where
  `*.config.js|mjs|cjs|ts` did. The name catalogues are gone from `permission_rules.dart`; it keeps the segment reading (trailing
  dots and spaces, `~N` short names, device names, ASCII only), the `.` and `..` refusal and link resolution.
- The program stores' sensitive places and credential variable names are lists too. `[host.store] protected` (the places an install
  may not declare a change at, under or holding, with the shared folders a program may enter only by a place of its own) and
  `[host.store] credential_variables` (the variables an install is never given), in the same syntax, with the old names as the
  recommended lists (`canoa_host::store::protect`, `Options::protected`, `Options::credential_variables`, `Options::from_config`,
  `GuardedSpawner::credentials`, `Config::store`). The home itself, the check that a state folder is named for the program and the
  links checks stay in code.
- The host's channels are `coqui-transport`'s `Channel` and `Failure`, and its WebSocket listeners and test dialers are `coqui-transport-web`'s, built with their builders; `coqui-web-channel` is gone from the graph, which holds one `coqui-transport` revision. The coqui-acp crates are at `ad1cef3` and coqui-agentic-peer at `8dad176`. Every listener keeps its settings: plain WebSocket, binary frames, the entry's origins, the proof-stage limits, and a non-loopback address still binds and is logged as non-default.
- The web app has no JavaScript of its own: its peer bridge is Dart (`app/lib/auth/web/`), WebCrypto over `package:web` and Noise as `coqui-peer-noise` compiled to WebAssembly (`app/web_noise`, built by `python app/tool/build_noise.py` into `app/web/noise/`, about 240 KB, never committed; a web build made without it shows Noise agents as unavailable). The bridge's calls, the wire and the keys are unchanged: the Noise key stays the non-extractable WebCrypto X25519 key in `dev.boriken.canoa.peer-noise`, which the WebAssembly never holds. The handshake pauses at the one Diffie-Hellman that uses it and WebCrypto computes it, so a browser without WebCrypto X25519 shows Noise as unavailable. A pairing refused by the agent tells the agent so before the page reports it. The extension keeps its own JavaScript methods and pins them in `bindings/browser/chromium/vendor/COQUI-SOURCE.json`; `app/web/vendor` and `canoa_peer_bridge.mjs` are gone.
- The app starts no agent program of its own. A command in `[agents]` is a source of the host like Claude is, so `SourceKind`, `AgentSource.command`, `startLocalAgent`, `CanoaApp(startAgent:)` and `checkSource`, the app's own program search for commands, and its profile preparation and approval at a session start are gone; a source's memory is kept under its label (before: `canoa/` before a hosted entry's). A session gets none of the app's profile until the host owns it, and says so.
- On the desktop, Claude, Codex, Antigravity, Grok and Pi are sources of the host the app carries, reached over its in-process link, not programs the app starts itself: the app's `agentPresets`, `SourceKind.preset` and the arguments of `canoa agent claude|codex` it started are gone. Their programs are found by the host (on `PATH`, else where Antigravity's and Grok's installers put them), and a source whose program is missing stays listed and says which. Until the host owns profiles, a session on one of these gets none of the profile, as a hosted agent does, and says so. `HostSupervisor.listening` lists the host's own sources too; `served` lists the entries a client on a network can reach, and only those make the host `running` rather than `idle`.
- A permission request from before a reconnect or a restart can no longer be answered: its card goes (it is not shown disabled), its tool line in the conversation reads stopped, a tool a reopened session's replay left waiting or running reads stopped too, and nothing is sent to the agent for any of them. Reopening an earlier session uses `session/resume` where the agent offers it beside `session/load`, and `session/load` where it offers only that.
- The app's model and effort choices before a session starts come from the source's provider through `canoa options`, not from a table in the app: Claude shows its models with their versions ("Opus 5.5", "Fable 5.1", "Default (Opus 5.5)"), Codex its models and the efforts each takes, and the effort list follows the model chosen. The asked list is kept for an hour per source. Antigravity and Grok, whose providers list their models only in a session, show "after start" until a session has run, then what it offered. Presets use the provider's icon, as hosted entries do.
- The app's hosted sources are the agent entries the `canoa` it runs lists as serving, not its own reading of canoa.cfg's `[host]`: an entry added there, a `harness` entry for any provider included, shows in the new-session source picker and Settings once the host serves it, and goes when it stops. A draft kept on a hosted source gets it back when the host serves it.
- Every coqui-acp crate is at `75342dcf`, which has the providers' accounts (`2972b6ad`) beside `modes`, `setting_sources` and the options a source offers.
- A harness entry chooses an `acp_harness` provider by id. `harness = "claude"` and `"codex"` are the providers `coqui-acp-claude` and `coqui-acp-codex` register in the host's own process; any other id is an outside provider that the entry's new `library` or `source` (with `source_settings` and `import_search`, as a provider entry has them) loads, in any language Guatiao loads and with no rebuild of Canoa. The entry's new `settings` table is the provider's configuration, checked against its schema when the host starts (`ServeError::Harness`). `modes` and `setting_sources` stay entry keys with their old meaning and validation (`modes` for claude and codex, `setting_sources` for claude), now the providers' settings of the same names (coqui-acp `953c43e2`); another id takes them in `settings`, and a key also under `settings` is refused as set twice. `EntryKind::Harness` now holds the provider id (a string), `origin` and `settings`. A Python `acp_harness` runs a session through `canoa` with `CANOA_TEST_PYTHON`.
- A harness entry's provider is loaded into a registry of its own, so an id resolves from that entry's file and no other; `library` or `source` on `harness = "claude"` or `"codex"` is refused; a `library` no longer inherits a `source` entry's DLL search.
- A Codex entry with `profiles` holds a resumed thread to the entry's `working_roots` as one without does; the profile's skills directory is added to the roots the provider is given (it was given none).
- How a harness instance departs from its provider's defaults, such as `settings = { allow_bypass = true }`, is logged at `info` as configuration.
- A harness entry's `settings` for `claude` or `codex` are checked as the entry's keys are (a mode, policy or sandbox must be text and one the provider takes; `executable` set twice is refused) and a relative `executable` there is made absolute from canoa.cfg's directory.
- The host's log no longer carries a harness's notices or the reason its program exited, for a harness entry: the provider kind has no route for them yet. A connection works on at most 64 requests, as before (`max_requests` in `settings` changes it).

- Usage shows beside the mode. An agent that advertises coqui-acp's usage extension gets a control after the mode with the bucket that matters most (a percentage, tokens or money used of the limit, and when it resets or its rate), a status from `[usage] warn_permille` (800 by default) and an error colour once exhausted, and a menu of every bucket; a session's spend joins the conversation's header. `canoa` passes `_coqui_acp/usage`, its `_coqui_acp/usage_update` notification and the client's wish for notices, and tells the agent the entry's name as the account and sets it on every report it relays; `stdio_agent --scripted --usage` plays an agent that reports a quota.
- Every coqui-acp crate is at `981a64ad`, on Guatiao `0350bae7` and coqui-aos `c73cf23`, for the usage model, its inferred limits and the Antigravity quota reader.
- Antigravity's usage is reported, not only inferred. `usage = "antigravity"` on a `[host.agents]` entry with `program` makes `canoa` read the agy's quota (coqui-acp's `antigravity` reader) from the loopback port its process opens, as `reported` buckets beside any inferred hit: after `session/new` and `session/load` (retrying at 2, 4, 8 and 16 seconds until the port is up), after each prompt answer, and for `_coqui_acp/usage` from a reading over 15 seconds old, always off the relay thread. The agent's own processes are its process and those below it (a launcher's child included), found from the system's process table with creation times, so a reused process id is not taken for a child. The desktop app installs an overlay from git beside Canoa.cfg, showing the commit, the tree digest and every file a sync would add, change or remove before anything changes, and applying **pins it by its AOS tree digest** in Canoa.cfg (`{ source, pin }`); a check whose digest is not the pin installs nothing, and the installed copy is digested again each time profiles are built, a changed one left out until synced. Nothing from a source runs: files are read from git's objects, never checked out; a link, a submodule, a name AOS refuses or two names differing only in case refuse the overlay, and entries under an excluded name (`.git`, `node_modules`, ...) are never installed. Only the named ref is fetched, a whole commit id pins that commit, and `http` or `git` sources are taken only at one. A project's profile is trusted per directory, as the file was shown, in `trust.json`; a changed file is ignored until trusted again, and trust can be revoked.
- `canoa_host::profile`: the same schema, merge, view and secret resolution in Rust, held to the app's by shared vectors (`crates/canoa-host/tests/vectors/profile.json`), and `overlay_layer`, which makes an AOS overlay's layer as the app does.
- `canoa_host::aos`: AOS v0 overlays read statically (TOML and JSON; YAML refused), validated, named, located by source string, digested and composed, and an overlay's environment built with substitution, on the specification's conformance vectors (agent-overlay-spec `061b8f5`, in `crates/canoa-host/tests/vectors/aos/`).
- The app keeps a list of every session it opens or resumes, by harness, across runs: the harness and the version the agent reported, the agent entry, where it runs (this computer, the app's `canoa-host`, a paired peer with its id, or the browser's provider), its working directory, the agent's session id, its title, and when it was created and last used. The side list groups the sessions not open now by harness, filters by one, and reopens one by starting its agent again or reaching its peer again, through `session/load` or `session/resume` as the agent offers; where it offers neither, or the session came through the browser, the row says so. Removing a row never deletes the agent's own session, and the confirmation says so. On a desktop it is `sessions.json` beside Canoa.cfg, on the web this origin's IndexedDB.
- Canoa.cfg `[sessions]`: `keep` (200), `keep_text` (off) and `text_messages` (200). What was said is kept only when `keep_text` is on, and Settings clears it. `[harnesses]` maps the name an agent reports to a harness, beyond the built-in Claude Code, Codex, Gemini, Pi, OpenCode and Grok; an unknown agent is labelled by its entry.
- `canoa-host serve --key-limit` and `--no-rekey`, and `ServeOptions::with_key_limit` and `with_rekey`; a setting looser than the default is logged. A client of the other method is logged as a method mismatch, never as a key to accept. A home records the method named last, so a host the app runs naming none keeps working after a move.
- Hosting shows the method beside the host's id, and the app's and the extension's add-by-hand forms ask for the agent's method instead of assuming one.
- Hosting reports a host that refused Canoa.cfg in the host's own words: it waits, up to `errorDrain` (2 s), for the host's standard error to close after its exit, which can come first.
- A Noise agent that turns the extension's key away fails the page's connect with a network error instead of leaving it waiting: the dial waits briefly after the handshake for the agent to end the connection, and a link that ended before its close callback was set still reports it.
- The extension reports a link that ends without the agent's close record as cut, sizes its frame limit for the longest record a Noise sender can make, refuses a known key named under another method, shows `mcp-config` with its key for the chosen machine's method, and says the `pair-accept --origin` its own origin needs.

- The extension proves an agent by the method stored with its key, Noise or WebCrypto, and pairs with a machine by the PIN it shows under Noise (**Pair with a code**). Each method has a key of its own. An agent stored before methods is WebCrypto's; a browser whose WebCrypto has no X25519 shows a Noise agent as unreachable, and says why, rather than trying another method. Discovered agents carry the method their record names.
- The app's web build proves an agent by the method named with its key in the connect dialog, Noise or WebCrypto, and pairs by the PIN a `coqui-acp-bridge pair-accept --method noise --origin ORIGIN` shows, the dialog naming this page's origin. An agent typed in by hand has no method until the person picks one; one named by a record or a host comes prefilled, and a PIN pairing fills in Noise. Each method has a key of its own, and the dialog shows this browser's id under the method chosen. A method this browser cannot run is shown with the reason, and connecting by it is refused before anything is dialled; no other method is tried. `coqui_web` moves to the revision whose `StagedChannel` gives a setup message as bytes.
- `app/web/vendor` holds `coqui-peer-noise` beside `coqui-peer-webcrypto`, each pinned by blob in `COQUI-SOURCE.json`, now one entry per file.

- `canoa-host` proves by Noise or by WebCrypto, the method of this user's identity: `serve`, `id` and `pair` take `--method noise|webcrypto`, and `serve` and `pair` print the method beside the peer id. A home keeps each method's identity in a file of its own and keeps the method it has; one with both has to name one. A client of the other method is refused, and the log says why.

- An MCP client outside any ACP session, such as an IDE or a CLI agent, can ask for a browser tab: a person turns this on for one paired machine under **Canoa browser permissions**, and `coqui-acp-bridge mcp-config` prints one stable entry for it. Off by default, and out of a page's reach.
- `canoa-host`, a new crate and command: serves each `[host]` entry of Canoa.cfg, a stdio ACP agent or a Guatiao agent provider, to keys you paired, on loopback only. `peers`, `accept` and `revoke` manage the keys; a removed key loses its link within about a second. A client cannot have it start a program: a stdio MCP server in a request and `_meta` never reach a stdio agent.
- The chat dials `ws://` on loopback, where the host listens. Everything after the peer proof is sealed, so the transport carries nothing it could read.
- The app keeps Canoa.cfg's `[host]` table when it saves its settings.
- `canoa-host serve --until-stdin-closes`: the host ends every agent it started, then itself, when its input closes, so it ends with the program that runs it. `Serving::stopper` and `Stopper::stop_agents` do the same from the library.
- The desktop app runs `canoa-host` as its child: the one `CANOA_HOST` names, else the one beside its executable, which the desktop build now puts there. It is started again after an unplanned end, with a pause that doubles up to a minute, and ended with its agents on quit or when the app dies.
- **Hosting**, in the side rail and the tray menu: the host's state and id, its agents, adding one by its command, the keys that may connect, pairing or removing one only from a dialog that shows its whole id, and a PIN for a native program.
- The tray menu opens Hosting, a double click on the tray icon opens the chat, and where Linux shows no tray icons, closing the window minimizes it rather than hiding it out of reach. Settings has **Quit Canoa**.
- `canoa-host pair`: shows a PIN that a native client uses to pair, such as `coqui-acp-bridge pair-dial`. One wrong try ends it.
- A `canoa-host` tool entry, `[host.tools.NAME]`, serves a command-line tool that has no ACP as an ACP agent, with no code for that tool: Canoa.cfg says how it keeps a conversation (one process per session, or one per message), how a prompt goes in, and how each JSON line it writes becomes text, thinking, a tool call, the end of a turn, or a question to the person, answered back to the tool only when they allow. Every session opens by saying what the tool does without asking, in the entry's own words, which an entry must give, and whether it remembers earlier messages; the app shows these in the conversation. `examples/config/pi.cfg` serves Pi through its RPC mode, with Pi's permission-gate extension's questions reaching the person.
- The connect dialog offers **Pi** through its ACP adapter, `pi-acp` 0.0.34, when `pi` is installed.
- A `canoa-host` provider entry can name a Guatiao source instead of a library, with `[host.providers.NAME.source_settings]`: a provider written in Python, Lua, JavaScript, Rhai or WebAssembly is served from one entry. `[host.providers.NAME.settings]` gives a provider the configuration it declares, checked against its schema. Settings reach the provider's process on its standard input, never its command line, and the process runs in Canoa.cfg's directory. The host and a provider's process speak ACP over a loopback socket of their own, so what a provider prints goes to the host's log, 1 MiB per connection at most, and never to the client. `Stopper::stop_agents` and `--until-stdin-closes` end provider processes too.

### Changed

- `chrome.storage.local` answers only the extension's own pages, so a content script can no longer read the agents' secret.
- The transport and the ACP client moved out: `coqui-web` and `coqui-acp` replace `crates/coqui-net-transport`, `bindings/dart/coqui_net_transport`, `app/lib/transport` and most of `app/lib/acp`. Canoa now also connects to ACP v1 agents.

### Fixed

- When a source cannot start, the app writes the reason it shows in the conversation to its log as well (`Canoa: NAME was not started: REASON`).
- Opening or refreshing the store reads a catalog's icons with one `git ls-tree` per few thousand characters of paths and one `git cat-file --batch`, not a process pair for each icon.
- The store offers Update and Remove only for an overlay it installed (its install record names the catalog); an overlay canoa.cfg names by hand from the same source is said to be, and left alone.
- The store shows an entry's homepage and repository as links that open in the system's browser when tapped (a plain ASCII `http` or `https` address; anything else stays text), as the overlay specification asks.
- A reopened session whose agent refuses, or no longer offers, the mode it was left in is given the profile's mode, and the profile report no longer says the kept mode replaced it.
- The web app draws its text under the host's strict policy with no `connect` source: it carries Roboto and points Flutter's fallback fonts at the site, so its build fetches nothing from `fonts.gstatic.com`.
- A hosted profile read a version 2 agent's capabilities and name from version 1's places (`agentCapabilities`, `agentInfo`), so a version 2 client was told the agent took no context, skills or MCP servers: version 2's `capabilities` and `info` are read now.
- Saving Settings, pinning, installing or removing an overlay, a catalog change, or keeping MCP choices no longer drops `[permissions] full_access` and `[notifications]` from the Canoa.cfg it saves.
- A session with an agent on `canoa-host`'s plain WebSocket on loopback is taken into the chat's list: it refused any `ws://` endpoint, though the dialer allows one on loopback.
- A sealed link that ends while the chat is still sending a request now fails that request. Before, under Noise, a refused key's link could end while the first request was being sealed, and the error reached no one.
- Settings opens from the side rail: its dialog, like Hosting's, now opens on the app's own navigator.
- A failed WebSocket or WebTransport connection now releases its socket. Before, `close()` did nothing once the stream had ended, so a peer that sent a frame over the limit left the socket open.
