# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- Settings → Profiles leaves out only the `[about]` field that is invalid or unknown, keeping the summary and icon beside it, and shows an overlay's icon as the still pixels of its first frame within the `[store]` icon limits.
- New keys prove by Noise: `canoa-host` on a home with no identity, and the key the extension calls its own. A home or agent made before keeps WebCrypto, and its pairings keep working. To move a host, run `canoa-host serve --method noise` once, which the home then records for the app's own `serve` and `pair`, and pair each browser again, by PIN or by accepting its Noise key: a key of one method is never the other's. Canoa's app reaches such a host by Noise once the person names that method, which `serve` prints and Hosting shows, or pairs by PIN.
- `canoa-host` builds on Guatiao `266baf9c`, coqui-acp `ee19118`, coqui-agentic-peer `9b1fee4` and coqui-web `445007a`, and the app on coqui-web `445007a`. A Guatiao manifest is now `<name>.guatiao` (or `<name>.guatiao.<major>[.<minor>]`): a `*.guatiao.toml` is no longer found, so rename each. A Python provider's `close` slot is `close`, no longer `close_`. A Python source's interpreter no longer reads `PYTHONPATH`, `PYTHONHOME` or the user's own site-packages unless its entry says `isolation = "inherit"`.

### Added

- A permission request shows every answer the agent offers, under its own names, refusals first: allow once, allow always, refuse once, refuse always, and any kind Canoa does not know, as it came. The answer chosen is the one sent. An "always" answer is the agent's to remember, and the card says so. The app builds on coqui-acp for this.
- Full access, off unless the person turns it on, for one conversation (**Full access…** in its header, after a dialog saying what it does) or for an agent (Settings, or `[permissions] full_access` in Canoa.cfg). It answers each request that offers to allow once with that option, and says so in the conversation; a request offering no allow once, an `allow_always` alone included, is still the person's. While it lasts a banner on the conversation and a mark on its row say so, and the banner's **Turn off** ends it in one action. Turning it on is logged as `weakened:`. It never touches the browser extension's grants.
- A conversation the person is not looking at notifies them when its agent asks leave to use a tool, asks a question or finishes a turn: a Windows toast, a freedesktop notification on Linux, or the browser's Notification API once allowed. A notification names the conversation, its agent and the kind, never what the agent sent, and choosing it opens the conversation. `[notifications]` in Canoa.cfg and Settings turn each kind off. The side list marks a conversation that needs the person, one that works and one with news since it was chosen, and the tray says how many wait.
- **Changes**: every file a conversation's tools changed, by file, at its latest, with additions and removals, a mark of viewed that holds until the file changes again, and a comment on any line that goes into the message being written with the file and line. Built from what the agent sent, never from disk; beside the conversation on a wide window, a sheet on a phone. A patch carries the files its ACP v2 `changes` or its `+++` lines name.
- Keyboard shortcuts for a new session, going to a session, the message being written, Stop, allowing or refusing once what the agent asks, and the changes; a command palette (Ctrl+K, ⌘K on a Mac) of actions, sessions and the agent's own commands; a sheet listing the shortcuts (Ctrl+/); and Up in an empty message bringing back the last one sent there.
- A message written while the agent works is queued under the conversation, editable and removable, and sent when the turn ends, one per turn. A stopped or failed turn holds the queue rather than dropping it, until the person sends the next or clears it.
- An agent's questions (ACP's form elicitation, which Canoa now advertises) show as a form in the conversation: text, choices, numbers and yes-or-no from the agent's schema, answered, declined or cancelled, the agent's text shown as data. A question notifies like a permission request. Built on coqui-acp `a381c4a`.
- An overlay store: **Store…** in Settings → Profiles lists the overlays of the [AOS catalogs](https://github.com/Boriken-Dev/agent-overlay-spec/blob/main/spec/v0/catalog.md) Canoa.cfg's `[catalogs]` names (a label of yours = `<repository>@<ref>#<catalog file>`), each fetched from git as an overlay is, with no checkout. Entries show their icon, name, summary, tags, catalog and source, and are searched by words and tags; a name two catalogs offer is shown once per catalog as `label/name`. An overlay's page shows what its catalog claims, then, once fetched and before anything is installed, what the overlay itself says and would do, computed from its own manifest and files as Settings → Profiles applies them. A catalog's pin is checked against the tree fetched, and a mismatch refuses the install. Install, update and remove go through the install path of an overlay named by hand and pin the overlay by its tree digest in `[overlays]`; a pin Canoa.cfg already gives it moves only when the person confirms the move, and an overlay Canoa.cfg names from another source is neither installed over nor removed. A source holding a password is refused, catalog and manifest text cannot add a line that reads as Canoa's own, and `[store]` bounds the entries listed and icon files read per catalog. Icons are PNG or WebP only, their size and header dimensions checked before decoding, shown as the still first frame; `[store]` sets the catalog and icon limits, at the specification's defaults. The Dart catalog reader passes the specification's `catalog.json` vectors and the catalog cases of `reading.json` (agent-overlay-spec `061b8f5`), all but those in YAML, which Canoa refuses.
- A source entry takes `import_search`, `library` or `path`: on Windows, whether what the source imports itself (Python's `python3.dll`) may come from the Windows directory, the working directory or `PATH` when `import_dirs` leaves it missing. Without it, an entry whose `import_dirs` names a directory takes `library`, and one that names none takes `path`, as every source did before; `canoa-host serve` logs each entry on `path` as weakened, saying how to narrow it.
- A Python source entry takes `isolation` (`shipped`, `isolated` or `inherit`), `home` and `import_dirs` in `[host.providers.NAME.source_settings]`. `home` and `import_dirs` are made absolute from Canoa.cfg's directory, as `dirs` and `paths` are; on Windows `import_dirs` names where `python3.dll` is found, in place of `PATH`. `canoa-host serve` logs an entry with `isolation = "inherit"` as weakened.
- Profiles: what an agent is launched with (environment variables, an initial context as text or a file, skills, MCP servers, and the model, effort and mode it starts with), in layers merged lowest first: built-in, named overlays, the person's own `[profile]`, a project's `.canoa/profile.toml` once its directory is trusted, the agent's `[agents.NAME.profile]`, and the session's. A later layer wins per key, environment variables, skills and MCP servers merge by name, and a layer can remove an entry (`remove = true`) or take back a value (`unset`). Secrets come only from `from_env` or `from_file`, resolved when a session starts and never shown or logged. **Settings → Profiles** shows each agent's effective profile with the layer of every value. An overlay or a project reads only the variables one of the person's own layers lists in `share_env`, and may not set those that decide what runs, where an agent's requests go or where a harness keeps its configuration (`PATH`, `NODE_OPTIONS`, `*_BASE_URL`, `LD_*` and the like); what it sets otherwise is left out and listed. Applying a profile to a harness comes later.
- `[overlays]` in Canoa.cfg names each overlay: an [Agent Overlay Specification](https://github.com/Boriken-Dev/agent-overlay-spec) v0 overlay, by an AOS source string (`<repository>@<ref>#<path>`) or a local directory. Its `overlay.cfg` (TOML, or JSON after `#!json`) and conventional files are read statically and validated, in Dart and in Rust on the specification's vectors; overlays layer in AOS composition order and `requires` is resolved among them. Canoa applies an overlay's environment (env files, `env`, `paths`, substituted when a session starts, reading only what overlays set and the variables you share), skills, MCP servers, rules, routing and context, and the model and effort hints for the agent's harness. Env scripts, setup, dependencies, runtime probes, commands and the `bin`/`lib` defaults, which would change `PATH`, `PYTHONPATH` and `NODE_PATH`, are read and listed in Settings → Profiles as not applied by Canoa yet; nothing of an overlay runs. An overlay that sets a variable a layer from elsewhere may not set, now including every variable AOS calls sensitive, is left out. `[about]` is store metadata: its summary and icon (PNG or WebP, its header checked before decoding, never SVG) show beside the overlay, and a problem in it never stops one. The desktop app installs an overlay from git beside Canoa.cfg, showing the commit, the tree digest and every file a sync would add, change or remove before anything changes, and applying **pins it by its AOS tree digest** in Canoa.cfg (`{ source, pin }`); a check whose digest is not the pin installs nothing, and the installed copy is digested again each time profiles are built, a changed one left out until synced. Nothing from a source runs: files are read from git's objects, never checked out; a link, a submodule, a name AOS refuses or two names differing only in case refuse the overlay, and entries under an excluded name (`.git`, `node_modules`, ...) are never installed. Only the named ref is fetched, a whole commit id pins that commit, and `http` or `git` sources are taken only at one. A project's profile is trusted per directory, as the file was shown, in `trust.json`; a changed file is ignored until trusted again, and trust can be revoked.
- `canoa_host::profile`: the same schema, merge, view and secret resolution in Rust, held to the app's by shared vectors (`crates/canoa-host/tests/vectors/profile.json`), and `overlay_layer`, which makes an AOS overlay's layer as the app does.
- `canoa_host::aos`: AOS v0 overlays read statically (TOML and JSON; YAML refused), validated, named, located by source string, digested and composed, and an overlay's environment built with substitution, on the specification's conformance vectors (agent-overlay-spec `061b8f5`, in `crates/canoa-host/tests/vectors/aos/`).
- The app keeps a list of every session it opens or resumes, by harness, across runs: the harness and the version the agent reported, the agent entry, where it runs (this computer, the app's `canoa-host`, a paired peer with its id, or the browser's provider), its working directory, the agent's session id, its title, and when it was created and last used. The side list groups the sessions not open now by harness, filters by one, and reopens one by starting its agent again or reaching its peer again, through `session/load` or `session/resume` as the agent offers; where it offers neither, or the session came through the browser, the row says so. Removing a row never deletes the agent's own session, and the confirmation says so. On a desktop it is `sessions.json` beside Canoa.cfg, on the web this origin's IndexedDB.
- Canoa.cfg `[sessions]`: `keep` (200), `keep_text` (off) and `text_messages` (200). What was said is kept only when `keep_text` is on, and Settings clears it. `[harnesses]` maps the name an agent reports to a harness, beyond the built-in Claude Code, Codex, Gemini, Pi, OpenCode and Grok; an unknown agent is labelled by its entry.
- `canoa-host serve --key-limit` and `--no-rekey`, and `ServeOptions::with_key_limit` and `with_rekey`; a setting looser than the default is logged. A client of the other method is logged as a method mismatch, never as a key to accept. A home records the method named last, so a host the app runs naming none keeps working after a move.
- Hosting shows the method beside the host's id, and the app's and the extension's add-by-hand forms ask for the agent's method instead of assuming one.
- Hosting reports a host that refused Canoa.cfg in the host's own words: it waits, up to `errorDrain` (2 s), for the host's standard error to close after its exit, which can come first.
- A Noise agent that turns the extension's key away fails the page's connect with a network error instead of leaving it waiting: the dial waits briefly after the handshake for the agent to end the connection, and a link that ended before its close callback was set still reports it.
- The extension reports a link that ends without the agent's close record as cut, sizes its frame limit for the longest record a Noise sender can make, refuses a known key named under another method, shows `mcp-config` with its key for the chosen machine's method, and says the `pair-accept --origin` its own origin needs.

- The extension proves an agent by the method stored with its key, Noise or WebCrypto, and pairs with a machine by the PIN it shows under Noise (**Pair with a code**). Each method has a key of its own. An agent stored before methods is WebCrypto's; a browser whose WebCrypto has no X25519 shows a Noise agent as unreachable, and says why, rather than trying another method. Discovered agents carry the method their record names.
- The app's web build proves an agent by the method named with its key in the connect dialog, Noise or WebCrypto, and pairs by the PIN a `coqui-acp-bridge pair-accept --method noise --origin ORIGIN` shows, the dialog naming this page's origin. An agent typed in by hand has no method until the person picks one; one named by a record or a host comes prefilled, and a PIN pairing fills in Noise. Each method has a key of its own, and the dialog shows this browser's id under the method chosen. A method this browser cannot run is shown with the reason, and connecting by it is refused before anything is dialled; no other method is tried. `coqui_web` moves to the revision whose `StagedChannel` gives a setup message as bytes.
- `app/web/vendor` holds `coqui-peer-noise` beside `coqui-peer-webcrypto`, each pinned by blob in `COQUI-SOURCE.json`, now one entry per file.

- `canoa-host` proves by Noise or by WebCrypto, the method of this user's identity: `serve`, `id` and `pair` take `--method noise|webcrypto`, and `serve` and `pair` print the method beside the peer id. A home keeps each method's identity in a file of its own and keeps the method it has; one with both has to name one. A client of the other method is refused, and the log says why.

- An MCP client outside any ACP session, such as an IDE or a CLI agent, can ask for a browser tab: a person turns this on for one paired machine under **Canoa browser permissions**, and `coqui-acp-bridge mcp-config` prints one stable entry for it. Off by default, and out of a page's reach.
- `canoa-host`, a new crate and command: serves each `[host]` entry of Canoa.cfg, a stdio ACP agent or a Guatiao agent provider, to keys you paired, on loopback only. `peers`, `accept` and `revoke` manage the keys; a removed key loses its link within about a second. A client cannot have it start a program: a stdio MCP server in a request and `_meta` never reach a stdio agent.
- The chat dials `ws://` on loopback, where the host listens. Everything after the peer proof is sealed, so the transport carries nothing it could read.
- The app keeps Canoa.cfg's `[host]` table when it saves its settings.
- `canoa-host serve --until-stdin-closes`: the host ends every agent it started, then itself, when its input closes, so it ends with the program that runs it. `Serving::stopper` and `Stopper::stop_agents` do the same from the library.
- The desktop app runs `canoa-host` as its child: the one `CANOA_HOST` names, else the one beside its executable, which the desktop build now puts there. It is started again after an unplanned end, with a pause that doubles up to a minute, and ended with its agents on quit or when the app dies.
- **Hosting**, in the side rail and the tray menu: the host's state and id, its agents, adding one by its command, the keys that may connect, pairing or removing one only from a dialog that shows its whole id, and a PIN for a native program.
- The tray menu opens Hosting, a double click on the tray icon opens the chat, and where Linux shows no tray icons, closing the window minimizes it rather than hiding it out of reach. Settings has **Quit Canoa**.
- `canoa-host pair`: shows a PIN that a native client uses to pair, such as `coqui-acp-bridge pair-dial`. One wrong try ends it.
- A `canoa-host` tool entry, `[host.tools.NAME]`, serves a command-line tool that has no ACP as an ACP agent, with no code for that tool: Canoa.cfg says how it keeps a conversation (one process per session, or one per message), how a prompt goes in, and how each JSON line it writes becomes text, thinking, a tool call, the end of a turn, or a question to the person, answered back to the tool only when they allow. Every session opens by saying what the tool does without asking, in the entry's own words, which an entry must give, and whether it remembers earlier messages; the app shows these in the conversation. `examples/config/pi.cfg` serves Pi through its RPC mode, with Pi's permission-gate extension's questions reaching the person.
- The connect dialog offers **Pi** through its ACP adapter, `pi-acp` 0.0.34, when `pi` is installed.
- A `canoa-host` provider entry can name a Guatiao source instead of a library, with `[host.providers.NAME.source_settings]`: a provider written in Python, Lua, JavaScript, Rhai or WebAssembly is served from one entry. `[host.providers.NAME.settings]` gives a provider the configuration it declares, checked against its schema. Settings reach the provider's process on its standard input, never its command line, and the process runs in Canoa.cfg's directory. The host and a provider's process speak ACP over a loopback socket of their own, so what a provider prints goes to the host's log, 1 MiB per connection at most, and never to the client. `Stopper::stop_agents` and `--until-stdin-closes` end provider processes too.

### Changed

- `chrome.storage.local` answers only the extension's own pages, so a content script can no longer read the agents' secret.
- The transport and the ACP client moved out: `coqui-web` and `coqui-acp` replace `crates/coqui-net-transport`, `bindings/dart/coqui_net_transport`, `app/lib/transport` and most of `app/lib/acp`. Canoa now also connects to ACP v1 agents.

### Fixed

- A session with an agent on `canoa-host`'s plain WebSocket on loopback is taken into the chat's list: it refused any `ws://` endpoint, though the dialer allows one on loopback.
- A sealed link that ends while the chat is still sending a request now fails that request. Before, under Noise, a refused key's link could end while the first request was being sealed, and the error reached no one.
- Settings opens from the side rail: its dialog, like Hosting's, now opens on the app's own navigator.
- A failed WebSocket or WebTransport connection now releases its socket. Before, `close()` did nothing once the stream had ended, so a peer that sent a frame over the limit left the socket open.

### Changed

- The app builds on `coqui_acp` `d64ea1a`. A turn the agent ends as cancelled shows "Stopped." and ends; a permission request the app cannot read is answered cancelled and said in the conversation, while the turn goes on; output a bridge dropped while nobody was connected is said as a notice; and a client takes only the traffic of the sessions it opened.
- `canoa-host` builds on coqui-acp `d64ea1a`, whose bridge stops an agent with everything it started: by job object on Windows, by process group on Unix.
- Text files are LF on every platform (`* text=auto eol=lf`). A Windows checkout made
  before this needs `git add --renormalize .` or a fresh clone.
