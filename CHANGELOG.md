# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added
- **The largest message a connection takes is a setting, so a large attachment is your choice.** `[host] max_message_bytes` (16 MiB by default, as it was) is the longest ACP message either way, for the links of paired keys, the app's own link, an agent program's output and the link to another machine's agent, with no ceiling of Canoa's own; a prompt carrying an attachment over about 12 MB passes the default, and a message over the setting is refused with the setting named. `canoa agent` takes `--max-message-bytes` for the same on its standard streams.
- **The default profile applies to every agent entry that names no profile.** canoa.cfg's top level (`[profile]`, `[overlays]`, `[profiles.default]`) now reaches the sessions of a hand-written `[host.agents.NAME]` program or harness entry as it does a source of the host's own: its overlays, skills, hooks, access, items and variables, `<NAME>_OVERLAY_ROOT` included; before, only an entry with `profiles` or `own_profile` got a profile, so the overlays never reached an entry written by hand. An entry that names `profiles` gets those and one that should run bare names an empty profile. `canoa check` prints the profile each entry starts with and why (`profile:`, and a `profile` field in JSON), and *Effective setup* has a `profile` item. `own_profile` is gone: an entry that sets it is refused as an unknown key, and the agent entry form no longer offers it.
- **The Secrets section has an index of vaults, like the Store.** All vaults, then one row per vault with how many secrets it holds; choosing a vault shows its secrets, what it can do, its settings and Change its settings and Remove this vault for one you set up. Set a secret from a vault's page starts on that vault, and Set up a vault is at the foot of the index. Tried against a stand-in host's list, not a real operating system store.
- **The system vault lists the credentials your operating system's store holds, not only Canoa's own.** On Windows every generic credential of your account shows in Secrets under the name Credential Manager gives it (its target), with its user name beside it and marked as another program's; the Keychain and the Secret Service are listed through their own search. Show reads one when you press it (a value that is neither UTF-8 nor UTF-16 text says so instead of showing bytes), Forget on one asks first and deletes it from the store, and a secret you set by hand is always Canoa's own, never written over another program's. A secret provider can now list such entries in `Names::others`. An agent gets nothing more: it still asks by name through the vault routing and the permission mode it already had. Tried over an in-memory stand-in for the store, not the real Credential Manager, Keychain or Secret Service.
- **A terminal copies and pastes like the terminals you know, in the desktop app and in the browser.** Ctrl+Shift+C, Ctrl+Insert and, on Windows, Ctrl+C while text is selected (with none it is still the interrupt) copy the selection; Ctrl+Shift+V, Ctrl+V and Shift+Insert paste, and ⌘C and ⌘V do both on a Mac; a right click has Copy, Paste and Select all; a paste is one write with line ends as Enter and the bracketed-paste markers when the shell asked, with no limit of its own. In a browser the keyboard paste is the page's `paste` event, which needs no permission (the menu's Paste, the one that must read the clipboard, says in words when the browser refuses), and a copy falls back to the browser's copy command where the clipboard API is missing. Select all is Ctrl+Shift+A (⌘A on a Mac): Ctrl+A is the shell's again. The web paste, copy and interrupt were run in Edge (`e2e/terminal_clipboard.mjs`); the desktop keys are widget-tested under each platform's key names, not run on Linux or macOS.
- **The speech-to-text of an account is described by a library, so the host names no OpenAI address, model or key field: `canoa-openai`.** A new `account_speech` kind says which accounts of some kinds can call a speech-to-text service (the standard their kind provides and the address its model API starts from, where a recording is posted, the credential that holds the key, the models), and the host offers each such account, lends its key while a recording opens and never writes it down; the Python and JavaScript SDKs have an `AccountSpeech` base class. OpenAI's offer is `canoa-openai`'s description, the offer made of an account is now `openai:NAME` (it was `openai_account:NAME`), the provider list names the account's kind for the person (`account_kind`), and the offer to type an OpenAI key into a form of its own is gone: add the key as an account, which is what an account is for.
- **whisper.cpp is a library's, like Foundry Local: `canoa-whisper`.** Its program and models, and the speech-to-text offer made of them, are no longer in the host: the crate adds the Store type `whisper` (its program `whisper_store`, no longer in Runtimes, and its models page `whisper_models`, which marks the model the host's copy holds) and says how the installed copy is run, and a build without it has no whisper.cpp program, models or offer. For that, a `model_store`'s speech service may be a program run for each recording (`SpeechService::program`; the host passes the launch path of the type's first store as `ServiceQuery::program` and writes the `speech_command` provider from the `SpeechRun` the library answers), where it was only a server; the offer, its `store`, its models as the install's channel and `speech/enable` are as they were.
- **The host's own pool of one account is not listed.** `pools/list`, an entry's `pools` and so the pool picker and Settings show an `any-<standard>` only while two or more accounts hold it, since one account cannot rotate (a harness's own login alone made `any-pi`, `any-codex` and the like); a session or canoa.cfg that names one still gets it, whatever it holds. A kind whose settings mark a property `x-provides-by-value` (`coqui_acp_api::PROVIDES_BY_VALUE`) provides the standards its value lists, so a Pi provider key whose variable is `ANTHROPIC_API_KEY` is in `any-anthropic-api` beside the Anthropic key accounts, and a harness that is not the kind's own is not given that setting.
- **A Store type's models are a library's, and so are their setting and their speech-to-text offer.** A new `model_store` kind lists the models of a Store type (`ExtensionType.models` names the provider), says what `+` does for each, runs one action through the host's spawner and keeps a per-model setting described as a guatiao schema and form; the host's `store/models`, `store/model` and `store/model_setting` replace `foundry/models`, `foundry/model` and `foundry/window`, and the Store's models page and its Use as speech provider button are drawn from what the library says, so the host and the app name no vendor's model. The window of a Foundry Local model is now kept as `[foundry.models."ID"] window = N` (it was `[foundry.windows]`), a speech table's `service` is the id of the Store type (`foundry`, no longer `foundry_local`), and the Python and JavaScript SDKs have a `ModelStore` base class.
- **A LiteLLM proxy is an account that runs Codex and Claude Code on one key and one budget.** The account kind `litellm` provides the OpenAI API and the Anthropic Messages API, so every harness that accepts either runs on it, in the pools of both standards, with one credential, one holder and one usage. Make it by signing in through the proxy's own SSO (LiteLLM's `--pkce` browser flow: Canoa shows the page, your browser signs you in, and the key comes back to an address on this computer; the proxy has to offer it, a beta of LiteLLM) or by setting a key; the key is kept as a secret and never in canoa.cfg. The account lists the proxy's models (`/v1/models`) and reports the key's budget (`spend` against `max_budget`, with when it resets) and its request and token limits (`/key/info`); a signed-in key the proxy stops accepting is renewed by its refresh token. Tried against a loopback stand-in of the proxy, never a real one. `canoa-litellm` carries it as a library, like `canoa-foundry`.
- **Any address that speaks one or several of the APIs agents use is an account.** The `api-gateway` kind (`canoa accounts add NAME --harness H --method api-gateway --input base_url=... --input standards=openai-api,anthropic-api`) names an address, the standards it speaks (any ids, one or several) and a key, so an OpenRouter-, Portkey- or LiteLLM-style proxy needs no crate of its own. Every harness that accepts one of the standards runs on it, the address moved to the harness's own endpoint setting; the models are the address's `/v1/models` when it speaks `openai-api`; the address and the form of the key can be named for each standard (`--input addresses=openai-api=https://llm.example.com/v1 --input credentials=anthropic-api=auth_token`), so a gateway that serves its standards at different addresses, or wants a bearer token for one and a key for another, is one account that runs Codex and Claude Code each at its own.
- **A library you add can offer account kinds, like a bundled one.** An `account_provider` that no agent owns, in a library or source named by `[host.extensions.NAME]` or by an agent entry, is an account maker: its kinds and sign-in methods appear in the catalog of every harness that accepts a standard the kind provides, `canoa accounts add` signs in through it, and the account runs those harnesses, reports its usage and lists its models through the library, with no change to Canoa. A kind or a sign-in method a bundled library (or an earlier one) already offers is not offered again, and the log says so. `examples/providers/python/gateway` is one, written in Python.
- **An account whose kind provides several standards is one account in every place.** An `account_provider` that no harness owns (a library that is no agent) now offers its kinds and sign-in methods to every harness that accepts a standard they provide, and is asked, whichever harness the account names, for its usage, models and renewal. Such an account is offered to every entry whose harness accepts one of its standards, sits in each pool of each of them and in each matching `any-<standard>` pool, and its usage is read once and kept for a minute for every pool, so a used-up bucket stops it in all of them. A kind whose settings schema marks a property `"x-provides": true` lets each account name the standards it provides. A harness is given only the credentials its standard names; what renews the account stays with the account's own provider.
- **Accounts can be pooled: a session picks an account or a pool of accounts that provide one standard.** `[host.pools.NAME]` has a `standard` (any credential standard's id) and the `accounts` it holds, each of which has to provide it; an entry names a pool among its `accounts`. The host makes an `any-<standard>` pool of every account that provides each standard, written nowhere and following the accounts. A session names a pool where it names an account and starts on the next of its accounts that lists the chosen model and has usage left, and the answer says which; a pool's models are those its accounts list, each once with the accounts that list it. `pools/list`, `pools/set` and `pools/remove` (in the app, Accounts) make, edit and remove them; `pools/turn` says which account takes the next turn: the accounts in turn at a new session and once the prompt cache has lapsed, the same account while it is warm, the next account when one has a bucket exhausted for the model or a turn was refused for a limit, and a refusal naming when the soonest allowance refills when none has usage left. A session on a single account is never moved; when it runs out the chat offers the move.
- **A session starts on an account and a model that account lists.** `initialize`'s `_meta["dev.boriken.canoa/model"]` names the model; the host asks the account's provider what it lists and refuses a model it does not, naming the account and the model. A task an agent hands to another is checked against the account it names, else the entry's first, and `delegate_targets` takes an `account` to list that account's models. The chat's model list follows the chosen account, and a model chosen on another account is taken back when the new one does not list it.
- **A speech table can name a library or a source of its own.** A `[speech.NAME]` or `[say.NAME]` table of canoa.cfg that has `library` (a Guatiao library file) or `source` (a source file, or `bundled:js` with `source_settings`) takes its `provider` from what that registry offers, as an entry of canoa.cfg does, so a speech-to-text or text-to-speech provider written in a script or a library runs without a change to Canoa. Those keys are not settings of the provider, are listed apart and are kept when its settings are saved; a table that names both, or an origin that lacks the provider, is listed with the reason.
- **The JavaScript SDK is typechecked.** `npm test` in `bindings/js/canoa-sdk` runs TypeScript over the SDK and the JavaScript examples and writes the declaration files to a folder it removes; it needs Guatiao's Node binding (`GUATIAO_NODE`), and TypeScript is a pinned dev dependency with a committed lockfile.
- **A package of scripts installs from the Extensions catalog and is the same on every platform.** An entry of an extensions catalog that says `runtime = "js"` names a folder (a manifest and JavaScript modules) instead of a library file: the Store plans it, fetches it, checks it against the folder's digest before keeping a byte, keeps it in the host's home and names it in `canoa.cfg` as a source the host carries (`source = "bundled:js"`), and checks the digest again each time the host loads it. There is no build and no per-platform file, and every host that reads the catalog ends with the same bytes, a paired host included, since each fetches and checks them itself. A package in Python is refused at the plan by a host with no Python source. [Providers written as scripts](docs/script_providers.md) says how to write, try and publish one.
- **The Python and JavaScript SDKs have base classes for profile items, catalog sources, settings sections and panel tabs**, with the ones that mirror what Canoa carries: `SettingProfileItem`, `EnvProfileItem` and `NetworkProfileItem`; `CommandCatalogSource` and `ReadCatalogSource`; `TerminalPanelTab`, `LogPanelTab` and `PagePanelTab` (a tab that opens a page at an address on this computer's loopback). Each kind's description and its models' schemas are committed and checked current, and an example library per language serves four kinds that the host lists.
- **A section's secrets are named secrets, not text in canoa.cfg.** A value an extension's Settings section marks sensitive (a token, a password) is now kept as the secret `settings/ID/MEMBER` by the secret provider `[secrets] accounts` names, which is the operating system's store unless you chose another, so it shows in the Secrets section and never rests in the file. A secret an earlier canoa.cfg holds in `[settings.ID]` is moved the first time the section is opened and taken out of the file; one that cannot be moved (the provider is locked or missing) stays and the section says why, and saving it is refused rather than dropping the secret. Tried against sealed files and a stand-in section, not the Windows credential store or Bitwarden.
- **A panel tab can stand for a page an extension serves.** A `panel_tab` provider can now say `page` and an address on this computer's loopback (`http` or `https` on `127.0.0.1`, `[::1]` or `localhost`; any other address is not offered). The + menu lists it and its tab names the page, shows the address and opens it in your browser from a button: Canoa embeds no web view, as for the Browser surface, so there is nothing for the page to reach inside the app. A page is offered only when the host runs on this computer, since a remote host's loopback is not yours. Tried against a stand-in extension's provider and a stand-in for the browser's launcher, not a real extension's server or a real browser. are named secrets, not text in canoa.cfg.** A value an extension's Settings section marks sensitive (a token, a password) is now kept as the secret `settings/ID/MEMBER` by the secret provider `[secrets] accounts` names, which is the operating system's store unless you chose another, so it shows in the Secrets section and never rests in the file. A secret an earlier canoa.cfg holds in `[settings.ID]` is moved the first time the section is opened and taken out of the file; one that cannot be moved (the provider is locked or missing) stays and the section says why, and saving it is refused rather than dropping the secret. Tried against sealed files and a stand-in section, not the Windows credential store or Bitwarden.
- **Settings' own pages are listed by the host like an extension's.** General, Appearance, Notifications, Voice, Shortcuts, Sources, Profiles, MCP servers, Permissions, Accounts, Mail, Shells, Usage, Store, Extensions and About are now `settings_section` providers the host registers the way an extension's library does (they have no form: the app draws each from its own widget, chosen by the id), and the app no longer carries a list of them. `settings/sections` answers them first, in that order, then what extensions add; a build or key that lacks what a page needs (Accounts, Mail, Shells, Extensions) still leaves it out, and About stays last. The list of these pages needs no grant (a key without `config.read` is listed only them, never the pages an extension adds), and the app keeps a copy of it that Settings shows until the host answers and when the host cannot be reached or refuses, so the person's own preferences are always there.
- **The bottom panel has one tab bar, and what a new tab can be comes from the host's providers.** A conversation's panel used to show a Terminal tab with a second row of shells under it; each shell is now a tab of the one bar (the split, rename and attach actions are in the panel's actions menu). The + menu offers Terminal (and Terminal in each shell the host lists), the host's Logs and whatever an extension adds: a new `panel_tab` kind says a tab's name, icon and what it shows, a shell (the host's own or one it names) or a log the provider keeps, which the app follows. The host lists them with `panel_tabs/list` and answers a log's latest lines with `panel_tabs/tail`; the Terminal and the host's own log are providers registered the way an extension's are. Tried against a stand-in extension's providers and shells, not an installed extension or a real host's terminal in the panel.
- **Add an agent offers the usage readers the host has.** `providers/list` also answers `usage_readers`, the `usage_reader` providers the bundled agents, and the libraries and sources of canoa.cfg, offer; the hosting dialog's Add an agent lists them under "Read its quota with" and the choice is the entry's `usage`. Without a choice the command decides, as before.
- **A usage reader can be written in Python or JavaScript.** `bindings/{python,js}/canoa-sdk` give `UsageReader` and `UsageReading` base classes (`reader`, `bucket_prefix` and the timings make the description; `open(members)` answers a reading whose `read(root, tree)` answers `reading([bucket(...)])` or `failed(why, retry)`), the kind is described by `include/canoa.usage.kinds.json` and `canoa.usage.schemas.json`, and `examples/providers/{python,js}/usage` is a reader in each language that `tests/script_providers.rs` runs through the host. An agent entry's `usage = "<id>"` now finds a reader among those the libraries and sources of canoa.cfg offer as well as the bundled agents'; an id that nothing offers is refused when `serve` starts, naming the entry, no longer when the file is read.
- **An extension can add a section to Settings, or a group under an existing one.** A new `settings_section` kind says a section's name, icon, the heading it sits under or the section it is a group in, and the form it asks for (a guatiao schema and the guatiao-intake form that shows it, drawn by the same renderer the voice settings and the profile items use). Its values are kept by the host in `[settings.ID]` of canoa.cfg, or by the provider itself. The host lists the sections it loaded with `settings/sections` and reads and writes the values with `settings/section_get` and `settings/section_set` (a secret is never answered, only that it is set); the app draws each as its own page under its heading, or as a titled group at the end of the page it names, and the search over Settings finds a group by its words. A section whose extension was removed is gone from Settings, and its values stay in canoa.cfg. Tried against a stand-in extension's providers, not an installed one.
- **A profile can have the proxy of a session carry a client certificate to the hosts you name, by pattern.** The proxy item's `client_certificate_hosts` (for `system` and `pac`) is a list of entries, each a `pattern` and the `identity` to present. A pattern is a host (`api.corp.example`), `*.name` for a name and what is under it, an address, or any other regular expression matched against the whole host (`(api|auth)[.]corp[.]example`; `.*` is every host), and the first entry that matches decides. For the hosts an entry matches, and no others, the proxy makes its own TLS to the host, verified by the operating system, and presents the entry's certificate: `system` (the default) is what your keystores or `[host.network]` choose by the authorities the server names, as a browser would, or one certificate you pick from the list the host gives (`network/client_certificates`: subject, issuer, expiry and thumbprint of what the Windows store, the macOS Keychain, a PKCS#11 token and the `[host.network]` file hold, never a key). It then answers the program's TLS with a certificate for that host made when a program first connects to it and kept until a day before it expires. The authority that signs lives in the host's memory for as long as the process runs, is written to no file and is shared by every session: one is limited (an X.509 name constraint every TLS library checks) to exactly the hosts the item names when every pattern is a plain host, `*.name` or address, and the one unlimited authority serves any pattern that is a regular expression. Sessions whose proxy items make the same settings share one proxy and its secret, which starts with the first and ends with the last (or `[host.network] proxy_idle_seconds` after it). The session's programs are told to trust the authority through `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`, `PIP_CERT`, `CARGO_HTTP_CAINFO` and `NPM_CONFIG_CAFILE` (a file in the session's private directory, with the system's roots beside it where a program replaces its roots), and nothing else is: it is added to no store of the system's, and its key is in no variable, report or file at all. Every other host stays an untouched tunnel. A program that reads none of those variables or pins its certificates fails for the matched hosts. The profile editor draws the entries as rows (add, remove, move up and down, since the first match decides) and the certificate as a pick, as a browser offers one: System (default), then each certificate the host lists by subject, issuer, expiry and source; one the host no longer lists stays chosen and is marked as not available. Tried against loopback stand-ins (an origin that insists on a client certificate, keystores holding one or two), not a real server, a real keystore or the programs themselves.
- **What a profile may set is a kind, and an extension can add to it.** A new `profile_item` kind says an item's name, the harnesses it is for and the form it asks for (a guatiao schema of the values it takes and the guatiao-intake form that shows it, drawn in the app by the renderer the voice settings use), and turns the values a profile holds for it into what a session gets: environment variables, arguments for a program the host starts, values of the session's own settings, and the network its programs use. The model, effort, mode, starting instructions and access are items Canoa carries, registered the way an extension's are; the host lists every item it loaded with `profile_items/list`, and Settings → Profiles draws a form for each (the access, which the editor had no row for, is one), so a profile keeps its values for an item at `[profiles.NAME.items.ID]`. A started session's profile report lists each item its profile holds and what it became. An item nothing offers any more (its extension was removed) keeps its values in the profile and says it is not applied.
- **Two items ship with the host as extensions: a proxy and an identity.** The identity gives a session's programs the name and address git commits under and the account label, and any other variable you write. The proxy chooses how its programs reach the network: `system` (the default) runs a proxy on the loopback address for that session alone, which sends each connection as the host's own network does (the system's proxy chosen per destination by PAC or WPAD, logged in to with Basic, Negotiate or NTLM, with a bypass list), so a program that knows only a plain proxy behaves as the system does, and the program must present a secret of the session; `none` gives its programs no proxy; `proxy` gives them one you name; `pac` chooses by a PAC script; and `command` starts a program of your own that listens and is handed to them. It adds no client certificate unless you name the hosts (below).
- **The credentials of your accounts and your mail passwords are secrets like any other.** They are kept as named secrets (`accounts/…`) by the provider `[secrets] accounts` names: the system store by default, sealed files (the new `file` provider) when there is none, or any setup of yours that keeps what it is given. The Secrets section lists them. What an earlier Canoa kept in the operating system's store under its own name, or in sealed files, is moved into the new place the first time each account is used, and the old copy is removed only once the new one reads back the same.
- **Secrets come from providers, and what you give once is kept as you say.** An agent that asks for a password or a key by name is answered without asking you when Canoa already holds it. Where a secret comes from is a new kind of provider, `secret_provider`: the form you type in, the operating system's credential store (Windows' Credential Manager, the Secret Service, the Keychain) and any an extension adds. The form offers how long to keep what you type (this once, this session, until Canoa closes, 15 minutes, an hour, 8 hours, a day) or to remember it in the system store, and a value that comes with its own end (a token that expires) is kept no longer than that. `[secrets]` in canoa.cfg chooses which provider answers which name.
- **Secrets is a section of the app.** It lists what the host holds for your agents: the provider, the name, the value hidden until you ask to see it, and how long it is kept (this conversation, until Canoa closes, the time left, or stored), with Forget and Set a secret, whose value you type into a form only your app and the host can read. It shows when the host grants `secrets`, which this app has.
- **A secret provider is set up in a form, and a secret setting comes from another provider.** Secrets, Set up a provider (and the Store, once `bw` is installed) draws a provider's settings from the schema and form the host describes; a setting the provider marks as taken from a secret (Bitwarden's session key) is a choice of the provider that gives it and the secret's name there, saved as a reference.
- **Secret providers are in the Store.** Store, Secret providers lists Bitwarden's command line, installs it when you have none (the release for your system, checked against the digest GitHub lists for it) and keeps it where only Canoa's secret providers run it. `secrets/configure` sets up a provider and takes a secret setting from another provider (the form, the system store) without ever writing it to canoa.cfg.
- **An agent's question for a secret no longer holds its session.** The agent can say how long it can wait (up to `[secrets] max_wait`, 240 seconds), a question nobody answered in time is taken off your screen and the agent is told it timed out, and an agent whose person has gone is told at once that no one is present.
- **Bitwarden is a secret provider that ships in Canoa, written in JavaScript.** It reads an item of your vault by name through Bitwarden's `bw` command with a session key you give once or take from another provider (such as the form), and needs nothing built: Canoa carries the engine that runs scripts like it (QuickJS), and `source = "bundled:js"` lets an extension of yours be one. A provider runs programs only through the spawner Canoa hands it, and Bitwarden is written with the SDK's `SecretProvider`. A library that adds no Store type can now be named as an extension for its other kinds.

### Changed
- **The host builds on coqui-acp's reviewed API: a harness says which account provider is its own, the cache lifetimes are named by Canoa, and the mode menu shows an agent's own words.** The account provider of a harness, and the settings of the harness it shares with it (the program, a Node and a script), are read from what the harness declares, so one whose account provider's id does not follow `<harness>_accounts` is found. `canoa options` and the app name the prompt-cache lifetimes the provider honours in Canoa's own words (Off, 5 minutes, 1 hour) rather than the provider's, and the mode menu shows an agent's own description of a mode when it gives one (Canoa's one line stays for an agent that gives none). A LiteLLM key's budget and limits are made into buckets by `coqui_acp_api::key_usage`, so they carry its labels (`Gateway budget`, `Gateway requests per minute`, `Gateway tokens per minute`) and source (`gateway`), and a key with no budget reports its spend with an unknown status rather than ok.
- **Limits on the person's own data and runs are settings, or pages, with today's values as defaults and no ceiling of the code's own.** `fs/list` takes `offset` and `limit` and answers `next`, with the page cut from the sorted whole (a folder past 1000 entries was cut before sorting); `fs/read` takes `offset` and answers `next` (a 512 KiB page is what one message carries, not a limit on the file), and the app puts an image together from its pages (a 2 MB photo had no preview). New settings: `[host.worktrees]` `max_per_repository` (32) and `git_seconds` (120), `[host.delegate]` `wait_seconds` (300) and `dial_seconds` (20), and a Foundry Local account's `answer_seconds` (1800). `[host.history] max_session_bytes` and a mail account's `timeout_secs` lose their ceilings, and `seconds` of `network/fetch` and `network/tunnel` has none. A secret provider's names are listed whole and a name or a value has no length limit of Canoa's (the three SDKs lose `MAX_NAME`, `MAX_VALUE` and `MAX_NAMES`).
- **The Store refuses a platform only when the publisher's release does.** The engine no longer checks `ProgramInfo::platforms` (what a store was measured on); the recipe's `release` says what its publisher has no build for, and Codex and Node name their macOS builds.
- **Any http or https address you type is accepted; plain http beyond this computer is told of, never refused.** An account's address (the API-gateway and LiteLLM kinds, and every kind's endpoint setting), a mail account's `server` and `autodiscover`, the skills directory and an MCP registry, and the address of an MCP server a paired client hands a session, took only `https` or `http` to this computer, each with its own hand-written parser. One `canoa::address` check (`url::Url`) now serves them all. A host that loads no Claude has no Claude account type, mark, name or source anywhere, and an agent a library adds appears the same way as one Canoa carries. `looks/list` serves the looks of the loaded agents. A Pi offer now keeps the profile and the reach of a built-in source, as Claude's and Codex's do.

### Fixed
- **Exchange autodiscovery sends the account's credential only to the account's own server or its address's domain.** A redirect or an EWS address in an Autodiscover answer is followed only when it is on the mailbox address's domain (or a name beneath it) or on the Autodiscover address the account names, and only over `https` (`http` is accepted for this computer); a reply naming any other server is refused, and the error says which server and to name the EWS address in the account's `server`. An account that names its `server` is not affected.
- **The app no longer holds a name to a rule of its own.** Add account, a mailbox and Hosting's Add an agent refused a name that did not match a pattern the app kept beside the host's, which after the host began to take any text for an account's name refused names the host accepts. They now ask only for a name and show the host's own refusal when it refuses one. The default catalog, the skills directory, the official MCP registry, the kinds of client and the `[host.kb]` keys the app keeps beside the host's are held equal to the host's by a test.
- **Saving a setting no longer drops the comments of a canoa.cfg in TOML, and the host has one editor and one writer for it.** `config/set` rewrote the whole file through a TOML serializer, so every comment, blank line and the order of the person's tables went on any change in Settings. A TOML file is now edited in place with `toml_edit`, by `config/set`, `canoa accounts add|remove`, an entry's offers, `pools/set` and `canoa mail add|remove` alike: the one table changes and every other byte stays, and a header with a comment or spaces after it is found, so the table is no longer added a second time (which the host then refused) or moved to the end of the file. Names are written quoted where a bare key could not hold them, so an account or a pool may be called any text with no control character, not only ASCII letters, digits, `-` and `_`. YAML and JSON, which have no layout of their own, are still written whole. canoa.cfg and the overlay records are written by one function that makes the file beside it, syncs it and puts it in place, keeping the mode (Unix) or the access list (Windows) the file had and writing through a link: `canoa accounts add` used to replace a link with a file, and on Windows a rewrite copied over the file in place, so a stop in the middle lost the old text (it now uses `ReplaceFileW`). A NUL byte in a source file of the host, which made `grep` call it binary, is gone.
- **The app reads a canoa.cfg that holds tables it does not own, and says when it cannot read the file.** A `[secrets]`, `[settings.ID]` or `[say.NAME]` table (or an extension's own) made the app refuse the whole file and run on defaults without a word, and the next save wrote the defaults over it. Every other table is now kept as read and written back as found, in TOML, YAML and JSON; a file that still cannot be read is shown, the app runs on its defaults, and nothing is written over it until it can be read. `network.connect_timeout` (any number of seconds above 0, typed in Settings with the old choices as suggestions) and `voice.output_speed` (any number above 0) no longer have ranges the host never had, and `[assets] cdn`, which nothing read, is gone. A served page now reads and saves `[voice]`, so dictation mode, language and read-replies survive a reload.
- **On Unix an agent started through `canoa launch` is a child of the process that started `launch`, not of `launch`.** `canoa launch` now becomes the program with `exec` once it has read its first line, so the agent keeps that process's id and parent: an application that started the host's programs through its own process starter still has the starter, and not a `launch` between, as the agent's parent, and a signal that ends the agent is seen as such. Windows still runs the program as a child of `launch`.
- **Usage lists the login each harness has where it runs.** The automatic account `local` of Claude, Codex, Pi and any other harness that offers its own login was in no list, so the Usage page never showed it and `usage/read` refused it. `accounts/list` (and `canoa accounts list`) now lists it after canoa.cfg's accounts as an `automatic` row of the kind `harness-login`, with an `id` of `local:<harness>` that usage is recorded and reported under, so one harness's `local` is told apart from another's (before, both were `local` in the usage log and the last allowances heard overwrote each other's); `usage/read` takes the `harness` for `local` and asks that harness's account provider, and the row carries the tokens the host recorded for it. The app shows each under its harness as "This machine's login", and Settings, pools and the session picker still list only canoa.cfg's accounts. Spend recorded earlier under `local` stays under that name.
- **An agent entry with no profile is told who its session is too.** Its program, and the shell tool of Claude Code or Codex under it, now find `AGENTS_HOST`, `AGENTS_HARNESS`, `AGENT`, `AGENTS_VENDOR` and the account's variables in their environment, as an entry with a profile does; before, only a profile's connection carried them, so a `[host.agents.NAME]` entry with neither `profiles` nor `own_profile` started its agent with none. Overlays, and so `<NAME>_OVERLAY_ROOT` and what an overlay declares, still come only with a profile.
- **A terminal takes what is typed once it is in front, and a hidden one no longer does.** A shell opened from the panel's + menu, a tab chosen again, a split, the Terminal section and a panel shown again all left the keyboard where it was, so a second tab's typing went to the first (hidden) shell, or to the message box, until the screen was clicked, and a panel hidden while a shell had the keyboard kept it, so the message box heard nothing. The shell the person chose, or brings in front, takes the keyboard, and a section, a panel or a tab that is out of sight cannot have it.
- **Dictation on Windows starts again in the built app.** The Windows speech plugin set a channel handler when it registered, which the generated registrant does before the app's `main` has created Flutter's bindings, so the registration failed without a word and the app's dictation fell back to a channel no plugin answers: it said "The speech service could not start: MissingPluginException." The plugin sets its handler when dictation starts, in the main window and in a second window alike, and the message for a call that fails names what failed in words, not the exception's type.
- **A command speech provider no longer holds up the host while it reads a long answer.** The script engine runs one call at a time, and the SDK decoded a program's output a byte at a time in script, which took seconds for the 4 MiB it keeps and made every other speech call wait behind it (a stop or a cancel of another recording included). The engine's `TextDecoder` now decodes in native code (4 MiB of UTF-8, non-ASCII included, took about 8 s and takes under 0.1 s), and a recording that waits for its program to end lets the host's other calls through between looks, so a cancel of it (the person pressing Cancel while it says Transcribing) is answered at once and ends the program instead of waiting for it, up to the two minutes the command may take, as does any other recording or catalog refresh meanwhile. Measured on Windows against a stand-in program, not a real recognizer.
- **The app's own host runs a Foundry Local account's SDK engine.** The command the host starts for the engine was not among the ones the app's child entry accepts, so `--canoa-child` refused it; the helper command is.
- **A program that ends the moment it starts no longer fails to start on Windows.** The system refuses to put a process that has already ended in a job object ("access denied"), and a provider, a tool or a program the Store ran sometimes met it under load as `Failed to assign job`. Such a process is now nothing to contain and starts as usual, its status readable; any other refusal says what the system said.
- **A link the host ends as the app lets it go is no longer an error nobody catches.** When the host ended (a restart, say) as the app closed its link, the link's own end was handed to the closing as an error, and where the close was not awaited it surfaced as an uncaught `Bad state: Transport disconnected`. The end of the connection is now told only to a reader that is still listening.
- **Dictation on Windows delivers what you said.** The plugin behind the system speech service asked the recognizer for no hypotheses, so nothing showed while you spoke; dropped the phrase the recognizer still held when you pressed Stop, so a sentence stopped before its pause came back as nothing; and lost every phrase after the first, since each came up as a final result and the first final ends a listen. The app now carries a copy of that plugin (pp/third_party/speech_to_text_windows) that shows the words as they are recognized, finishes the phrase in the recognizer when you stop and returns all of the session's phrases as one text, lists the languages of the recognizers installed instead of two fixed English ones and starts the one you chose, and reports a missing recognizer, a language none understands or a microphone that will not open as the reason in the composer. Tried against the installed recognizer with recorded speech played in place of the microphone (the plugin in a Windows ARM64 app, its native part on ARM64 and x64), never with a microphone.
- **Dictation no longer waits for ever, and every way it can fail says why in the composer.** On Windows the operating system's speech service ended only the first dictation: from the second on its stream never closed, so the composer stayed on "Transcribing". Now each service's end is routed to the dictation that is running, a service that does not say it has finished within ten seconds of Stop is ended with that as the reason, and a press shows "Starting" at once with Cancel. A speech provider that does not answer Stop within four minutes, a host that does not open or take a recording within thirty seconds, or one that cannot list its providers within twenty, ends the dictation naming what did not answer, and Cancel is there while a service finishes. A dictation that ends with no words says nothing was heard instead of looking as if nothing happened.
- **A session's proxy, PAC and command modes keep the roots and the client certificate `[host.network]` names**, which they had lost: the network a session's own requests use starts from the person's settings and changes only the proxy, its login and its bypass list, and never takes the host's own proxy login to another proxy.
- **A session whose proxy item is `none` reaches the network with no proxy.** The programs the host starts for it were given the system's proxy anyway, since the item left their environment without a proxy variable and the host adds the system's to a program that has none. They are now given `NO_PROXY=*`, which says no proxy and which the host's own starter takes for it. The knowledge tools' requests for a session (the query's embedding and the model that orders passages) go through the network its profile chose; a SOCKS proxy a PAC script names is carried by a session's proxy as an HTTP proxy is, and is now tested against a SOCKS5 stand-in.
- **The app asks for the profile items again when the extensions the host has loaded change**, so an item an extension adds or takes away shows after the host restarts for it without reloading the app.
- **A sign-in rule for browsers decides on its own in the portal.** The portal serves a page and nothing else, so it says its client is a browser as a fact it established, not a claim; the sign-in rules (coqui-access `a7aa391`) hold a client kind they were not told is verified to the rules with no client as well, and without that a rule with `clients = ["browser"]` could only add steps.
- **A Foundry Local model stops working for a client that went away.** A Claude Code killed at its timeout left the model busy for twenty minutes and Foundry Local holding the session, so nothing behind it could run. The gateway now watches each request's connection and, when the client hangs up, ends the call: with the service engine it closes the connection to the service, with the SDK engine it cancels the native request, and a request waiting its turn is dropped. Through a proxy the host's network puts in front of the service the call is abandoned but the service cannot be told.
- **A tool call the token limit cut is a stop for length, not an error.** Foundry Local answers HTTP 500 (`Tool-call output was interrupted`) when an answer runs out of tokens while the model writes a tool call; the gateway now answers `max_tokens` (Messages), `length` (chat completions) or `incomplete` (Responses), with the half call dropped and a line saying so, which the agent already knows how to meet.
- **A Foundry Local model run by the SDK engine runs in a process of its own.** The native library crashed the host's own process on some prompts (a segmentation fault on about two thousand tokens). The host now starts `canoa foundry-engine` for the account; a crash there fails the request under way with how the process ended and the next request starts it again.
- **The SDK engine no longer writes Foundry Local's models folder.** The SDK keeps the models registered with it in a catalog file inside the models folder it is given, which was Foundry Local's own; it is now given `foundry-models/` in the host's home, with the model linked into it. A home on another drive than Foundry Local's cache falls back to Foundry Local's folder, changes its catalog file while the model runs and puts it back, and the log says so.
- **A Foundry Local account that runs its model with `engine = "sdk"` finds the model Foundry Local downloaded and loads it.** The SDK looked in a models folder of its own, so every model was "not found"; it now reads Foundry Local's own folder (`SdkConfig::cache` names another), registers the execution provider the model runs on, loads the model when the gateway starts and unloads it, and takes a window copy it registered out of Foundry Local's catalog file, when the gateway goes. The process no longer ends in the SDK's teardown when the engine is released.
- **Codex no longer gives up on a Foundry Local model that takes minutes to read its prompt, and a turn that fails says why.** Codex waits five minutes for an event and does not count the gateway's `: keep-alive` comment lines as one; a stream of Responses now repeats `response.in_progress` while the model works. A failure in the middle of the stream ends it as `response.failed` with the reason, where it was an `error` event Codex ignored.
- **A proxy variable you left empty no longer stops the host's proxy from reaching a program.** On Linux and macOS, where `https_proxy` and `HTTPS_PROXY` are two variables, an empty lower-case one that a program reads first meant "no proxy", so a program the host started went direct although the host had added its own `HTTPS_PROXY`; the empty one is now taken out of that program's environment when the host adds the proxy. A microphone that is refused or cannot start is reported in words. Linux needs `parecord` (PulseAudio or PipeWire's Pulse tools) installed.
- **A microphone in the composer.** Press it, or Ctrl+Shift+Space (Command on a Mac), to dictate: the first use with a service says where the audio goes, the microphone opens only until you stop it, and the text lands in the message at the cursor for you to edit. Nothing is sent for you, attachments stay as they are, Cancel puts nothing in, and a refused microphone, a provider error or a host that went away ends the dictation and says why.
- **A dictation carries what its speech service noted, and your voice profile reaches the service.** When a service answers front matter with the text (language detected, confidence, what it heard of the voice, anything it wants the next model to know), the message gets it as a small attachment, `dictation.md`, whose front matter the agent reads as one more block of the prompt: a block and not `_meta`, because an agent hands a prompt's blocks to its model and ignores the prompt's `_meta`. You see it among the message's attachments and can take it off before sending; a second dictation in the message adds `dictation-2.md`, and an agent that takes no embedded files gets none and the dictation says why. Settings, Voice has a Your voice group (voice, accent, words and names; `[voice] voice`, `accent` and `vocabulary` in canoa.cfg) that goes to the provider at the start of each dictation with the language, and is only what you write.
- **A host with no credential store keeps accounts in sealed files by itself.** `[host] account_store` is now `auto` by default: the operating system's store when it answers, else a file per account sealed to a key in the host's directory, as a Linux service with no session bus needs. The host logs the reason as a non-default note and `canoa accounts list` prints it; once files hold an account `auto` stays on files; `os` insists on the operating system's store and its error names `auto` and `file`.
- **Models and efforts are listed when an agent is chosen, before any session starts.** `canoa options NAME --entry` on an entry that runs a program speaking ACP asks the program through a short session with no prompt: it starts as a session would, opens one session in a temporary directory, reads the model and effort options, closes the session (`session/close`, where the program offers it) and ends the process, within `--wait` seconds (20 by default). The answer is kept for the process by the entry and the program's version. A program whose session lists none says so; one that cannot be started or answers wrongly is `failed` with the reason, and one that is not there is `not_installed`. `--account NAME` asks as one of the entry's accounts, so a signed-in account lists what it may use; the app asks as the account a new session would start on and again when the person chooses another, and says "Listing models…" while it waits. A Claude Code that lists no model reports signed out or failed, never a list that comes after start.
- **The Store as stores.** Its index lists each store (catalog) with what it offers; choosing one opens it as a banner (its name, description and featured items, then one per popular tag) over tiles with an icon, name, summary, publisher and a + that installs from the tile, with search and tags scoped to it. The choice is kept across runs. The index toggle leaves the section rail: the layout control at the header's right is the only one, with Ctrl+B.

An entry's page lists its skills with their descriptions, rules, context, knowledge, hooks, environment scripts, MCP servers, `bin` commands and requirements without a fetch. Nothing is installed or run by reading.
- **Prompt cache: Off, and only what the agent honours.** `cache_lifetime = "off"` (and `canoa agent claude --cache-lifetime off`) turns Claude Code's prompt cache off by setting `DISABLE_PROMPT_CACHING`. `canoa options` prints `cache_choices`, the lifetimes the provider honours under its own names (Claude Code: Off, 5 minutes, 1 hour; Codex: none), and the new-session view offers those and "Agent default" and nothing else: a saved choice the agent does not honour shows as unavailable and the agent's default is asked. The host sends Off only to a provider that lists it.

- **Agents can search the knowledge an overlay ships.** A client that sets `_meta["dev.boriken.canoa/kb"]` in `initialize` gives its sessions an MCP server, `canoa-kb`, with `kb_search` (passages ranked by score, each with its file, heading and line range, never an answer), `kb_read` (lines of one file) and `kb_list`, over the overlays the session's loadout gave it, and a built-in skill that says when to use them. The app has a Searchable choice on each installed overlay and the endpoints under Hosts, and reads a canoa.cfg whose overlay has `kb` (it refused one before).

### Changed
- **`share_env` is gone.** An overlay's text reads any variable of this computer, by `${NAME}` or by a `from_env` or `env` provider reference, and the overlay's report lists each such read as `env-passthrough`. A profile that names `share_env` is refused. The report no longer has `ungranted` or `unresolved`, and a variable that is not set fails the session's start by name.
- **A header an overlay's MCP server reads from a variable is sent over plain `http` too.** The report lists the server as `insecure-transport`, as dotagents does, and no longer drops the header.
- **A Store program's launch may set any variable.** The host records its launch after checking only that the files it names lie inside the version's folder.
- **No variable is refused from a layer you chose.** An overlay, a project, an MCP server or a `pre-env` hook may set `PATH`, `NODE_OPTIONS`, `LD_PRELOAD`, `HTTPS_PROXY`, a harness's home or an endpoint, and it applies; the list of such names is gone. Only the names the AOS specification reserves for the host (`AOS_*`, `*_OVERLAY_ROOT`, `*_OVERLAY_STATE`) are refused. A variable that changes how programs find code, trust certificates or reach the network is listed in the overlay's report as `env-sensitive`.
- **Every session carries `AGENTS_HOST`, `AGENTS_HARNESS`, `AGENT`, `AGENTS_VENDOR`, `AGENTS_MODEL`, `AGENTS_EFFORT`, `AGENTS_HARNESS_VERSION`, `AGENTS_ACCOUNT`, `AGENTS_ACCOUNT_KIND`, `AGENTS_ACCOUNT_PROVIDER`, `AGENTS_PROFILE`, `AGENTS_LOADOUT` and `AGENTS_ROLE`,** each only when it has a value, and a `pre-env` or other hook also `AGENTS_PROJECT_ROOT` and `AGENTS_SESSION_ID`. Every layer's `${...}` reads them before it applies, so one overlay can adapt to each harness; the names, ids and vendors are dotagents'.
- **The browser extension lives in `clients/browser/chromium/`, not `bindings/`.** It is a client of the host, not a binding for a library. Load the extension from the new folder; `python app/tool/build.py chromium` packs into it.
- **An overlay's own `bin/` and `lib/` are on the agent's `PATH`, `PYTHONPATH` and `NODE_PATH`.** They go first, ahead of the host's own entries, for every agent, as the specification's defaults and `paths` say, and a `paths` entry that leaves the overlay's folder is refused. The agent itself is still looked up on the host's own `PATH` (for an agent started by `canoa launch`, and on Unix for one run in the host). Each line of a profile's report that is not applied names its overlay, once per item, so two overlays missing the same thing are two lines.
- **The app's transport package is `coqui_transport_web`.** `coqui_web` is deprecated and replaced by `coqui-transport-web`'s Dart package at `1e0c145`, which also stops its early-message handoff from buffering a transport end's close as an error when no application listener is attached yet. The imports are renamed; nothing else in the app changes.
- **A one-time code is replaced only by someone who showed it.** The portal asks the code provider for a new setup of an account that has a code only when the person showed a code or a recovery code for it in the setup's own steps; a rule for `enrol` that asks for a password alone no longer replaces a code, and `canoa portal factor enrol NAME` refuses an account that has one (`reset` it first). A first setup is unchanged. Takes coqui-access 365b02e.
- **The chat's own held choices go the way a draft's do.** The choices a conversation holds (a profile's values, remembered defaults, changes made during a turn) are sent with the mode and the model together, and the effort and the other options once the model has answered; the pin of `coqui_acp` moves for it.
- **A git source on a network share is allowed.** `overlay/check`, `catalog/fetch`, `skill/fetch` and `store/read_ahead` no longer refuse a `\\host\share` or `//host/share` source by its text: the person running the host names one as the file explorer opens it, and a paired key reaches a place on this computer only under a working root with the `folders` grant, as before.
- **Sign-in, renewal, watching and plan limits are an account provider's.** The host registers `claude_accounts`, `codex_accounts` and `pi_accounts` beside the harness providers, and an outside library's `<harness>_accounts` (`stdio_accounts`, settings `harness = "grok"`) is built from the same file as its harness. `accounts/catalog`, `canoa accounts add` and an entry's offered accounts take the kinds, the sign-in methods and whether a kind renews from the account provider's `offers()`, so only a kind it offers is accepted: Pi offers `pi-oauth` only, Antigravity none. A sign-in runs through its `login`; a rotating login is watched through its `watch` while a connection or a models call runs on the account (begun once the harness has placed the login), and its renewals and losses are stored as before (the harness is handed no account keeper: it neither signs in nor renews, and the `acp_harness` kind has no `login` or `renew`); `usage/read` goes through its `usage` and an expired login is renewed through its `renew`, with the stored login file written into the account's directory first, since the account provider looks at the directory and never fills it. `renew_poll_ms` and `command_timeout_ms` are no longer harness settings (Codex's harness keeps `command_timeout_ms`): a harness entry's `account_settings` configures its account provider, whose `executable` follows the entry's unless it says another.
- **The app opens on a new session, which exists only once it is sent.** A launch, closing the last session or New session shows the page of choices (agent, account, model, workspace, composer) with no row in the side list and nothing started; Send makes the session, its row appears and the page becomes the conversation. One such page waits at a time. With no agent installed the page says so and links to the Store, which is where an agent is installed; it no longer lists Install buttons.
- **An account is offered to the agent itself, never to an entry of its own.** Signing in to an account no longer makes a "Claude accounts" entry beside Claude: the account is added to Claude's (or Codex's) own entry. A canoa.cfg that already holds such an entry, as the application made it (`<provider>-accounts` titled "<Provider> accounts", `peers = []`, no other key), has its accounts folded into the agent's own entry once, when the host starts or first reads accounts, and the entry is taken out; an entry of the person's with that name and any other setting is left as it is.
- **One crate per agent.** `canoa-claude`, `canoa-codex`, `canoa-grok`, `canoa-pi` and `canoa-antigravity` each carry what Canoa knows of one agent: its source preset, its Store recipe (moved out of `canoa-host`, with the recipe contract and its helpers now in `canoa::store::recipe`, and `canoa::preset::SourcePreset`) and, for Claude, Codex and Pi, the coqui-acp provider re-exported. Nothing the host does changed: provider and Store ids, URLs, digests, preset names and search places are as they were.
- **A program install asks its form the way a sign-in does.** The question an install puts to the person (a login or token its installer needs) now comes as the sealed `_coqui_acp/secret_request` of `accounts/add`, bound by the same asker, in place of `store/ask`, so a typed secret crosses the control channel only sealed to a key made for that question, for the application's own link and for a paired key alike. Plain fields stay plain. A grant that lasts until the tab closes is seen only by its own tab. A page's `session/cancel` closes the window asking about that session's permission request and answers the agent `cancelled`. Asking again for an agent already granted ends the connections on the old grant, and the old grant is never written back. A request window closes when its page goes, and nothing is granted to a page that has gone. A link the agent did not end in order closes as `failed`, not `agent`.
- **The secret tools' server refuses a connection another user owns on Linux.** Delegation's and the Store's servers already did; the secrets server answered any local user who held a bearer, such as one read from an agent's command line. The three now share one server.
- **The web app starts with no service worker, and draws every glyph.** A browser that had visited an earlier build kept its service worker, and Flutter's loader registered the build's own and waited up to 4 seconds for it ("prepareServiceWorker took more than 4000ms") before starting the app. The app now registers none, drops one an earlier build left, and its build no longer publishes `flutter_service_worker.js`. The fallback fonts the engine asks for when Roboto lacks a glyph (symbols, arrows, emoji, CJK, every script) were looked for beside the page and never put there, so each fetch failed; `build.py` now copies all 724 of them (20.7 MiB), pinned by SHA-256 in `tools/fallback_fonts.sha256`, from the deps branch's mirror, which `tools/mirror_deps.py` fills. The build reaches no network and stops when one is missing or changed.
- `host/restart` ends the host as soon as the answer is sent, from the connection that sent it, instead of from a thread that slept 300 ms.
- `catalog/fetch` refuses a network share as a source, as `overlay/check` does, before git is started; `overlay/check` tests it once.
- `cargo clippy` is clean on Rust 1.89, the minimum version (`Scope::allows_path`).
- **On Linux and macOS the host inside the app reads how its children ended** while the app has a process of its own running (a session, the store's git, a notifier): the app's process handling collects any child of its process that ends, and a worktree request's `git` failed as if it had run too long. The host starts its agents, providers, tools and `git` from a process starter of its own (`canoa spawner`, hidden), which keeps each uncollected until the host collects it, so an agent's stop signals only its own live group. Overlay hooks and the processes `coqui-acp-harness` starts (sign-ins, installers, a harness's model list) go through it too, and a hook whose status cannot be read refuses instead of running to its timeout and passing. The commands `coqui-acp-secrets` runs go through it too, every child it holds ends with the application however it ends, one stalled spawn no longer strands the others, and a process that left its group by `setsid` ends with it on Linux. Nothing changes on Windows. `coqui-acp` is pinned to the commit with `Agent::spawn_with`.
- A folder on a Windows share (`\\server\share\app`) is an ordinary working directory. The host writes `\\?\UNC\` and `\\?\C:\` paths plain before it compares them with the working roots and before an agent is given them, a `..` or `.` segment is still refused, and a device path (`\\.\pipe\x`) is refused with or without roots. A `[host.tools]` entry no longer refuses a share as a session's directory, and one started through an npm `.cmd` file runs its program in that folder (cmd.exe takes no share as a working directory); a batch file of any other kind is refused there with its reason. Worktrees are made on a share a working root names. A share written with forward slashes (`//server/share/app`, as git writes one) is read as the same share. The app starts a session in a folder on a share, and Add an agent takes one as the agent's working root. Claude Code and Codex entries take a folder on a share, a `.cmd` command of theirs runs in it, and a Codex thread recorded there is resumed under a root that holds it: coqui-acp moves to a revision where a session's folder is no longer held to its network-path rule (that rule still holds an MCP server's command and a plugin), its Dart client takes a share as absolute, and `coqui_acp_api::batch::start_in` starts the program an npm `.cmd` file names, which the tool runner now calls too.
