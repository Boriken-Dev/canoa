# `canoa-host` profiles, hooks, and overlays

## Profiles (`canoa_host::profile`)

The schema of a profile, what an agent is launched with, and its merge in layers. The app reads the same schema; `tests/vectors/profile.json` holds both to the same views and refusals. `serve` applies a `[host.profiles]` profile to an agent entry that offers it (see Serving).

```rust
pub const PROFILE_META: &str = "dev.boriken.canoa/profile";
/// `initialize`'s `_meta` key naming, as a list of names, the overlays this connection starts with: only a narrowing of what the profile lists.
pub const OVERLAYS_META: &str = "dev.boriken.canoa/overlays";
/// `initialize`'s `_meta` key naming, as a loadout's name, the `[loadouts]` entry this connection starts with.
pub const LOADOUT_META: &str = "dev.boriken.canoa/loadout";
/// `initialize`'s `_meta` key naming, as text, the kind of client (`browser`, `outlook`, `word`, `excel`, `powerpoint`): a connection that names no loadout, and whose preset names none, starts with `[defaults.clients]`'s loadout for that kind, else `[defaults] loadout`. A kind the file gives nothing is only a label; anything but text is refused. The profile report carries the `loadout` the connection got.
pub const CLIENT_META: &str = "dev.boriken.canoa/client";
pub fn launch(program: &OsStr, args: &[OsString], max: usize) -> io::Error
```

`launch` reads one line of at most `max` bytes, `{"canoa_host_launch": 1, "env": [[NAME, VALUE], ...], "args": [ARG, ...]}` (`args` optional: arguments for the program after those of `launch`'s own command line, which carry the access for Antigravity), runs `program` with those variables added, passes the rest of standard input to it, and on Unix becomes the program (`exec`: the program keeps the process's id and parent, so its parent is the process that started `launch`, and its status is the one that parent sees); on Windows it runs the program as a child, relays the rest of standard input and exits with its status (1 for none); it returns only an error: `InvalidData` for a line of another form, or why the program did not start. It is `canoa launch`.

`DEFAULT_PRESET` (`"default"`) is `[profiles.default]`: always there (`HostProfile::default_preset` is an empty `Preset` when the file has none, `resolve_preset("default")` never fails, and a `config/set` of `profiles` without `default` is refused), and the preset a session that names none starts with. `Preset::items` holds what a profile keeps for each `profile_item` (`[profiles.NAME.items.ID]`, values by field name); `Preset::item_values` is everything the profile holds by item id, the session's own settings (`model`, `effort`, `mode`, `context`, `access`) included, and `Preset::session_layer` the layer the built-in items make of those. `ItemSet` is the items a host offers (the built-in and bundled providers and those its entries' and extensions' libraries add, opened when `serve` binds); a started session applies each item its profile holds through it and reports `items.ID` with what it became. The proxy a `system` or `pac` network runs for a session (`network::session`) listens on loopback only, answers only a request that carries the session's secret as the proxy password, and ends with the connection.

```toml
model = "m"                      # effort, mode likewise: text, not empty, no control character
context = { text = "..." }       # or { file = "CONTEXT.md" }: exactly one
unset = ["model"]                # model, effort, mode or context of a lower layer; not beside that key
[env.NAME]                       # NAME: a letter or _, then letters, digits or _, up to 128
value = "v"                      # exactly one of value, from_env (a variable's name), from_file (a path), remove = true
[skills.NAME]                    # NAME, and mcp's and headers': 1 to 64 letters, digits, - or _
path = "skills/review"           # or remove = true
[mcp.NAME]
type = "stdio"                   # stdio: command, args, [mcp.NAME.env.X]; http or sse: url (http:// or https://), [mcp.NAME.headers.X]
command = "npx"                  # or remove = true alone
```

- **Merge**: lowest first. A scalar a later layer sets replaces the lower one; `unset` takes it away first. A named entry a later layer sets replaces the lower one whole and keeps its place; `Change::Remove` takes it out, and set again later it comes last. `removed` lists only what was there to remove, in order.
- **Layers from elsewhere** (`is_confined`: overlay, project) read any variable of this computer, as the person's own do. A confined layer that sets a variable the AOS specification reserves for the host (`coqui_aos::is_reserved_variable`: `AOS_*`, `*_OVERLAY_ROOT`, `*_OVERLAY_STATE`), in `env` or a stdio server's `env`, is refused at parse time (`Rule::Reserved`, key `env.NAME` or `mcp.NAME.env.NAME`); no other variable is refused, and removing one is allowed. There is no `share_env`: a profile that names it is a parse error.
- **The view** has `model`, `effort`, `mode`, `context` when set, and always `env`, `skills`, `mcp`, and `removed`.
- **Paths** are judged on the text, the same on every platform. In a confined layer (overlay, project) a path is relative and stays below its directory: no leading `/`, `\` or `~`, no `:`, no `..` segment. Elsewhere any non-empty path without NUL.
- **Errors** never quote a value: `Invalid.key` names the setting (`env.A`, `mcp.a.headers.T`), or for a refused name the table holding it (`env`, `mcp.a.env`). The first refusal in a document is, in order: anything serde refuses (an unknown key, a wrong type, a key twice) as `Parse`; then `model`, `effort`, `mode`, `context`, `unset`, then `env`, `skills` and `mcp` entries in the document's order.
- **`resolve`** reads `FromEnv` through `lookup` and `FromFile` from `dir` (an absolute path only outside a confined layer), less one final `\n` or `\r\n`. The path is canonicalized and that path is what is read; for a confined layer it must be under `dir` canonicalized, so a link out of the project is refused. It must be a regular file of at most `MAX_SECRET_FILE` bytes, UTF-8. Call it only when a session starts.
- **`parse_git`** reads an AOS source string (`coqui_aos::Source::parse`): the path follows the first `#`, without leading or trailing `/`, and must be an AOS relative path; the ref follows the last `@` when it holds no `/`, `:` or `\`. Refused besides what AOS refuses: a source that is not Git, or names no ref; a repository holding a space or control character, or a scheme other than `https`, `http`, `ssh`, `git`, `file` in lowercase; `file://` with a host, or a path opening with `\\` or `//` (another host's share); `http://` or `git://` at a ref that is not a `full_commit_id`, since nothing else checks what a plaintext transport carries; a ref `git check-ref-format` refuses, or one opening with `-`. `Dir` is never parsed here.
- **`overlay_layer`** makes the layer of an AOS overlay from its tree, whose digest it computes: the root variable `<NAME>_OVERLAY_ROOT` (a `Value`), then each env file's and `env`'s variables as written, then path additions per variable (the overlay's own `bin/` on `PATH`, `lib/python/` on `PYTHONPATH` and `lib/node/` on `NODE_PATH` come first, as the specification's defaults say; each is read over the host's own value of the variable, which `build_each` names so a default addition never starts from empty), merged as any layer's; bundled skills `skills/<name>` (a skill the overlay names by source or by a name for a catalog is not bundled: it is in `AosLayer::elsewhere`, never in `profile.skills` from this function); MCP servers (a command with a separator made absolute under the root; `env_passthrough` and `headers_env` as optional `env:` references; no header over plain `http` to another host); `contexts` from rules, routing lines, `context` and the harness's `context`; `model` and `effort` from `[harness.<input.harness>]`. Mapping entries are taken in key byte order.
  Refused whole: a name AOS refuses, a tree it cannot digest, an unreadable or invalid `overlay.cfg` (problems under `/about` alone never refuse), a missing or unreadable env file, a path addition that leaves the overlay's folder (`path`, or `invalid` where the manifest check says so first), a variable the specification reserves for the host (`reserved`; every other variable, sensitive or not, applies, and `report` lists the sensitive ones as `env-sensitive`). The agent is found on the host's own `PATH` before the overlay's is added: `canoa launch` and, on Unix, the host's process starter look a bare program name up there when the profile sets `PATH` (`profile::found_on_own_path`); on Windows an in-process Claude, Codex or Pi is started by `coqui-acp-harness`'s own std `Command`, which looks the bare name up on the child's `PATH`.
  What it needs of the computer (`runtime`, and the interpreters its scripts name) is checked by `profile::needs` when a session starts, against the session's `PATH` and then the Store's runtime folders, once per overlay: each need is a report item `runtime.python`, `runtime.node`, `runtime.interpreter: sh` or `runtime.commands: git` (`runtime.os` when `runtime.os` leaves this OS out), `applied` when found and `off` with why when not, with `offer` naming the Store runtime provider (`python_store`, `node_store`, `git_bash_store`, `powershell_store`) that installs it; a version is read by running the program's `--version` (5 seconds, once while its file is as it is). The first program of a name on the `PATH` is the one that counts.
  What preparing made (`profile::prepare`) and the commands `scripts` expose (`profile::commands`) are items of the same report: `dependencies: FILE` and `setup: PATH` are `applied` when the record under `overlays/.prepared/NAME.json` names the overlay's digest (`off`, saying to install or sync the overlay, when it does not; the packages then go on `PYTHONPATH` and `NODE_PATH` after `lib/`, `<NAME>_OVERLAY_STATE` is the state directory, and `AosLayer::packages` and `state` hold them), and `scripts.NAME` is `applied` when its launcher was made in `overlays/.environments/NAME/commands/` (first on `PATH`; a name two overlays share without regard to ASCII case is `refused` for both). A stdio MCP server's bare `command` is also looked for in its overlay's own `PATH` additions (`overlay::path_additions`: `bin/` by default, those that go first before the host's `PATH`, those that go last after it) and given to the agent as an absolute path; a name no folder holds is `refused`, as before.
  The agent itself is found on this process's `PATH` and the Store's runtime folders when its environment sets `PATH`: `Serving::bind` gives `coqui_acp_harness::set_program_dirs` the runtime folders, and the harness's own start (every system, an in-process Claude, Codex or Pi) looks the name up there. Not applied, and listed in `not_applied`: `mcp.skills`, an MCP `timeout` and working directory, other harnesses' hints and the harness's own keys.
- **Templating** (`profile::hosted::template`, the specification's "Templating" through `coqui_aos::{template_values, context_text, skill_text}`): an overlay's `Context::Template` files and the body of its bundled `SKILL.md` have `${NAME}` replaced when `parts_for` hands them out, never in the installed bytes (so the digest, a pin and a move are unchanged). `AOS_OVERLAY_ROOT` is the private copy the overlay's hooks run from, made when a text names it; `AOS_OVERLAY_NAME` is the normalized identity; `AOS_PROJECT_ROOT` is the `cwd` of each `session/new|load|resume` (a context naming it is replaced again per session by `Parts::system_prompt_for`; a skill's body is written once per connection, so it keeps the name as written); `AOS_OVERLAY_STATE` and `AOS_OVERLAY_SCOPE` have no value (no state directory, no scope label). Option values come from `[overlays.NAME] options` (`HostProfile::options`), else the manifest's default; a sensitive option is never replaced. A value of the wrong type refuses each text of that overlay that is templated, reported `refused` under `context` or `skills.NAME` with the option's name and no value.
  `rules`, `routing` and a skill fetched from elsewhere are not templated. The bound on the context counts the replaced text.
- **An AOS layer in a merge** adds an `OverlayReport` to `overlays`, and its `AosLayer` to `aos`. `unset = ["context"]` also takes back every `contexts` entry below. `Effective::environment` builds the overlays' environment first, lowest first, over this process's environment through `lookup`: every root variable, then each overlay's env files, `env` and path additions with substitution. A placeholder reads what overlays set and any variable of this process its text names. A variable an overlay won takes the built value (an optional reference not resolved leaves it out); an error is `Resolve` with key `overlay:<identity>.env.<subject>`. The view adds `contexts` and `overlays` when there are any.

## Overlay hooks (`canoa_host::profile`)

A hook is a program an overlay runs at a named moment of a session (`hook.<ext>` and `[hooks]` in the overlay's manifest, the specification's `hooks.md`). Canoa fires each event it sees over ACP, for the overlays of a profile (a `[host.profiles]` profile, or canoa.cfg's top level for a source of the host's own). It fires nothing for an overlay it does not read. A hook may allow, as a harness's own may: a combined `allow` on a `pre-tool` answers the permission question the person would have been asked (below); nothing else a hook prints approves a prompt or a session.

- **Off until allowed, by digest.** An overlay's hooks run only when canoa.cfg names the overlay's tree digest (`allow_hooks = { team = "sha256:..." }` in `[host.profiles.NAME]`, `[agents.NAME.hooks]` team = "sha256:..." for a source of the host's own), or when the person, asked by the host, allows them for one session (`_canoa/profile/approve`: the question carries `hooks`, one entry per overlay with `overlay`, `digest`, `changed`, `failClosed` and its `events`, each `{event, run, timeout, onFailure, match?, sets?, fires}`; the answer's `allowHooks` lists overlay names, and a name the question did not list is ignored). Both allowances name the files' digest, so a changed overlay is off again (`changed` says it was allowed at another version) and never allowed by itself. An overlay with a hook that has `on_failure = "refuse"` is not activated while its hooks are off (the report says `left out`): a guard that is off would fail open. Only a client that is this process's own link and says it answers (`APPROVE_META`) is asked; every other client gets canoa.cfg's allowances only.
- **What runs.** Each hook runs from a private copy of the overlay's files made from the bytes the digest covered (removed with the connection), as the agent's own hooks do: in the session's working folder (the `cwd` of its payload; a folder that is gone makes the run `not-run`) and with the session's environment, as a child process of the host, with no process group or job object. The environment is the host's own, the variables of the person's own layers, and the environment the specification gives its event (`hook_environment`): every overlay's root variable (each the path of that overlay's copy), every overlay's declarations stacked in composition order (the top layer's value wins, and a secret granted to one overlay reaches every overlay's hooks), the `pre-env` output of the connection, what the earlier hooks of the event set (`env`, whether or not Canoa can apply it), and the hook's own overlay's `AOS_OVERLAY_ROOT`, `AOS_OVERLAY_NAME`, `AOS_OVERLAY_STATE` and `AOS_HOOK_EVENT`; a `pre-env` hook gets the host's environment, the root variables and what the `pre-env` hooks before it in composition order set, run in the directory canoa.cfg is in.
  At its time limit the hook's own process is stopped and nothing it started is. A hook also gets what the overlays' env scripts set (applied after every overlay's declarations, in run order). Canoa runs no overlay's setup, and the agent starts the MCP servers in its own environment, so those are the session's too. The hooks of an event run in the specification's order (`hook_order`: composition order; Canoa has no hook of the user's or the project's). The event is the first argument; the payload, exactly the keys the specification gives the event, is one JSON object on standard input. Interpreters are the first of `python3`/`python` (`python`/`python3` on Windows), `node`, `pwsh`/`powershell`, `bash`, `sh` found on the host's `PATH`; a hook whose interpreter is missing fails as `not-run`.
- **Bounds** are `coqui_aos::Settings`' defaults: 60 seconds a run (or the entry's `timeout`, if shorter), 120 seconds an event, 64 KiB of output (read no further), 1 MiB of payload (the hook is not run), 1024 characters of `reason`. Standard error is read and dropped. A run that fails (`exit`, `timeout`, `too-large`, `output`, `not-run`, `payload-too-large`, `event-timeout`) applies nothing and is logged by cause, never quoting its output; with `on_failure = "refuse"` it also refuses the event (a prompt is blocked, a tool call denied, a session or the agent's start refused).
- **The session's base environment** (`profile::Session`, built in `Connection::prepare_with` from `Starting { who, host }`): the identity variables dotagents stamps (`AGENTS_HARNESS` the harness id, `AGENTS_VENDOR`, `AGENT`, `AGENTS_MODEL`) and Canoa's own (`AGENTS_HOST=canoa`, `AGENTS_HARNESS_VERSION`, `AGENTS_EFFORT`, `AGENTS_ACCOUNT`, `AGENTS_ACCOUNT_KIND`, `AGENTS_ACCOUNT_PROVIDER`, `AGENTS_PROFILE`, `AGENTS_LOADOUT`, `AGENTS_ROLE`, `AGENTS_PROJECT_ROOT`, and the session's access as `AGENTS_SANDBOX`, `AGENTS_NETWORK` and `AGENTS_APPROVALS`), each only when it has a value and never empty; a value the host's own environment already holds is kept. An agent entry with no `Connection` (canoa.cfg's top level holds nothing for it) has none, so `give_agent_flow` builds the same identity variables with `Session::new` and gives them to the agent alone: a harness entry's provider takes them as its request's environment (`kind::Harness::connection_as`), and a program entry is started through `canoa launch` with them on its first line (`Scoped::launching`).
  `merge_with` makes every name readable by every layer (a `built-in:session` entry in `share_env`), so a layer's `${...}`, `from_env` and `if_unset` see them; the agent's environment starts with the identity variables and a layer's own value for one replaces it. `Starting::host` holds what the host sets for the session itself (read, never handed on again). The session's folder and id (`AGENTS_PROJECT_ROOT`, `AGENTS_SESSION_ID`) are added to the environment a hook runs in, from its working directory and the session in its payload. The harness id comes from the provider an entry runs (`claude`, `codex`, `pi`) or the entry's name (`harness_identity`; Grok is `grok`/`xai`, not yet in dotagents' registry). The account's kind and provider are read from its kind id and provided standards (`account_words`).
- **The access of a program the host starts** (Grok, Antigravity, OpenCode, whose `OPENCODE_PERMISSION` is one JSON variable; `Connection::launched_as`, chosen by the harness id the entry gives, so an entry that is only reported as one by its `initialize` answer is started as its entry says): `Connection::prepare_with` asks `Access::translate` (coqui-acp-harness) for the target's variables, arguments and JSON. The variables join the agent's environment unless a layer already sets the name (reported under `access.env.NAME`); the arguments go on `canoa launch`'s first line as `args`; the JSON (Grok's `yoloMode`) is merged into each session request's `_meta`. The Profile line's `access.*` items read the same translation, with `Part::said`.
- **The account's variables** (`Starting::account`, from `kind::Harness::account_environment`): before the account is held, `Accounts::preview` makes the grant it would be given (settings, provided standards and the state folder's path, no credential, nothing created) and the harness's own provider (`coqui_acp_claude::accounts::environment`, `coqui_acp_codex::accounts::environment`) lists the variables that grant sets that hold no credential; the names the specification reserves are dropped. They are read by every layer, ahead of the host's own variables, and are not handed on again, since the provider applies them after the profile's environment: a layer that sets the same name is reported `not supported` under `env.NAME`. Pi lists none yet.
- **Output** goes where the specification says and no further: `context` is added as a pair of content blocks (a label Canoa wrote, then the hook's text alone, so nothing it prints can pass for the label), `decision = "block"` stops a prompt, `"deny"` a tool call, `"ask"` leaves it to the person, `"allow"` answers for them (below). A decision an event does not take is an `output` failure. `context` for a new session goes into `systemPrompt` when the agent says it takes one; otherwise, and for a resumed session and for `post-tool`, it goes after the user's own blocks in that session's next prompt, once. `env` is applied only for `pre-env` (the agent's process environment; a name the specification reserves is dropped by `coqui_aos::fire_event`, a sensitive one is applied and listed as `env-sensitive`); for every other event it is `hook-not-applied`, since ACP has no way to set a variable for the agent's later commands.
- **Session identity.** `session` in a payload is Canoa's own id for the session (random, per connection), never the agent's.
- **The report** (`_meta[PROFILE_META]`, and the profile dialog) lists `hooks.NAME` (off, with `hook-not-allowed`) or `hooks.NAME.EVENT` per hook: `applied`, `applied` with `hook-partial`, or `not supported` with `hook-unsupported`; a failure appears as `hooks.NAME.EVENT` refused with `hook-failed: CAUSE` on the answer to the next session request. Context a hook prints that would take the session past the bound (UTF-8 bytes, together with the hook context the session already holds) is left out whole and reported `hooks.NAME.EVENT` `hook-not-applied`; a later part that fits is still added. `env_scripts.NAME` (off, `env-script-not-allowed`) says an overlay with env scripts has hooks canoa.cfg does not allow at its digest: the overlay still applies, and its env scripts do not run (Canoa runs none either way).

- **Env scripts** run under the same allowance as hooks (`allow_hooks`; an overlay at another digest, or with none, reports `env-script-not-allowed` and runs none, and the person's one-session allow never reaches them, since they run before anyone can be asked). `Hooks::env_scripts` runs them once when a connection starts, through `coqui_aos::composed_environment_running`: after each overlay's `env_files`, `env` and `paths`, in composition order, each script gets the environment the stack has at its turn (the host's own and the session's variables, every root, the `pre-env` output, the earlier overlays' declarations and scripts, its own overlay's declarations, and its `AOS_OVERLAY_*`) and prints JSON objects that go on top, unsubstituted. The script is its overlay's file from the private copy of the bytes the digest covered, run by its `interpreter` (found on the host's `PATH` as the hooks' are, never through a shell) in that copy, with its `args`, its `timeout` (60 s; `0` runs to the end) and `Settings::hook_output_bytes` as the bound on its output.
  A script that does not start, times out, exits non-zero, prints too much or prints anything but the specification's objects applies nothing: the session starts, and `env_scripts.NAME.PATH` is `refused` saying which and ending with the last 300 characters of its standard error (never its output). Each that ran is `applied` and names the variables it set; a sensitive one is also listed as `env-sensitive`. What each gave is kept (`overlay::ScriptRuns`), so every environment built later (the MCP servers' text, hooks' `hook_environment`) reads the same output, and no script runs twice. A default script no interpreter here can run is `script-not-run`. Not done: a script sees the host's process environment and the session's variables, not the person's own layers' variables; a hook sees script output applied after every overlay's declarations, not between them; the `python` interpreter is the first `python3`/`python` on the `PATH`, not the overlay's prepared runtime.

What fires, per event and harness. Every harness is reached through ACP, so the table is the same for all of them except where it says; `cd`, `pre-compact` and the `compact` and `clear` reasons of `session-start` are what ACP does not show, and the table after this one says, harness by harness, where they fire and where they cannot:

| Event | Canoa fires it | Output applied | Cannot |
| --- | --- | --- | --- |
| `pre-env` | Before the agent starts, once per connection, for hooks canoa.cfg allows | `env` (the agent's environment), a failed guard starts no agent | the person's allowance (nobody can be asked yet) |
| `session-start` | `session/new` as `new`; `session/load` and `session/resume` as `resume`; Claude Code's own start after a compaction as `compact` (see Native hooks) | `context`; a failed guard answers the request `-32000` (not for `compact`, which has happened; its `context` goes in the next prompt) | `clear`, `fork` (never sent: a hook matching only those is `hook-unsupported`); `compact` for every harness but Claude Code; `env` (`hook-not-applied`) |
| `session-end` | `session/close`, and for each session still open when the connection ends | none | a killed host, an agent that exits without closing |
| `prompt` | Each `session/prompt`, before the agent has it (declared only) | `context`, `block` (the client gets `stopReason: "refusal"` and a message naming the overlay and the reason) | `env` |
| `turn-end` | The agent's answer to a prompt, after it was passed on | none | continuing the turn |
| `pre-tool` | Each `session/request_permission` (declared only) | `deny` (the host rejects it itself with the request's `reject_once`, else `reject_always`, else cancels, and the client is never asked), `allow` (the host answers with the request's `allow_once`, see below), `ask` and no decision (the client is asked as it would be) | A call the agent's own rules allow, which asks nothing (`hook-partial`); `context` and `env`, and an `allow` that carries an `input` (`hook-not-applied`: ACP's answer names an option and cannot carry a rewritten call, so the allow is not applied either) |
| `post-tool` | The `tool_call_update` that ends a call, `completed` or `failed` (declared only) | `context` (next prompt) | none; the call has run |
| `cd`, `pre-compact` | Claude Code only, through its own hooks (see Native hooks) | `pre-compact`: `block`; `cd`: none | every other harness (`hook-unsupported`, the reason in the report); `pre-compact`'s `context`, `cd`'s `env` (`hook-not-applied`) |

**An allow.** Hooks combine to the tightest: a deny beats an ask, an ask beats an allow, and a deny ends the event (an ask or an allow leaves the next hook to decide). A combined `allow` answers `session/request_permission` itself with the request's `allow_once` option, never `allow_always` (the agent asks about the next call again), and the client is never asked; it is dropped as a deny is. It does not lift the person's refusals.
The agent asks only for a call its own deny rules and mode have left to the person, so those are not overridden; the host adds the person's list of protected paths (`[permissions] protected`, carried in `HostProfile::protected`; unset, the app's recommended list, which is `src/protected_default.txt`: the app's `recommendedProtected` must equal it, and `protected_paths_test.dart` fails when they differ): a call whose `locations` or `rawInput` path keys (`file_path`, `path`, `notebook_path`, `filePath`, `paths`) name a protected place, resolved against the session's folder with `..` worked out and links followed, or a path that cannot be placed (empty, `~`, climbing above its root), goes to the person as it would have, with `hook-not-applied: allow` in the report; so does a request with no `allow_once` option.
The call is read at `toolCall` (ACP v1) or `subject.toolCall` (v2); a question with neither (a v2 command subject, an unknown shape), a request to widen the sandbox (a `fileSystem` in its input, Codex's "Grant more permissions"), a path with a `..` component, on Windows a part ending in a dot or space or holding a `:`, and an `allow_once` option whose id another option shares are never answered by an allow. On a call of kind `other` (an MCP tool's), a hook whose `match` does not name `other` still runs and may deny or ask, but its allow does not count (`hook-not-applied`). **The text of a shell command is not read for paths, so allowing an `execute` call can mean writes to protected paths**: a hook that allows commands answers for everything they do. The native forwarder carries no `PreToolUse` (only `start`, `pre-compact` and `batch`), so no allow becomes a plugin hook's approval.

By harness (`harness` in a payload is the AOS id, from the agent's `initialize` or an entry named `Claude`, `Codex`, `Gemini` or `Pi`; any other entry is `canoa` for `pre-env`): `session-start` context reaches the system prompt of an agent that says it takes one (the Claude and Codex adapters when they announce it) and the first prompt of one that does not (Pi, Gemini CLI, OpenCode, and any agent that says nothing). A tool's `kind` is the agent's own ACP `kind`, `other` when it sends none, and an `other` call runs every `pre-tool` and `post-tool` hook whatever its `match`; `tool.name` is Claude's `_meta.claudeCode.toolName`, else the call's `title`. What only a harness's own hooks could see and Canoa does not fire (a call its own rules allow, an `env` for later commands) is not fired; compaction, a `cd` and a compacted session's start are fired for Claude Code only (below).

### A project's context files (`profile::hosted::project_context`)

A session's agent is handed the project's agent context as the specification's "Project context files" orders it (`coqui_aos::context_files`): in the folder the session opens in (`session/new`, `session/load`, `session/resume`'s `cwd`), `AGENTS.md` and `AGENTS.*.md` and the same names in `.agents`, local files last; `AGENTS_DIR` and `AGENTS_CONTEXT` in the session's environment change the places and the names (an invalid entry is reported as refused). The files the agent's description says it loads itself (`VendorInfo::context_files`: Codex's `AGENTS.md`) are left out and reported `off`. The text goes with each file's path, two blocks each (a label the host wrote, then the file): in the ACP `systemPrompt`, after the profile's context and before a hook's, for a new session whose agent takes one, else with the session's first prompt, after the user's own blocks. A file that is not UTF-8 or would pass the 1 MiB bound of the session's context is reported `refused` and not handed over. The report has an item `project_context.<path>` for each.

Where the agent is Claude Code (its hooks can report `cd`) and the folder holds a context file, the session is given the plugin of the harness's own hooks, and each time its working directory changes the files of the directories between the folder it opened in and the new one that it has not been given wait for its next prompt, broad first, once. Going back, and entering a directory again, add nothing. An agent whose hooks cannot report the directory (Codex has no event for it) is given the files of the folder it opens in only. A session with no context file in its folder, and no overlay hook, keeps no state and gets no plugin. The two variables are read when the connection starts.

### Native hooks (`profile::hosted::hooks::{forward, native}`, `canoa hook-forward`)

For Claude Code the host asks the harness's own hooks to report what ACP does not show. When an overlay with hooks the person or canoa.cfg allowed listens to `cd`, `pre-compact`, or `session-start` for `compact` or `clear` (a hook with no `match` listens to every reason), each `session/new`, `load` and `resume` of a Claude Code session (`claude-code` by `initialize`'s agent name or an entry named `Claude`) carries a second plugin in `_meta.claudeCode.options.plugins`: `canoa-hooks`, in a directory made for that request under the connection's own private directory (see below), removed with the session, or when the request ends in an error, or with the connection.
Its `hooks/hooks.json` has one command hook (`"shell": "bash"`, which Claude Code runs the command through whatever the person's default) per report the overlays need: `SessionStart` (every source: `startup` and `resume` only say where the session is, `compact` and `clear` run the overlays' `session-start`), `PreCompact` (`pre-compact`, with `trigger` `manual` or `auto`), `PostToolBatch` (`cd`: the host compares the working directory Claude Code reports after each batch of tool calls with the one it has, spelled as the host holds it ignoring separators and, on Windows, case; Claude Code's own `CwdChanged` is not given to a plugin's hooks, and `options.settings` is ignored by the adapter). The command is `PROGRAM [program_args] hook-forward --channel DIR/channel.json KIND`, the host's own program quoted for the harness's shell; a guard's `pre-compact` command carries `--refuse` (not a secret), so a forwarder that cannot read its channel still stops the compaction.
No hook is written when the program's or the directory's path holds a character that cannot be quoted safely (`"`, `$`, backtick, `%`, `!`, a control character; backslashes are written as `/`; `'`, `&` and `;` are fine inside double quotes). When the plugin cannot be written (a path that cannot be quoted, a directory that is not the host's own, no room for another secret, a failed write) a session on a harness that needs it for an overlay hook with `on_failure = "refuse"` (`cd`, `pre-compact`, or `session-start` for `compact`/`clear`) is refused (`-32000`) as a `session-start` guard's is; otherwise the session opens and the report says `hook-failed` for the events that needed it. The adapter must be started with `--allow-client-plugins`, as it must for a profile's skills; without it `session/new` answers `-32602`.

`canoa hook-forward [--refuse] KIND --channel FILE` (hidden; it is one of the host's own commands, so an application runs it as `--canoa-child hook-forward`) reads the harness's payload on standard input, keeps only `source`, `trigger` and `cwd` (each a string of at most 2 KiB; nothing else of it, a tool's input or output and a prompt included, leaves the process), reports them on the channel and answers the harness with its exit status alone: 0, or 2 when the host says the compaction is blocked. It prints nothing to standard output and one fixed line to standard error, so what an overlay's hook prints never reaches the harness; `context` goes to the person's next prompt as the other events' does. The host stays the one place that runs hooks, with every bound and the environment above.

The connection's private directory (`canoa-profile-PID-RANDOM`) is made once, at the first thing written under it, in `$XDG_RUNTIME_DIR` where that is set and exists (Unix) and the temporary directory otherwise: created non-recursively, never when something is already at the path, with mode `0700` and checked to be a directory of this user's with no access for others (Unix), or with every inherited right removed and only OWNER RIGHTS and the system granted (Windows, through `icacls`, so no name is looked up); a session's directory is made inside it the same way, and the connection's directory is removed only when the connection ends. A directory that cannot be made that way is not used. At the start of a connection, directories of the same kind a dead host left (`canoa-hooks-*` and `canoa-profile-*`, owned by this user, an hour old and, on Unix, whose host (the pid in the name) no longer runs or that is a day old, or, on Windows, that no host holds open) are removed. The channel is a loopback TCP listener per connection, with `127.0.0.1:PORT` and a 128-bit secret for each session request in that request's `channel.json` (never on a command line or in the environment).
On Linux only connections from this user's own processes are heard (the socket's owner, as for the delegation tool server); the secrets keep other users and other connections out, and not the person's own sessions from one another, whose agents the person already trusts. A request is one line of at most 8 KiB: `{secret, nonce, kind, fields}`. The host compares the secret against every one it holds in constant time, drops with no answer anything else (a bad secret, a line past its bound, JSON that is not one request, a kind it does not know), queues at most 64 and runs at most 16 handlers, each of which has 250 ms in all to receive its line, and answers `{nonce, block}` with the forwarder's own nonce, which the forwarder checks; a block is honoured only for `pre-compact`. A session loaded again is given the plugin and secret it already has. The reports are read between the messages the host relays (every 50 ms at most), so an event's hooks run on the relay's thread as the other events' do; a secret ends with its session (`session/close`, or the connection) and a report for a session that is not open is dropped.
A forwarder that is not answered (no host, an unreadable or missing channel file, an answer not signed by the secret, a refused secret, a timeout of 130 s) stops the harness only when it was given `--refuse`, exit status 2; for everything else it lets the harness go on. A hook that fails with `on_failure = "refuse"` blocks the compaction, as for a prompt.

Per harness and event (measured through the real adapters on Claude Code 2.1.311 and Codex 0.166.0; each cell is a test or a recorded measurement):

| Event | Claude Code (`coqui-acp-claude`, `canoa agent claude`) | Codex (`coqui-acp-codex`) | Gemini CLI, Pi, others |
| --- | --- | --- | --- |
| `cd` | fired, from the working directory after each batch of tool calls | cannot: Codex has no event for it | cannot |
| `pre-compact` | fired for the person's `/compact` (`manual`), through `PreCompact`; `auto` is the same hook and was not triggered | cannot: the adapter has no compaction request, and Codex's hook has no trigger over ACP | cannot |
| `session-start` `compact` | fired, after a `/compact` | cannot, as `pre-compact` | cannot |
| `session-start` `clear` | cannot: the person's `/clear` ends Claude Code's session and the adapter's, so no session starts after it | cannot: no `/clear` over ACP | cannot |

Codex's own hooks could carry these through a `hooks.json` and a trust line (`[hooks.state.'KEY'] trusted_hash`) in its home, but none of the four events is reachable over ACP, so the host writes nothing into a Codex home. The report says each as `hook-unsupported` with the reason.

## AOS overlays (`coqui-aos`)

`canoa_host` has no AOS module of its own: overlays are read, validated, digested, composed and their environment built by the [`coqui-aos`](https://github.com/Boriken-Dev/coqui-aos) crate (a git dependency at one revision; its `AGENTS.md` is the API header), which passes the specification's conformance vectors in full. What is Canoa's own is how a profile uses them (`profile::overlay_layer`, `profile::hosted`), held to `tests/vectors/profile.json`:

- **Reading.** The manifest is `coqui_aos::read_overlay` at the default `Settings`: `OVERLAY.md`'s front matter (restricted YAML, or the format its first line names) or `overlay.cfg` (TOML, JSON after `#!json`, YAML after `#!yaml`); a tag, anchor, alias or merge key is refused, and so are both files together (`manifest` refusal, subject the reader's class). A body of `OVERLAY.md` that is context becomes a `Context::Text` (the front matter is no context), never the file; `CONTEXT.md` beside it is not applied and is listed in `not_applied` as `context: CONTEXT.md, ignored ...`. Mapping order is the document's order; every order Canoa shows is key byte order.
- **A tree** is a `coqui_aos::OverlayTree` (every member's path and bytes), as `coqui_aos::read_tree` reads a directory (`OverlayInput::tree`); `overlay_layer` digests it again with `digest_entries`. A path under an excluded name is not in a tree `read_tree` returns, so it is neither digested nor delivered.
- **Limits** are `coqui_aos::Settings`: an installed overlay at the defaults (4096 files, 64 MiB), a host-profile skill's directory at 1024 files and 16 MiB.
- **The environment** is `coqui_aos::composed_environment` over the overlays in composition order, once after each overlay (`build_each`), from an `Environment` of the process variables an overlay's text names (any word of its manifest or env files), each readable by a placeholder and granted to the `env` provider. `Built::owned` is a variable an overlay set, even to the value the process holds (found by composing again over a base whose values are marked). A refusal is `ProfileError::Resolve` with key `overlay:<identity>.env.<subject>`.
- **The report** (`OverlayReport`) is `coqui_aos::effective` over the manifest and its env files with every variable their text names granted and empty: `non_defaults` are the specification's for what Canoa applies (`unpinned`, `env-passthrough`, `secret-read`, `env-sensitive`, `insecure-transport`; not `setup-network`, `deps-network` and the rest, since nothing of them runs; `env-script` is not listed here either, since the connection's own report lists each script that ran). When that call refuses (a partial lock, an env-path conflict) the report lists none, since the environment would refuse too.
- **A server over plain `http`** to another host (`insecure-transport` in that report) never gets `headers_env`.
