# `canoa-host` multi-user portal and home lock

## The portal (`canoa_host::portal`, feature `portal`, Unix; `canoa_host::portal_link`)

`canoa portal` serves the web app to people who sign in with their account on this machine, and gives each a `canoa serve --portal` of their own, started as them. The guide is `docs/portal.md`; this is the contract.

- **A mount under a path prefix** (`base_path`, `mount.rs`; `Mount` is on `Inner`, the guide's "Under a path prefix"). The routes, pages and constants are written for `/` and never name the prefix: `Mount::enter` takes it off a request's target (a bare `/canoa` goes to `/canoa/`, a target outside is `404`, and the request then names its cookies with the mount's words, `Request::cookie_slug`), and `Mount::leave` puts it on the answer: a `Location` that starts with `/`, every `Set-Cookie` of a `__Host-` cookie (renamed `__Secure-NAME.WORDS`, `Path=` the mount), and the `href`, `action`, `src`, `data-options-url` and `<option value` paths of an HTML body. A path a page writes some other way (a JSON body, a header, a file's text) is made with `Mount::path` where it is written: `canoa.json`'s channel addresses, `GET /portal/account`'s `path`s, and the site's `index.html`, which is read whole below a mount so that `leave` rewrites its `<base href="/">`. At `/` both do nothing and the bytes are the root's. New pages and cookies follow the rule by writing root paths and `__Host-` names; a new place that writes a path another way must call `Mount::path`. `X-Forwarded-Prefix` is not read (the guide says why). `tests/prefix.rs` is the proof.
- **The Office add-in** (portal settings `office = false`, `office_frames`, `office_handoff_seconds = 60`; `office_frames` is checked as `[host.web] office_frames` is, `Settings::check` naming it; each non-default is logged at `warn`). With `office` the portal answers, under the add-in's own policies (`web::Office`, the same as the standalone server's), `GET /office/taskpane.html`, `dialog.html`, `taskpane.js`, `relation.js`, `dialog.js` and `icon-16|32|64|80.png` to anyone, and `GET /office/app/` (the site's `index.html`, `frame-ancestors 'self'` and the Office origins, no `X-Frame-Options`) to a browser with a session, else `401`; any other `/office/...` path is the site's, behind the sign-in, with today's headers. `GET /office/session` answers JSON, `200 {"signed_in": true, "user"}` or `401 {"signed_in": false}`. `GET /office/signin` (`Sec-Fetch-Site` absent or `same-origin`, else `403`) sets the marker `__Host-canoa-office=1; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=600` and answers `303 /portal/login`.
  While the marker is in a request, every answer drops `Cross-Origin-Opener-Policy` (a header value that is empty is never sent), and a sign-in that completes (`steps::advance`, any method, any number of steps) opens no session: it keeps a `session::Handoff` (account, uid, method, `password_at`, fingerprint, steps, the time of its code) in `Handoffs` (memory only, `office_handoff` long, `max_sessions` in all and `max_sessions_per_user` for one account, the oldest of an account going first), clears the marker and the pending cookie and answers `303 /office/dialog.html#done=STRING` (43 characters of URL-safe base64, only its SHA-256 kept). `POST /office/session` `{"handoff": STRING}` (`from_own_page`, else `403`; no JSON string `400`; an unknown, used or old string `401`, one claim in any case) opens a session with `open_after` from the handoff, runs `resume` (the account's standing and the sign-in policy again, from this request's address) and answers `200 {"signed_in": true, "user"}` with `__Host-canoa-pane=TOKEN; Path=/; Secure; HttpOnly; SameSite=None; Partitioned; Max-Age=SESSION`.
  `Request::token` is `__Host-canoa`, else `__Host-canoa-pane`; `POST /portal/logout` ends both sessions and clears both cookies. Nothing else about a session changes: a `POST` and an upgrade still check `Origin` and `Sec-Fetch-Site`, `/canoa.json` still refuses a request that crossed sites.
  - Requests: `GET|POST /portal/login` (form `method` = `password` with `user` and `password`, `certificate`, or `passkey` with `answer`, the browser's signed answer as `PublicKeyCredential` JSON, taken only with the challenge the cookie `__Host-canoa-passkey` names (`passkeys::COOKIE`), which is taken as it is used; failures count against the address (`Throttle::begin_passkey`), not an account's name; a method the policy does not offer this connection is `403` before the throttle and before any provider, a method word it does not know `400`), `GET /portal/methods` (no cookie; `{"methods": [...]}`; `certificate` only on `socket`), `GET /portal/login.css`, `/portal/login.js` and `/portal/icon.svg` (the brand's icon, the favicon; the pages' policy has `img-src 'self'`), `GET|POST /portal/certificate` (signed in; `action` = `enrol` or `remove`; enrolling needs a certificate on `socket` and the password: the session's own, when a password signed it in within `enrol` with this same certificate, else typed again in the form through the throttle; refusals are `403`;
  a pin or removal is logged at `warn` with the fingerprint and address, and ends the account's certificate sessions that used the old pin), `POST /portal/logout`, `GET /portal/session`, `GET /canoa.json`, `POST /portal/pair`, `GET /portal/ws/entry/NAME` and `/portal/ws/control` (WebSocket), and any other `GET` or `HEAD` is the site, to a signed-in browser (else `303 /portal/login`), except `/manifest.json`, `/favicon.ico` and `/icons/NAME`, which anyone is given (a browser fetches the manifest with no cookie; they hold nothing private). Every request carries one `Host` that is `localhost`, an address or one of `hosts` (else 421). A `POST` and a WebSocket upgrade need an `Origin` equal to `Host` and no `Sec-Fetch-Site` but `same-origin` (else 403). A body is at most 4096 bytes. HTTP/1.1, one thread a connection. It listens on `socket`, a Unix socket only the proxy's group can reach, and optionally a loopback `listen` for development (beyond loopback is refused: the cookie is `Secure`, so a proxy speaks TLS). `GET /canoa.json` starts a host, so a browser that says `Sec-Fetch-Site` is not `same-origin` or `none` is refused (403).
  An `Origin` is the page's own `scheme://host`: `https` when the proxy (on `socket`) says `X-Forwarded-Proto: https` or the host is not `localhost` or an address, else `http`; `null` is never one. The sign-in page sends `Referrer-Policy: same-origin`, every other answer `no-referrer`. The sign-in and certificate pages have the policy `default-src 'none'; style-src 'self'; script-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`, no inline script or style, and are server-rendered from the same method list `/portal/methods` answers; `login.js` only counts a `429`'s `Retry-After` down. The sign-in policy decides which methods a request may use (below). A certificate sign-in whose request carries no certificate header is `401` with its own notice, is not counted by the throttle and asks no provider; an expired certificate and one pinned to no one are `401` with their own notices, counted, naming no account, and the log says which of the three (never the certificate). A password sign-in on `socket` that carries a certificate pinned to no one is redirected to `/portal/certificate`.
- **Sign-in.** `Throttle::begin` is asked before the accounts, in one step with counting the try: an address (IPv6 by its /64) with `max_failures_per_pair` failures for this account, or `max_failures_per_address` for any, in `failure_window` is `429` and PAM is not called; an account with more than `slow_after_user_failures` failures from anywhere makes the try wait `slow` per failure over, up to 30 times, and is never shut out. A wrong password, an unknown name, an account the provider does not admit and root or a user id below `min_uid` are all `401`; accounts that cannot be asked are `503`, and count as a failure; only a success (or a try never made, a busy portal) takes its count back. Every failed sign-in, `429` included, is answered no sooner than `failure_floor` after the request began. The session is a random 256-bit token; the cookie is `__Host-canoa=TOKEN; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=session_seconds`; only the SHA-256 of the token is kept; an account holds `max_sessions_per_user`, the oldest ending when another comes. A cookie named twice is no session.
  The address counted is the TCP peer's on `listen`, which never believes a header; on `socket` it is the last address in `client_address_header` that is not in `trusted_proxies`, or one shared address when there is none.
- **Sign-in policy.** `sign_in_policy` (an `Entry`; `provider` defaults to `coqui_signin_rules`, built in, any other from `library`; `enrol` is not read) is a coqui-access `coqui_sign_in_policy` provider, built when the portal binds (a provider that is missing, does not load or refuses its configuration is `PortalError::Settings`); with none, `SignInRules::single_factor` over the methods `Accounts::methods` lists.
  It is asked, with `service` `portal`, `client` `browser` and the time: (1) for the page and `GET /portal/methods`, `purpose` `sign_in`, no person, no steps, the address the proxy reported or `None` (never `0.0.0.0`: that stays the throttle's key for an unknown address) - the offered methods are the policy's, in its order, that this portal has (`Method::from_id`; another word is ignored) and, for `certificate`, only on `socket`; (2) for a `POST /portal/login` before the throttle and before any provider: the method not offered is `403` (a word that is not a method of the portal's is `400`), and only the `providers` of its `Offer` are asked, in its order (`Accounts::sign_in*` take them; a name no provider has asks nobody); (3) once a provider accepts, with the account (`Person { id: uid as text, name, groups }`, the groups the system directory gives) and `done` = the one step (`Factor { method, provider, person }`): `complete` opens the session, which keeps `done`; anything else, and an error from the policy (logged), is not a success - the try stays counted, and the answer is `401` and the floor, so a policy that cannot decide reads as one that decides against;
  (4) `purpose` `resume` in `resume`, which `host_for` (`GET /canoa.json`, `POST /portal/pair`, each WebSocket upgrade) and `GET /portal/session` and `GET|POST /portal/certificate` all go through, with the session's steps, the address now and the groups `Accounts::still` returns: not `complete` closes the session (`401`; `303` to the sign-in page for the certificate page), an error is `503`, and so is a directory that cannot say the groups (the session stands). The address is compared to `trusted_proxies` as an IPv4 address when it is IPv4-mapped. The log says at bind which policy is in force. A password retyped at `/portal/certificate` is first checked for `password` among the policy's offers for the client. The log names the method, the address and the rule, never a name typed. `coqui_access_proxy` in `authenticators` stops `Access::new`.
  A provider that answers by `claims` goes to the matcher (`matcher`: a list of `MatcherRule { by, template, domain, pins }`, coqui-access's `MatchRule`; none is its defaults, the UPN as a name then the email; it asks the operating system's accounts only): exactly one account is a match and is then admitted by `Access::admit` under `min_uid` and `groups`; none or several is `SignIn::Refused` (logged without the claims); a directory error is `SignIn::Failed`. `local` without `domain` makes `Access::new` fail; a value with more than one `@` makes no candidate for a rule that strips or takes the realm (the matcher's own rule), and a match whose `Person::id` is not the admitted account's numeric user id is refused. Only a certificate on `socket` is ever asked of a provider, so none reaches the matcher from `listen`.
- **Second step.** A valid step the policy finds not enough, with methods still offered, opens a pending sign-in (`session::Pendings`, memory only; the cookie `__Host-canoa-pending=TOKEN; Path=/; Secure; HttpOnly; SameSite=Strict`, only the SHA-256 kept): the account, the steps passed, a count of tries, the first method, when a password was typed and the certificate its request carried. `pending_seconds` (300) and `max_pending_tries` (5, right or wrong; the try after the last ends it unchecked) bound it; `POST /portal/login` with `method=cancel` ends it. While it lives, `GET /portal/login` and `GET /portal/methods` (`{"step":"next","methods":[...]}`) answer from the policy's offer for its steps and the account's groups now, a method not offered is `403` with nothing asked or counted, and a code (`method=totp|recovery_code`, field `code`) is checked for the pending account only (`Accounts::check_code`): the browser never names whose it is. A password or certificate step must name the pending account, else it fails and counts.
  Each try passes `guard_try`: the pending try count, `Throttle::begin` under the account's lower-case name (the pair and address limits, `429`), then `Throttle::begin_person` (`max_factor_failures_per_person`, default 5, by user id, from any address, sliding over `failure_window`, and `max_factor_failures_per_day`, default 20 over `factor_day_seconds`; `begin_person` says which limit; a refused try is not counted for the person but stays counted for its address, `401`, and is logged: at `warn` with the account for the first in a window, at `info` after). A right step takes its counts back. When the offer after a step includes `certificate` and the request is on `socket` and carries one that `certificate_status` says is `PinState::Yours` for the pending account, it is tried in the same request; any other certificate is not tried (it would count a failure against someone who only sent a password). The session opened records every step; its `method` is `password` when one was typed (with `password_at` and the fingerprint of that request's certificate), else the first, and `close_certificates` ends sessions that have a certificate step.
  `resume` ends a session whose `done` holds `totp` or `recovery_code` when `factor_standing` is no longer `Enrolled` (disabled, reset, none), or when the record's made time is not the value the session recorded (`Session::code_made`, taken when it opened: a code set up again), and answers `503` when the codes cannot be read; a channel's liveness check does the same every `CODE_LOOK` (3 s) for such a session and keeps the channel when the read fails.
  A code record is keyed `UID:NAME` (`code_key`), so a user id made again does not find the earlier account's code; `reset_factor` asks the provider's account kind to reset the account (`AccountPut::reset`: the provider takes the code away and keeps the mark, `AccountInfo::reset`), and `FactorStanding::Reset` (a reset account, or an account of the same user id under another name) blocks every self-setup until `canoa portal factor enrol NAME --code` (the provider lifts that account's mark when its first code is confirmed; `Access::clear_reset(uid)` removes the marks of that user id under other names) lifts it; `Access::unlock` asks the kind to unlock (`AccountPut::unlock`: it ends the provider's own delay and sets `AccountInfo::unlocked_unix`, in seconds), and the portal's `guard_try` clears the account's counts (`Throttle::clear_person`) when it sees a later time than it acted on; `Access::check_code_files_owned` runs first in that command, once the providers are built (building one writes nothing), over the files the code provider's entry names (`source`, `pending`, `waiting`; the provider is the one whose authenticator takes one-time codes) and their locks and folders, no other provider's. An account the provider holds no code for is neither marked by a reset nor stamped by an unlock.
- **`/portal/factor`.** `GET` shows whether the account has a code and what to do; `POST` (own page only) `action` is `step` (a signed-in person shows a factor the policy's `enrol` decision asks again, `method` and its fields; the steps are kept in a pending state of purpose `enrol` bound to that session, `enrol_seconds` long), `begin` (only when `enrol` is `complete` for the steps shown, and, for an account that already has a code, only when those steps include its `totp` or a `recovery_code`: a rule for `enrol` that asks for a password alone does not replace a code; for a sign-in's pending state the purpose is `enrol_first`, which only a rule that names it allows, and also only when the account has no code, is not `Reset` and the sign-in offers `totp`; logged at `warn` there; answers the link, a QR code as inline SVG and the recovery codes, once), `confirm` (`code`; passes `guard_try`; confirms the waiting setup, which in a sign-in is also its `totp` step) or `cancel`. No cookie is `401`; with no `enrol` rule nobody gets past `Nobody`. A portal with no code provider answers `403` to every action.
- **`GET /portal/account`.** A session's own question (`401` with none or an ended one, which `resume` decides as the pages do): which of the portal's own pages it may open now. `{user, code?, passkeys?, certificate?, sign_out}`; each page is `{path, allowed, reason?}` plus `set_up` (code: enrolled or disabled), `count` (passkeys, `null` when unreadable) or `pinned` and `disabled` (certificate); a page this portal does not keep (no code provider, no passkey provider, no certificate provider with `enrol`) is absent. `allowed` is the page's own gate, never a second rule: `factor::availability` and `passkeys::availability` call the `gate` the page calls (policy purpose `enrol`, the standing, and the steps already shown), and a code in use that the `enrol` rule cannot ask a code for is `false`; a person who holds passkeys is `allowed` there whatever adding takes; the certificate page is `false` when none is pinned and the connection carries none. `account::links` says which pages exist for the pages' own links (`page::Links`, `nav`): each signed-in page links to the others and to `/`. `Cache-Control: no-store`.
- **`/portal/passkey` and `/portal/passkeys`.** `POST /portal/passkey` (own page only) makes the challenge for the step the browser is at: the pending sign-in's account, or none; with `for=enrol` for a signed-in person showing a passkey again under `enrol`. It answers `{"options": ...}` and sets the cookie (`Secure`, `HttpOnly`, `SameSite=Strict`, as long as the provider's challenge lives); `403` when the policy does not offer `passkey` here (nothing is asked of the provider), `404` for a named account with no passkey, `429` with `Retry-After` when the provider holds `ceremonies_per_source` for the address or `max_passkey_ceremonies` wait. `GET /portal/passkeys` lists the account's passkeys and what adding one takes; `POST` (own page only) `action` is `step` (as `/portal/factor`'s: the steps are kept in a pending state of purpose `enrol` bound to the session), `begin` and `confirm` (only when `enrol` is `complete` for the steps shown; one registration uses them up; logged at `warn` with the credential's id), `remove` (ends the sessions that passkey opened) and `label` (a session alone may), `cancel`. `resume` and a channel's liveness check end a session whose passkey the account no longer holds. With no `enrol` rule nobody can add a passkey.
- **`canoa portal [--config FILE] passkeys list | remove NAME [ID]`**, run as the portal's account: `list` prints a JSON line per passkey (`user`, `id`, `label`, `added`, `last_used`, `synced`, `disabled`), never a key; `remove` takes one passkey, or every passkey of the account, away and prints `{"removed": {account, passkeys}}`; status 2 for a portal with no passkey provider or files another account owns, 1 for a failure or nothing removed.
- **`canoa portal [--config FILE] factor list | enrol NAME [--code CODE] | reset NAME | reset --id UID:NAME | unlock NAME`**, run as the portal's account: `list` prints a JSON line per account (`id`, `user`, `enrolled`, `disabled`, `waiting`, `reset`), `enrol` without `--code` prints `{"enrol": {user, uri, recovery_codes}}` once and with it confirms the setup waiting, `reset` prints `{"reset": {account, had_one}}`; status 2 for a portal with no code provider or an account it does not sign in, 1 for a failure.
- **Channels.** The socket's path is `socket_dir/USER/entries/NAME.sock` or `socket_dir/USER/control.sock`, made from the session's account name and a `NAME` of letters, digits, `_` and `-` checked here, and nothing else the browser sends. Messages are relayed between the WebSocket (binary only; text ends the channel) and the socket's length-prefixed frames, at most `max_message` bytes each. A channel ends when either side does, when its session ends (sign-out or expiry, checked twice a second) or when the portal stops. A user may hold `max_relays_per_user` open. A write that makes no progress for 30 s ends the channel, and the socket is shut before the writer's lock is wanted.
- **Hosts.** `Accounts::still` is asked at each use: an account that is gone loses its sessions (401). `acquire` asks the introduction socket and, when it does not answer, starts the unit and asks again for `start_seconds`, never above `max_hosts` running. Each user has a state of their own, a lock held across only that user's own start or stop; `ask` has one 5 s deadline for the whole answer (at most 64 KiB). A host with no channel and no use for `idle` is stopped (checked every tenth of that, between 0.2 s and 30 s); one with a channel open never is. `Systemd` runs `[elevate] systemctl start|stop --no-ask-password UNIT`, which may be `dist/canoa-instance`, a root helper that takes only those words, a `NAME_PATTERN` name and an account in `ALLOWED_GROUPS` with a user id of 1000 or more outside the system ranges (it sets its own `PATH` and `LC_ALL`). `POST /portal/pair` `{"peer"}` asks the host to accept that key every 250 ms for `pair_seconds`, `200` once it is, `404` when it never connected.

- **`serve --portal DIR --portal-user USER`** (`ServeOptions::with_portal`): `check_account` first refuses to run as root, in `system_uid` ranges, below `--portal-min-uid` (1000), as an account in none of the `--portal-group` groups (one at least is required), as a name (`USER`) that is not the last part of `DIR`, or with a `DIR` this account does not own (status 2); then, as with `--allow-empty`, a canoa.cfg that does not exist yet reads as empty (the person's own file is where settings are written, and the control channel creates it on the first one); `DIR/entries` is made (`0755`); every entry that is not a host source, and the control channel (made if canoa.cfg has none, with canoa.cfg's limits when it has), listen on a Unix socket there, mode `0666`, replacing any `listen` canoa.cfg gives; `[host.web]` and `--web` are ignored. Every connection is checked with the system's own word for who is at the other end (`SO_PEERCRED`): one whose user is not `USER` is closed before a byte is read and logged at `warn`.
  A paired key is the person's own browser, so on the control channel it holds `Grant::all()` with no entry under `grants`; an entry's `peers`, when it lists keys, still applies. Every harness entry that names no profile starts with the person's own top level there too.
- **The introduction socket**, `DIR/portal.sock`, takes one line of JSON a connection from `USER` only: `{"op":"index"}` answers `{"peer", "method", "os", "entries": [{"name", "kind", "harness"?, "title"?}]}` with no `url` (the control channel is there, `kind` `control`); `{"op":"accept","peer"}` is `peers::accept` (only a key that connected and waits) and answers `{"ok":true,"peer"}` or `{"error"}`; `{"op":"revoke","peer"}` answers `{"ok": bool}`; any other request `{"error"}`. A request is at most 4096 bytes and 5 s.
- The sockets are `coqui-transport-pipe` listeners at mode `0666` with no group, so the pipe crate's own checks stand: a parent that others can write, or that another user owns, is refused. The unit makes `DIR` as root, owned by the person, under a `/run/canoa` only root writes.

## One host on a home (`canoa_host::home`)

```rust
pub fn Home::at(dir: impl Into<PathBuf>) -> Home
pub fn Home::of_user() -> Result<Home, cabuya::Error>   // COQUI_AGENTIC_PEER_HOME, else ~/.canoa (%USERPROFILE%\.canoa on Windows)

pub fn Home::lock(&self, name: &str) -> Result<HomeLock, LockError>
pub fn Home::holder(&self) -> Option<Holder>   // by what it wrote; proves nothing about the lock
#[non_exhaustive] pub struct Holder { pub name: String, pub pid: u32 }
#[non_exhaustive] pub enum LockError { Held { dir: PathBuf, holder: Option<Holder> }, Io { dir: PathBuf, source: io::Error } }
```

- `lock` takes the operating system's lock, made with its parents when absent: on Unix on the directory itself, on Windows on `host.lock` in it, held open so that nobody can delete or rename it meanwhile; removing a file cannot let a second host in. It writes `{"pid", "name"}` to `host.holder` through a file of a name nobody could know in advance, made only where nothing is. So a holder that dies gives it up however it died, and a process id used again proves nothing. `Held` says who, or `None` when the holder has not said within half a second. Two locks in one process conflict too.
- Dropping a `HomeLock` removes `host.holder` and gives the lock up; `host.lock`, on Windows, stays.
- The lock is only as good as the filesystem's: a home on WSL's `/mnt/c` (9p) is not locked against a host on Windows, and a network filesystem is untested.
- What `Display` says of `Held` names the holder, its process and the home. `canoa serve` and the app show it.
- A file system that has no such lock is `Io`: that host does not start.
