# `canoa-host` serving, web, native host, providers, and tools

## Serving (`canoa_host::serve`)


- `stop_agents` ends each agent and each provider process with what it started (job object on Windows, process group on Unix), and turns every later proven connection away before its agent serves it. The listeners stay bound.
- `stop` does that and ends the rest, so an application can start a host again in its own process: each listener closes within 100 ms, when `run` returns, and a fixed address can be bound again; a proven link ends within about a second; a link still in its proof ends by `PROOF_LIMIT` at the latest, holding no address. An entry could one day be served from a stream in this process rather than a program: `run` keeps what serves a connection behind one private enum.

- `bind` binds every entry before any is served, so a failure leaves none listening. An entry that listens on a pipe is bound by `coqui-transport-pipe` with its defaults (see "A pipe or Unix socket"); a failure is `ServeError::Pipe`, and `Listening::url` is then `pipe:NAME` or `unix:PATH`, as `Listen` prints it, not a `ws://` URL. An entry on an address beyond loopback is bound as a plain WebSocket listener with `plain_beyond_loopback` set (the person chose the address) and logged at `info` as `non-default: host.agents.NAME.listen is ADDRESS, default loopback`: every message after the proof is sealed, so the address is the person's to choose.
- Each connection: the WebSocket handshake, then the proof of the identity's method, Noise (`coqui-peer-noise`) or WebCrypto (`coqui-peer-webcrypto`), within `PROOF_LIMIT`; a client of the other method fails it, and the log names both methods. Then the trust store decides (a stranger that proved its key is recorded as waiting), then the entry's `peers`, through a `canoa::Registry` holding one verified `Service` per entry and a grant of `ACP_CAPABILITY` per listed key. Every later message is sealed in the proof's session, which is checked against the store every second: a removed key loses its link.
- On an agent or tool entry, worktree requests (see "Worktrees") are answered by the host before anything else, up to 16 per connection, then the connection ends; once a first other message has come, one is answered `-32600`.
- The first message must be plain ACP: a link of streams (`coqui_link::mux`) is refused. Then a fresh process serves that connection, relayed by `coqui_acp_bridge::relay`, and is stopped with its process tree when either side ends.
- An agent entry runs `program args`.
  Every message from the client to it is parsed and the host's own serialization forwarded: `params` other than an object is answered `-32602`, since a list would fill a request's fields in order; `_meta` is removed at every depth, except that an `initialize` is given coqui-acp's usage opt-in again, `{"notify": <true whenever the host keeps a usage log, else the client's own wish, false unless it asked>, "account": <the entry's name>}` (the host hides the agent's `_coqui_acp/usage_update` from a client that did not ask, so the log has the spend of a client that never asks or polls) under `dev.boriken.coqui.acp/usage` in the client's capabilities (`clientCapabilities`, or `capabilities` from version 2), and every usage report the agent sends back (the `_coqui_acp/usage_update` notification's, and an answer to `_coqui_acp/usage`) leaves with `account` set to the entry's name whatever the agent named, so a client never reads an account the host did not assign;
  when the agent's `initialize` answer does not advertise the usage capability, the host stands in for it (`usage_splice`): it adds the capability with `sources: ["inferred"]`, reads each failed `session/prompt` answer (the error's message and data) and each `refusal` (what the agent said in that turn) for the entry's limit phrases, keeps one report per entry shared by its connections (bucket `inferred`, exhausted, `account` the entry's name, `revision` and `observed_at` the host's), answers `_coqui_acp/usage` itself without forwarding it and sends `_coqui_acp/usage_update` to a client that opted in with `notify` when the report changes; an inferred hit ends at its `resets_at`, else at `observed_at` plus its `retry_after`, else when a turn of the agent ends well, and a good turn does not clear one whose end has not come; with `limit_phrases = []` the host adds and answers nothing; an agent that advertises the capability is untouched;
  before the `initialize` answer shows the agent does not advertise it (and after an `initialize` that failed) the host only forwards, and while it speaks for the agent it drops the agent's own `_coqui_acp/usage_update` and any answer to a usage request it answered; agent text is kept only for a session with a prompt open; a request whose `params.mcpServers` holds anything but `http` or `sse` at an http or https address, or `acp`, is answered `-32602` (plain http beyond this computer is the person's own client's choice: it passes and is logged at `info` as `non-default: a client's MCP server is plain http to HOST`) and never reaches the agent; with `working_roots`, so is one whose `cwd` or `additionalDirectories` is outside them; what is not one JSON object is answered `-32700` or `-32600`. A refused notification is dropped.
- `usage = "<reader id>"` on an agent entry (`program`, never `harness`) makes the host read the agent's quota as well, through the `usage_reader` provider of that id that a bundled agent's crate offers (`canoa::usage_reader`; `antigravity` is `canoa-antigravity`'s, the one value today; an id is held to what an id is when canoa.cfg is read, and the host looks for it among the bundled agents' readers and those of the libraries and sources of canoa.cfg's entries and extensions when it serves (`serve` stops with `ServeError::Usage` naming the entry when none offers it); an `[agents.NAME]` command that is a bundled preset's own program and arguments, such as `agy acp`, gets its preset's reader). The host owns when to read (`usage_splice/reader.rs`) and the reader owns what a reading is: it describes its id, its bucket prefix and its timings (`ReaderInfo`), and opens a reading for each connection that is told the agent's `session/new` answer (`UsageReading::opened`, which Antigravity's takes the models from) and asked for the figures of a process (`UsageReading::read`).
  The `initialize` answer's capability then says `sources: ["reported", "inferred"]` and `needs_session: true`, and the entry's report is the buckets read (Antigravity's, from coqui-acp's `AgyQuota`: ids `agy:<first model id>`, permille, `reported`) beside any inferred hit, its `revision` the sum of the two counts. A reading looks at the processes that are the agent's, which the host gives the reader as the `process_members` object: the one the host started and those below it (`usage_splice/members.rs`: on Windows a Toolhelp snapshot taken in the host's process, elsewhere `/bin/ps -A -o pid=,ppid=,pgid=` taking children by parent and the process group the agent leads; a table that cannot be had leaves the agent's own process; on Windows each row carries the process's creation time and a child counts only if created at or after its parent, so an orphan whose dead parent's id was reused is not adopted). The reader tries the agent's own process alone first and uses the tree from the first time that finds no port, which is the case below `canoa launch` for a profile (Antigravity's).
  The port that answered is kept for the agent's life and asked again with no listing; ports are listed again only after it fails (on Windows the listing is `GetExtendedTcpTable` in the host's process, so no `netstat.exe` runs). A client that asks for figures does not wait for the settle time. Antigravity's models are `session/new`'s `models.availableModels[].{modelId, name}`. A reading runs on a worker thread of the connection, never the relay thread: once the session has been open for the reader's settle time (10 seconds for Antigravity) with no turn running or its first turn has ended, never while `session/new` is being answered or a first turn runs (then at once, and after each of the reader's retry times, 2, 4, 8 and 16 seconds for Antigravity, while the agent shows nothing to read), after each prompt answer, and for `_coqui_acp/usage` from a reading younger than the reader's cache time (15 seconds), else after one; the answer and any `_coqui_acp/usage_update` are written by the connection's receive loop on its next 50 ms tick.
  With no session open, `_coqui_acp/usage` starts a private agent (the entry's program and args, the host's environment), initializes, opens an empty session in `<state_dir>/usage-read`, reads the whole tree of the process, retrying while the reader says it shows nothing yet, and ends it; one at a time per entry, not within the reader's cache time of the last start, and none while a session of the entry is being opened (the entry's figures as they stand answer then), the reader's limit at most (40 seconds for Antigravity). The private agent is started through the host's record of its agents, so stopping the host ends it and none starts while it stops; it is also ended when its process ends early. A request that comes while one reads waits for it. None starts for an entry with `profiles` (its environment is not applied to the private agent, so it would read the host's account, not the connection's) or when `ServeOptions::state_dir` is none; the answer is then what the entry holds. The entry's buckets are shared by its connections, except for an entry with `profiles`, where each connection keeps its own, so no connection is answered from another's reading.
  The account's email (else its name) and plan leave the reader as `Reading::account` and are shown to the person by `usage/read`; its picture never does.
- **An agent entry with `profiles`** runs `provider_program launch -- PROGRAM ARGS...` instead, whose first line of standard input the host writes: the profile's environment (see `profile::launch`). The client chooses a profile by name in its first message, `initialize`, under `params._meta["dev.boriken.canoa/profile"]` (`profile::PROFILE_META`); none takes the first. A first message that is not `initialize` (after any worktree requests, which the host answers itself, see "Worktrees") is answered `-32600` (`-32602` when it names a profile), a name the entry does not offer or a value that is not text `-32602`, each logged, and then no reference is read and no process starts; a choice in any later message is answered `-32602` and logged. A reference that cannot be resolved (`from_env` unset, `from_file` unreadable) answers `-32603` and starts nothing. Each overlay the profile names is read from `overlays/NAME` beside canoa.cfg (4096 files, 64 MiB at most), with no link or excluded name, and must have the digest `overlays/NAME.json` records; else it is left out and reported.
  An overlay is read whole once per process and kept while its record's digest and every file's path, size and modification time stay as they were; the interpreters hooks run with are looked for once per `PATH` and `PATHEXT` value (looked for again when one has gone), and what a killed host left in the temporary directory is swept once per process, on a thread of its own. A skill an overlay names from elsewhere is delivered like a bundled one only from what the app fetched, which the host never fetches itself: `overlays/.skills/LOWERCASE-NAME/` (the files its tree digest covers, 1024 files and 16 MiB at most) and `overlays/.skills/LOWERCASE-NAME.json` (`name`, `source`, `digest`, `overlays`, ...). It is used when the record's `name` is the skill's, its `overlays` lists this overlay, for a source entry its `source` is the entry's and the entry's `pin` (if any) and canoa.cfg's `[skill_pins]` entry for the name (if any) are both its `digest`, the record is a JSON object of at most 64 KiB, neither it, `.skills` nor the skill's directory is a link, the files have exactly that digest, and they pass `coqui_aos::read_fetched_skill` (a `SKILL.md` with YAML front matter naming it).
  Otherwise it is not delivered and the report says why: `not supported` with `from SOURCE, not fetched` or `a named skill; no catalog resolved it here` when nothing applies, `refused` when a record or the files do not check. The skills of all the profile's overlays are planned together (`coqui_aos::resolve_skills`, no catalogs): a skill from elsewhere never takes a name another overlay's skill holds, whatever its overlay's `priority`; one kept out is reported `refused` under `skills.NAME` with its overlay, a name more than one overlay offers under `skills.NAME.collision` with the overlay delivered, and a delivered one from plain `http`/`git://` or a private network address under `skills.NAME.insecure-transport` or `skills.NAME.private-source`. A delivered skill with no pin, from the overlay or `[skill_pins]`, is also reported under `skills.NAME.unpinned`, and one whose front matter has keys beyond `name`, `description`, `license`, `compatibility` and `metadata` under `skills.NAME.skill-keys`.
  A client may also narrow the overlays one connection starts with, by `initialize`'s `_meta["dev.boriken.canoa/overlays"]` (`profile::OVERLAYS_META`), a list of names (anything else is `-32602` and logged): only the profile's overlays among them are read, each other the profile lists is reported `off` under `overlay` ("not chosen for this session"), and a name the profile does not list adds nothing and is reported `not supported`. The person's own layers and the agent's are never narrowed.
  The agent's `initialize` answer decides the harness (from `agentInfo.name`, else an entry named `Claude`, `Codex`, `Gemini`, `Antigravity` or `Pi`) and what it takes (`systemPrompt`, `additionalDirectories`, MCP transports, by ACP v1 or v2 capability paths); then every `session/new`, `session/load` and `session/resume`, after the scope above, gets the context as `systemPrompt` (`append`, before a client's own blocks), the MCP servers in `mcpServers` (v1's stdio form untyped; a client's server of a name the profile holds, started or not, is `-32602`), skills written once per connection to a private temporary directory (removed after the agent ends) as the Claude plugin `canoa-profile` in `_meta.claudeCode.options.plugins` or a directory Codex or Antigravity (`agy acp`, `agentInfo.name` `Antigravity ACP Server`) reads (its `skills` folder under the Agent Skills directory inside) in `additionalDirectories`; an agent of either that does not advertise `additionalDirectories` is `not supported`.
  How an agent is given its skills and its hooks plugin (a local plugin loaded through `_meta`, an additional directory, or not at all), what its own hooks give for the events ACP does not show, and which table of words says what became of the access are the agent's own answers to `agent_vendor` (`skills_delivery`, `hooks_delivery`, `hook_support`, `access_target`); the host holds none of them. A session request before `initialize` is answered `-32600`. A stdio server's `command` goes absolute: as written, from its layer's directory when it holds a separator, else the first match on the host's `PATH` (absolute entries only; `PATHEXT` on Windows), refused when none is found. An overlay's MCP server starts only when `allow_mcp` names it at its digest (`sha256` of `{"layer", "server"}` as the view writes them, and `"program"`, the stdio program found); off, it is logged with that digest. The answer to `initialize` and to each session request carries `_meta[PROFILE_META]` = `{"name", "harness", "summary", "items": [{"key", "layer", "state", "how", "digest"?}]}`, `state` being `applied`, `not supported`, `off` or `refused`: names, never values. No project profile is read.
- **What a harness entry is given is what its provider declares.** `serve::harness_settings` puts the access, `allow_client_access`, `allow_bypass`, `modes` and `setting_sources` into a harness's settings only where the provider's settings schema declares the key (`kind::declares_setting`; `vendors::bundled_declares` for the bundled ones), so a provider that runs a stdio agent as it is gets the program and the limits of a connection and nothing more. The per-agent answers beyond a description (an account's variables, a login's file, a shell word, why skills are not taken, the sessions a program kept) are `AgentVendor` methods asked through `vendors::behave(agent, ..)`, which reaches the bundled agents' providers; an agent a library from canoa.cfg adds is described by `describe` and answers none of them.
- **A harness entry** runs an `acp_harness` provider, chosen by its id, in this process for each connection, over the same channel and scope as an agent entry. `bind` gives each entry a registry of its own: `claude`, `codex`, `pi` and `opencode` (coqui-acp-claude's, coqui-acp-codex's, coqui-acp-pi's and coqui-acp-harness's stdio providers, compiled into the host and registered with `local_providers!`) for an entry with no `library` or `source`, and only what the entry's file offers for one that has it (config refuses an origin on `claude`, `codex`, `pi` or `opencode`), the way a provider entry loads it but in this process, not a process of its own; it then builds each entry's instance from the entry's settings, which the provider checks against its schema (`ServeError::Harness` names the entry and the reason, no value).
  A connection starts with `StartRequest` (the entry's `working_roots`, which hold a session and a resumed Codex thread; with a profile also the profile's environment and, when the entry has roots, the directory the connection's skills are written under, `Connection::skills`; an entry with no roots gives none), the host's `LocalSpawner` (the provider starts its program as this host's child, ended with everything it started when the connection or the host ends), a sink that hands the provider's messages to the client (no keeper: the harness reports no account's renewal, the account provider's watch does), and the cache lifetime the connection asks: the client's choice for the session in `initialize`'s `_meta` (`CACHE_META`), else the entry's `cache_lifetime`, else the client's default for its kind of session, else the provider's own (`default`). Claude Code's provider sets `CLAUDE_CODE_PROMPT_CACHE_TTL` and `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` to `5m` for `short` and `1h` for `long`; Codex's says it ignores it (`canoa options` prints each provider's sentence as `cache_lifetime`, and an entry's own setting as `cache_lifetime_setting`).
  With a profile the host builds a second instance with `allow_client_plugins = true` where the provider has that setting (Claude Code's), for the one plugin it writes. `stop_agents` closes every connection at once, which makes each provider close its sessions and end each command line with what it started, waits for no client that has stopped reading, and returns once each provider has said `closed` or after 10 s each. A provider that ends the connection with a failure ends it, and the reason is logged at `info`. How the built instance departs from its schema's defaults (Guatiao's `schema::differences`) and the provider's `non_defaults` are logged at `info` as `non-default: host.agents.NAME: SETTING is VALUE, default D`, so `settings = { allow_bypass = true }` is logged as `bypass = true` is. The host sets `max_requests` to 64 for `claude` and `codex` unless `settings` say another.
  A provider's notices (a version it was not tested with, a failure of its plumbing, the end of its program mid-session, how and never what it last wrote) come through the spawner's `notice` and are logged at `info` with the entry and the kind (`notice`, `exited`, `fault`); so are its own `closed` status and reason. The `mode` option offers every mode the agent has, Bypass included, unless the entry's `settings` name `modes` or `allow_bypass`: a paired key is the person's own, and the access a session runs with is its profile's (the standard access when the entry offers none). A `settings` value for either is logged at `info` as configuration.
- A profile reads an agent's `initialize` answer where its version puts what it says: `capabilities` and `info` in version 2, `agentCapabilities` and `agentInfo` in version 1. `coqui-acp-claude` is Claude Code and `coqui-acp-codex` Codex.
- A tool entry is served as an agent entry whose program is `provider_program` itself: `provider_program tool --name NAME --spec JSON`, the entry as `ToolSpec` serializes it. So the scope above applies to its clients, and the process, with every tool process it starts, ends with the connection.
- A provider entry is not filtered: its facade reads the client's `_meta` launch values (`context`, `model`, `effort`, an opaque `meta`) and hands them to the provider, and refuses an environment name. What a provider does with them is the provider's.
- A provider entry runs `provider_program provider (--library L | --source S) --provider ID --max-sessions N --directory D --settings-on-stdin [--import-search library|path] [--working-root R]... --connect A`, so a library or source is loaded only in that connection's process, which runs in `D`. The command line holds paths, names and the address only. For each connection the host listens on a loopback port of its own, `A`; writes the entry's `source_settings` and `settings` and a one-time token of 32 random bytes as the first line of the process's standard input (`HostLine`), then closes it; and takes the first connection to `A` that sends the token within `START_LIMIT`, up to 8 that do not. ACP runs on that socket alone. What the process writes to standard output or error goes to the host's standard error, `OUTPUT_LIMIT` bytes per connection in all, the rest read and dropped after one warning; none of it reaches the client. The process and what it starts are ended with the connection, by job object on Windows and process group elsewhere. Its facade refuses any `mcpServers` and checks `working_roots` itself.
- On Windows a source entry whose `import_search` is `path` is logged as `bind` binds it: at `info` as `non-default: host.providers.NAME.import_search is path, default library: …` when the file names it, at `warn` as `host.providers.NAME.import_search is path, because import_dirs names no directory: …` (saying to set `import_dirs` or `import_search = "library"`) when the host took it as the default. `Origin::Source::import_search_named` tells the two apart.
- A provider entry whose `source_settings` hold `isolation = "inherit"` is logged at `info` as `bind` binds it: `non-default: host.providers.NAME.source_settings.isolation is inherit, default shipped`. No other source setting is judged.
- `max_peers` connections per entry at once; past it a proven peer is turned away. Past `MAX_UNPROVEN` handshakes at once across entries, a new connection is dropped.

## Shared sessions (`shared = true`)

An agent or harness entry with `shared = true` keeps each session's agent running in the host, held by coqui-acp's `coqui-acp-hub`, so a session outlives the connection that opened it and several clients take part in it. An entry without it is served as before: one agent per connection, ended with it.

- **Opening.** The first client of a session speaks to the agent as it does on an unshared entry (`initialize`, `authenticate`, `session/new` or `session/load`, with the profile and layers it always gets); once the agent has answered the one that opens the session, the host's hub takes over that client and every later message goes through it. One connection serves one session: a second `session/new` on it is refused (open another connection).
- **Attaching.** A connection whose first message is `initialize` while the entry has a running session is answered from what the agent offered (`loadSession` and `sessionCapabilities.resume` on); then `session/load` or `session/resume` naming a running session of that entry attaches to it, an extension request (a method starting `_`, such as the usage an app asks for once connected) sent before that is answered with an error and the connection goes on, and anything else opens a session of its own. `session/load` replays everything the hub retained (from `_meta["dev.boriken.coqui.acp/hub"].cursor`, an opaque value taken from an earlier message's `_meta[...].seq` or an earlier answer's `cursor`, only what follows it), answers `{ _meta: { <key>: { cursor, truncated } } }`, then asks again any permission request still open. Updates that happened before the first client's `session/load` of an agent's own history are not in the replay (they went to that client directly). A key already attached takes over its own earlier connection.
- **Surviving a restart.** With `shared_keep_log` (on by default) and a home, the host writes each session's log to `<home>/shared_sessions/<hash>.jsonl` as it is logged (a header line naming the entry and the session, then one update a line as the hub fanned it out; owner-only on Unix; rewritten trimmed to `shared_log_entries` and `shared_log_bytes` when it has grown to twice that). A session the person closed, the idle rule ended or whose agent exited leaves no file; one the host's stopping or a crash interrupted leaves it, and it is read for as long as `shared_idle_seconds` from its last write (older ones are removed when the host starts, and when read). The agent is not kept: after the restart the first client to `session/load` or `session/resume` the session by name starts a new agent that loads it, and the hub goes on from the kept log with the cursors unchanged. That client's own request is answered by the hub: the kept log is replayed (after the cursor it names, or all of it), the agent's own replay of its history is not sent (the log holds it), and the answer is the agent's result with the hub's `_meta` cursor.
  A cursor the log cannot continue from (`cursor_ahead`, `cursor_expired` or `bad_cursor` in `error.data.reason`, code -32602) is answered with an error and attaches nothing, to any client; the client loads again with no cursor. With no kept log (`shared_keep_log = false`, no home, or none for that session) the first client back is given the agent's own history as before, its cursor is not consulted, and the log starts past every cursor an earlier log can have issued (the time in milliseconds), so a later client holding an old cursor is refused with `cursor_expired` instead of being replayed from the wrong place. Only the log is kept: the running turn, queued prompts and open permission requests are not.
- **Taking part.** Every attached client gets every update, a prompt is stamped with the client that sent it (`_meta[...] = { client, label, prompt }`) and queued behind a running turn, a permission request goes to every attached client and the first answer wins (the others get `_dev.boriken.coqui.acp/hub_permission_closed`), `session/cancel` from any client cancels the turn, presence is `_dev.boriken.coqui.acp/hub_presence` (each client is sent the list with its own entry marked `"self": true`). A client's id is its key's id, its label the entry's name, its role `operator`, its subject `owner` for this host's own key and `key:<id>` for any other.
- **Who may attach.** The hub's policy is the host's own, asked again at each action: the key must still be paired (`peers` store) and listed by the entry (`peers`), and, to attach, trusted with at least the control grants of the key that opened the session, since the session's tools, secrets and delegation are the opener's. Every key an entry admits and that passes these may read, prompt, answer permissions in and end every session of that entry. A task another agent handed out is never kept.
- **Ending.** `session/close` `{ sessionId }` from an attached client answers `{}` and ends the session. `shared_idle_seconds` (86400; `0` never) ends one nobody is attached to for that long, counted from the hub's `last_activity` (an agent's update, a client's message, an attach or detach); the hub itself never reaps. The agent exiting, or the host stopping, ends it, and the attached clients are told (`_dev.boriken.coqui.acp/hub_ended`); the log of one ended by the host's stopping goes on being kept (see Surviving a restart), that of any other ending is removed. At most `max_peers` sessions of an entry are kept at once (the same bound as connections); a client that stops reading is detached once 256 MiB wait for it.
- **Listing.** `sessions/running` `{}` on the control channel (`ledger.read`) -> `{"sessions": [{"entry", "session", "clients": [{"id", "label", "role"}], "lastActivity", "cursor", "turnRunning", "permissionsWaiting", "title"?, "cwd"?}]}`, newest activity first: the sessions of every shared entry that are open now and that the asking key could attach to under the rules above (an unpaired or unlisted key, or one trusted with less than the opener, sees none of them). `lastActivity` is the host's clock in milliseconds since the Unix epoch, `cursor` the log's head (an attach from it replays nothing), `title` the last `session_info_update` the agent sent and `cwd` the folder its opener named; the app's own link is listed as the host's own key.
- `shared_permission_window_seconds` is the hub's `permission_window_ms`: once a permission request has waited that long with nobody answering, the host logs it at `info` (`has waited for an answer past the entry's window`) and leaves it open for whoever attaches next.
- The hub's notes (a refused action, a permission answered, an unanswered one) are logged at `info` with the entry; nothing is auto-denied. Two sessions of one entry whose agent gave the same id are both kept, but only the older can be attached to.

## A transport provider (`transport = "<id>"`)

An entry listens through a provider of coqui-transport-guatiao's `transport` kind when it names one: `transport = "pipe"` or `"websocket"` (compiled in, registered in a registry of the entry's own) or the id of an outside provider that `transport_library` or `transport_source` loads, into a registry of its own too, so an id is resolved from that entry's own file and no other (`ServeError::Transport` names the entry; its words quote no setting's value). `transport_settings` is the provider's configuration, checked against its schema first. With no `transport` key nothing changes: `listen` is an address, `pipe:NAME` or `unix:PATH` as always.

- `bind` starts the listener, so a refused configuration, an endpoint the provider cannot read or one that is taken stops `serve` there, and `Listening::url` is the endpoint the provider says a peer can dial (a port asked for as `0` is the one the system chose). The provider's own `non_defaults` are logged at `info` as `non-default: host.agents.NAME.transport has SETTING at VALUE, default DEFAULT`, and an outside provider's code loading into the host's process is logged too.
- Each connection the provider hands over is a `coqui_transport::Channel` the host's proof runs on, as on a socket: the same trust store, `peers`, `max_peers` and 64 unproven connections shared with the sockets, every message after the proof sealed. Stopping the host closes the listener and waits (up to 5 s) for the provider to say it has stopped, so the endpoint is free when `run` returns. Peers wait for the accept loop in a queue of 16 and past it are turned away; a connection holds at most 64 messages for the host, and a message over the limit in force (`set_max_message`: the proof's size until the proof is done) ends it. The provider's own message limit applies as well, so an outside provider that takes less than the sealed session's records fails the session.
- What the transport is, not the host, decides the framing, who can reach it and the wire: the built-in `pipe` frames with a big-endian `u32` (the entry's `listen = "pipe:NAME"` frames little-endian, so a client of one is not a client of the other); the built-in `websocket` sends text messages unless `listen.frames` is `"binary"`, which the proof needs, and it takes the host's `[host] origins` as its `listen.origins` when the entry lists none (logged; an entry's own list replaces them), and listens beyond loopback only with `listen.plain_beyond_loopback` in `transport_settings`, which the host logs, the link being sealed after the proof as on any address. Each upgrade runs on a thread of its own, at most `max_handshakes` (default 64) at once, so a silent peer delays nobody. The built-ins cap a message at 1 MiB (the `channel.max_message` of `pipe`, `listen.limits.max_message` of `websocket`), below the sealed session's 16 MiB records: raise it in `transport_settings` for an entry that carries more. Two entries cannot name one endpoint; endpoints asking for port 0 are not one. A web page is never offered such an entry: `Listening::on_address` is false.
- Only the entries' listening goes through a provider. Dialling (`a2a` sources, delegation), `wss://` and WebTransport do not: they wait for the kind to carry TLS configuration.

## A pipe or Unix socket (`canoa_host::pipe`)

```rust
pub use coqui_transport_pipe::{Error, Listener, PipeName, Stream};
#[derive(Debug)] pub struct PipeChannel;   // Send, Sync; coqui_transport::Channel
impl PipeChannel {
    pub fn new(stream: coqui_transport_pipe::Stream, max_message: usize) -> PipeChannel   // a connected stream
    pub fn connect(name: &PipeName, max_message: usize) -> Result<PipeChannel, Error>     // a client; Error::NotListening / AccessDenied / TimedOut
    pub fn peer(&self) -> io::Result<coqui_transport_pipe::OsIdentity>                    // who the system says is at the other end
}
```

- An entry whose `listen` is `pipe:NAME` or `unix:PATH` is served as one on an address is: a fresh agent per proven connection, the same proof of the host's method, the same trust store (a key that is not paired is turned away and waits for `canoa accept`), `peers`, `max_peers`, worktree requests and the 64 unproven connections at once, shared with the sockets. Nothing differs after the connection opens.
- What differs is the transport: the operating system's access control stands before the proof, and `coqui-transport-pipe`'s defaults are kept (Windows: a security descriptor for the current user alone, plus the integrity label of an elevated host, the first instance of the name taken so nobody else holds it, remote clients refused; Unix: a `0600` socket in a directory only its owner (or root) can write, a stale socket replaced and a live one not). Neither replaces the key proof, and the proof does not trust the access control: the same user's other processes reach the pipe, and so would anyone the descriptor let in. The peer's process and user are logged at `debug`.
- A message is a little-endian `u32` length and then its body (coqui-transport-web's length-prefixed stream format), with no WebSocket handshake and no origin check. `PipeChannel` reads on demand with no read-ahead, so a bound `set_max_message` changes applies to the next message the peer sends. Zero length, over the bound, or a peer that leaves mid-message ends the channel (`Failure::Protocol` or `PathLost`); a clean end between messages is `Ok(None)`. A write that times out ends the channel (a cancelled pipe write on Windows leaves the stream's position unknown).
- Every peer on pipes shares one bucket of the trust store's waiting queue, since there is no address to tell them apart by.
- The served web page never offers or allows a pipe entry: `/canoa.json` and the page's Content-Security-Policy leave it out (`Listening::on_address`), and no browser can reach it.
- A pipe name on Windows is visible to every user: the first instance is taken at bind, so a second host on one name is `ServeError::Pipe` (`NameTaken`), but a client that connects before any host bound reaches whoever bound first, and only the key proof tells it from the host.
## The browser extension's native host (`canoa_host::native`, `[host.native]`, `canoa native`)


- The browser starts the native host with the extension's origin as its first argument (`chrome-extension://ID/`, then `--parent-window=N` on Windows): `main` turns that into the hidden `canoa native-host ORIGIN`, which is `relay` on standard input and output. On Windows the browser runs it through `cmd.exe /d /s /c` with named pipes for standard streams. One port is one link: the relay ends when the browser closes its input or the door closes.
- **Native messages** (a `u32` in native byte order, then JSON; to the browser at most 1 MiB, from it at most 1 MiB plus a little): `{"op":"hello"}` answers `{"reply":"hello","running":true,peer,method,name,version,entries:[{name,label,kind,local}],control,web?,hostname?,addresses}` from the host's door (`web` the origin of `[host.web]`, `http` or `https` by its certificate, with loopback for an unspecified address, left out when the port is the system's to pick; `hostname` this computer's name in lower case, `hostnames` that and its DNS name when the system gives one, `addresses` up to 16 of its network addresses, never loopback or link-local: what the extension counts as "on this computer", beside loopback; a claim that only narrows what a page may do, and given by the stopped relay's `hello` too), or `{"reply":"hello","running":false}` (`"door":false` when a host holds the home with its door shut). `{"op":"open","entry":NAME}` (an entry, `@control`, or `@pair`) answers `{"reply":"open","opened":true}` or `{"reply":"open","error":...}`; after it only `{"d":BASE64}` pieces go either way, and `{"closed":true}` ends the link.
  `{"op":"discover","seconds":N}` searches itself, whether or not a host runs, and answers `{"reply":"discover","candidates":[...]}` as `discover/nearby` does (below), or `{"reply":"discover","error":...}`; it needs no key, since the browser that may start the program is the one the install allowed, and what it returns is claims. `{"op":"start"}` runs `launch.json`'s program, detached (`DETACHED_PROCESS`, plus `CREATE_BREAKAWAY_FROM_JOB` where the browser's job allows it; a new process group on Unix) and only when no host holds the home; it answers `{"reply":"start","started":PID}` or an error. Anything else is `{"error":"unknown op"}`.
- **The door** (`serve::door`) is bound by `Serving::bind` in the home (`ServeOptions::state_dir`), unless `[host.native] enabled = false`, a portal, or no state directory. A connection's first message is `{"canoa_native":1,"open":NAME,"origin":ORIGIN}` (at most 64 KiB, within 5 s); `@hello` is answered and closed (once the web server is bound, `Serving::note_web` adds `"web_app": {"url", "office", "office_local"}` to that answer, `url` being `WebServer::local_url`: loopback named `localhost`; the Office COM add-in finds the chat there with no address configured), anything else is answered `{"opened":true}` and then served as `connection` serves any link: the proof of the host's method, the trust store, the entry's `peers`, scope and `max_peers`. `@control` is the control channel with `[host.native] control` for every paired key: through the door that set replaces whatever grants `[host.control]` gives the key. `@tools` is where a program offers its tools to the host's sessions (**Tools a program offers**, below): only a key the extension's PIN pairing bound to its origin, and holding `tools.provide` in that same set, is let in, and one without the grant is refused with `{"type":"refused"}` without it. A door that cannot be bound is logged and left out, and why is written to `<home>/native/door-error.txt`, which a relay's `hello` (`"door":false,"why"`) and `canoa native status` (`door_error`) say.
  Unproven connections count against `MAX_UNPROVEN`.
- **Office tools of a page's session**: a session request a web page made gets no tool servers, except the Office providers (`outlook`, `word`, `excel`, never `browser`) that `_meta["dev.boriken.canoa/site"].tools` names, and only on a link that is the extension's own (the native door, with the key its PIN pairing bound to the extension's origin); on any other link the field is ignored. The extension also sends `pane`, a token (8 to 64 hexadecimal digits) of the pane's tab, which `@tools` repeats as `session.pane` in the provider's `open` message so a provider can answer a session from the pane that opened it.
- **`[host.native]`**: `enabled` (default true) and `control`, a list of grant names (default `ledger.read`, `ledger.write`, `worktree`, `store.read`, `folders`, `config.read`, `config.write`, `discover`, `tools.provide`). `config.write.sessions`, `overlay.write`, `host.restart`, `upload`, `files.write`, `files.write.host`, `terminal`, `voice.setup` and `hosting` are refused there. `store/index` is served by `overlay.read` (the catalog entries) and `store.programs` (the program entries), neither in the default list: the extension reads the catalog index only when `control` names `overlay.read`, and a `refresh` it asks for is refused, since it needs `overlay.write`.
- **The door's other end:** a relay speaks to the door only when the system says the server end is held by the user it runs as (the pipe's owner on Windows, the peer's credentials on Unix); one it cannot place is not spoken to. A record of origins (`origins.json`) that exists and cannot be read allows no key through the door, and `record_origin` will not write over it; a pairing that cannot record its origin takes its key back out of the trust store.
- **Pairing**: `canoa pair --native [--until-stdin-closes] [--method M]` binds `pair_door_name`, prints `{"pin","peer","method","native":true}`, takes one connection at a time that asks for `@pair`, runs the PIN pairing on it, records the origin the browser reported beside the key (`<home>/native/origins.json`) and prints `{"paired":PEER}`. The door then turns that key away from any other origin; a key with no record (`canoa accept`) is bound to none. The host never holds a PIN, so pairing works with the host stopped.
- **Registration** (`canoa native install [--name NAME] [--extension-id ID]... [--browser chrome|edge|chromium|chrome-for-testing]... [--profile DIR]... [--launch PROGRAM [-- ARGS...]]`, `uninstall`, `status`): `dev.boriken.canoa` (`--name` registers another name the extension does not look for, for trying a registration), `type stdio`, `path` the running executable, `allowed_origins` `KNOWN_EXTENSIONS` plus the given ids. Windows: the manifest at `<home>/native/NAME.json` and `HKCU\Software\{Google\Chrome,Chromium,Microsoft\Edge}\NativeMessagingHosts\NAME`. Linux and macOS: `NativeMessagingHosts/NAME.json` in each browser's profile directory that exists, and in each `--profile`. `--launch` (default this program's `serve`) is recorded in `<home>/native/launch.json`; `status` prints `{name,registered,launch,running,holder}`. Flatpak and Snap browsers cannot start a native host: not handled.

- `bind` refuses plain HTTP beyond loopback (`PlainBeyondLoopback`), a zero limit but `immutable_age` (`Limit`, naming the canoa.cfg setting), a `connect` source of another form than the file allows (`Connect`), an `office_frames` source that is not one `https` origin (`OfficeFrame`), a directory that cannot be resolved, holds no `index.html`, or is or holds one of `keep_out` once resolved (`Site`), and no directory in a build without `web` (`NoSite`); reads `cert` (every PEM certificate, in order) and `key` (one PEM private key) into a rustls server configuration with its safe default versions (TLS 1.2 and 1.3), the `ring` provider, ALPN `http/1.1` and no client certificate (`Tls`, naming the file, never its contents); and logs at `info` each limit above its default as `non-default: host.web.SETTING is V, default D`, a `listen` beyond loopback, and each `connect` source as `non-default: host.web.connect lets the page connect to SOURCE…`; on Unix a `key` file others may read is logged at `warn`, since nothing in the file asked for it.
  Plain HTTP beyond loopback stays refused: the page is not sealed like an entry's link, so whoever is on the path could rewrite the code that holds the person's key. Then it binds (`Listen`). The site's directory is resolved once, at `bind`.
- HTTP/1.1 and 1.0, `GET` and `HEAD` only (else 405 with `Allow: GET, HEAD`). Refused with 400: a request with a body (`Transfer-Encoding`, more than one `Content-Length`, or one other than 0), no `Host` or two (HTTP/1.0 included), a target that does not start with `/` (absolute-form included), anything `httparse` refuses. A `Host` that is not `localhost`, an IP address or one of `hosts`, with any port, is refused with 421, which stops a page of another site reaching this one by DNS rebinding. More than 64 headers or `max_request_bytes` is 431; a head not complete within `request_time` is 408. Every refusal closes the connection.
- **Paths.** The target's path (the query left out) is split at `/` and each segment percent-decoded; refused with 404 is any segment that is empty (but a last one), `.` or `..`, starts or ends with a dot, ends with a space, holds a control character, `/`, `\`, `:`, `*`, `?`, `"`, `<`, `>` or `|` once decoded, is not UTF-8, or is a Windows device name with any extension (`CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `CLOCK$`, `COM` or `LPT` and a digit or `¹`, `²`, `³`). The file is the resolved path (every link followed) under the resolved root, each segment of which, once resolved, must pass the same rules: one that resolves outside the root, or to a name a request could not give (an NTFS short name such as `GIT~1` resolving to `.git`, a link to a dot-name), is refused with 404 and logged, whatever it is, and a directory is never listed. From the site built in, the path is looked up as written.
- **The app's routes.** A path naming nothing, or a directory, whose last segment has no `.` is answered with the root's `index.html` (200, `no-cache`); any other missing file is 404.
- **The Office add-in's routes** (`[host.web] office = true`; with it off `/office/...` is an ordinary path and nothing below applies).
  The host carries the add-in's task pane (the page that loads Office.js and frames the chat-only app), its dialog page and their scripts, and answers exactly these paths, each with the policy it needs and no other route changes: `/office/taskpane.html` (`script-src` and `connect-src` are `'self'`, and add `https://officeapis.public.onecdn.static.microsoft` only in a build made with `CANOA_OFFICE_JS=cdn`; `frame-src 'self'`; `frame-ancestors` is `https://outlook.office.com https://outlook.office365.com https://outlook.live.com https://*.office.com https://*.cloud.microsoft` and `office_frames`; no `X-Frame-Options`), `/office/dialog.html` (`script-src` and `connect-src` as the task pane's; still `frame-ancestors 'none'` and `X-Frame-Options: DENY`; no `Cross-Origin-Opener-Policy`, so Office's dialog keeps its link to the window that opened it), `/office/taskpane.js`, `/office/relation.js` and `/office/dialog.js` (the usual headers), `/office/js/<file>` (Office.js and the files the pane loads, and `/office/js/LICENSE.md`, from the deps mirror's copy of OfficeDev/office-js, the usual headers and `Cache-Control: max-age=3600`; none in a `cdn` build;
  the repository's telemetry and sign-in files are not carried), `/office/app/` (the site's `index.html` under the usual policy, `script-src` unchanged, with `frame-ancestors 'self'` and the same origins and no `X-Frame-Options`: the page the task pane frames, `?mode=chat&relation=<kind>:<key>&label=` as the app reads them) and `/office/icon-16.png`, `-32`, `-64` and `-80` (the site's `icons/Icon-192.png` with `Cross-Origin-Resource-Policy: cross-origin`, as Office draws it from its own origin). Every other path, `/office/app/deeper` and `/office/other` included, is the site's and has today's headers. Microsoft publishes no list of the origins that frame a task pane: the built-in ones are a starting list to check against each client, and Word, Excel and PowerPoint on the web (SharePoint, `officeapps.live.com`) are named only through `office_frames`. `/office/app/canoa.json` is `/canoa.json` for the app page that asks for it beside itself. The add-in's manifests are rendered by `clients/office/render.mjs`. The portal answers the same routes itself with `office = true` in its own settings (below); with it off it answers none of this.
- **The add-in on this computer** (`[host.web] office = true` and `office_local = true`, `listen` on loopback, normally with a `cert` and `key` the person names, since Office wants HTTPS). The page the task pane frames needs no PIN and no `canoa accept`: after its key has connected once and been turned away, it sends `POST /office/admit?peer=<id>` (empty body) and the host accepts that waiting key (`TrustStore::accept`), then holds it as a page's key for this run: on the control channel it holds `[host.native] control` besides its own grants (and the sessions it starts are given the tools its grants allow: the same set plus `mail` when `[host.mail]` names an account and its tools are on), and `restricted` no longer turns it away from `@control`. `/canoa.json` names the path as `admit` only to a request whose `Host` is a loopback name.
  The request is refused (`403`, `Cache-Control: no-store`) unless it comes from a loopback address, its `Host` is a loopback name, its `Origin` is exactly the scheme and `Host` of the request and `Sec-Fetch-Site`, when sent, is `same-origin`; `404` for a key that never connected, `403` for one the trust store knows connected from another address, `400` for no id or one that is not an id. Without `office_local`, `POST` is `405` as ever and `/canoa.json` has no `admit`. What stops others: a page of another origin cannot send that `Origin`, a name pointed at this computer fails the `Host` check, and a key the host never saw connect is not accepted; a program on this computer, or another account's on a shared computer, can send any header and so can ask for a key it has just connected with (see `clients/office/README.md`).
  The admitted keys are kept in `<home>/office/admitted.json` (`{"secret": bool, "keys": [ids]}`, written on each admission) and read when the host starts: a key the trust store still accepts is held as a page's key again at once, with its control grants, so a restart needs no new request; a file that cannot be read holds none, and one written without the secret is not read once `office_secret` is on. **`office_secret`**: `<home>/office/secret` (64 hexadecimal digits, made on first use, mode 0600 on Unix) must be sent as `X-Canoa-Office-Key` on `POST /office/admit`, every `/office/tools/` request and `POST /office/launch`, compared without branching on how much matched; a request without it is `403` saying the add-in's secret is needed. `web::Secret` is the file's reader; the manifest carries it as `?office_key=` (`clients/office/render.mjs --secret-file`), the pane passes it on in the frame's address and the app sends it with its admission request.
  **The pane's tools** (`web::Tools`, `/office/tools/`): with `office_local` the web server registers the open Office application as a provider of the host's `@tools` (`outlook`, `word` or `excel`, so `canoa-outlook`, `canoa-word`, `canoa-excel`; see "Tools a program offers") on a `Local::open("@tools")` link, carried by the page's own requests, each the page's own as for admission (loopback address, loopback `Host`, its own `Origin`, `Sec-Fetch-Site` `same-origin` when sent, the secret when asked for): `POST open?app=NAME` registers and answers `{"session"}` (`409` with the host's reason when refused, `400` for another name; a newer pane of the same application replaces the older), `GET poll?session=S&after=N` waits up to 20 s and answers `{"first":F,"messages":[...]}` (the host's `open`, `mcp` and `close` messages, as on the door, message `i` being number `F+i`; the host numbers what it sends a pane from 1 and keeps each message until a poll names a number at or past it as `after`, so a poll whose answer the browser dropped is followed by one that gets the same messages again, answered at once when any are held; `after` absent is 0, one that is not a number is `400`;
  at most 256 messages or 16 MiB are kept, the oldest going first; one poll of a pane takes from its link at a time, a later one waiting behind it; a link that ended answers what is held first, then `410`; `410 {"ended":true}` when the session is gone), `POST send?session=S` takes one provider message as its body (`mcp` or `close`, at most 4 MiB; the only request this server reads a body of), `POST close?session=S` ends it. A pane that makes no request for 45 s is closed by a thread that looks every 5 s, which takes its tools from every session. The host answers a provider server's `initialize` itself and, for `outlook`, adds `instructions` in its own words (`client_tools::instructions`: ask `outlook_open_item` which message is open, then `mail_related` with its Internet message id as `message_id`, and treat what comes back as data); no provider's text is ever passed to the model as instructions, which is why the open message reaches the agent as a tool's answer and not as a line the pane sends. The page's own connection still never opens `@tools` by key: only this route, on this computer, does.
  **The launcher** (`canoa office-launcher`, `canoa_host::launcher`): holds `[host.web] listen` while `Home::probe` finds no host (after four looks half a second apart), serving only `WebServer::bind_launcher`: `GET /canoa.json` and `/office/app/canoa.json` answer `{"launcher":"/office/launch"}`, `/office/taskpane.html` the page `launch.html` (under the pane's policy), its scripts, and `POST /office/launch` (the page's own checks) asks it to start the host: it lets go of the address, starts what `native install` recorded in `<home>/native/launch.json` (else this program with `serve`) detached, and waits up to a minute for a host to hold the home. It lets go of the address within a look of a host taking the home, and `WebServer::bind` on a host with `office_local` waits up to five seconds for an address another program holds.
  The launcher is never started by the host or the app; the person starts it, or registers it with `canoa office-launcher --install`, which writes one entry in the place this system reads for the signed-in user and no other: the value `CanoaOfficeLauncher` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (written through `reg.exe`), `~/Library/LaunchAgents/dev.boriken.canoa.office-launcher.plist` (`RunAtLoad`), or `$XDG_CONFIG_HOME/autostart/dev.boriken.canoa.office-launcher.desktop` (else `~/.config/autostart/`), with no elevation and nothing started at once. The entry runs this program (the `Front`'s `program`, its leading arguments too, as `launch_of` uses them), `office-launcher` and, when a config was named (`--config` or `CANOA_CONFIG`), `--config` with each file made absolute (a leading `+` and the list separator kept); it refuses a canoa.cfg with no `[host.web]` having `office` and `office_local`.
  `--install` again replaces the entry, `--uninstall` deletes only it (no error when it is absent), and `--status` prints `registered`, what the entry runs, whether that is what `--install` would write now (`current`), the address, whether something accepts a connection there (`answers`), whether a host holds the home (`host_runs`) and `launcher_answers` (answers and no host holds the home); `--format json` prints one object of those. On Windows `canoa.exe` is a console program, so the launcher's window stays open while it runs.
- **`/canoa.json`** (`HOST_INDEX`, the query left out, before any file of that name): `{"peer", "method", "os", "web", "entries": [{"name", "kind", "url", "harness"?, "title"?}]}`, the host's id, method, operating system (`windows`, `linux`, `macos`), `web` (`local` when the person sits at this computer, `remote` when the browser is only the interface: `[host.web] mode`, else by the request's `Host`, loopback being local; an editor or file manager is started on the host in local mode, and offered as a Remote-SSH link in remote) and each entry as `serve` prints it (the control channel too, kind `control`, when it listens on an address; a page needs its address to reach the ledger, folders and uploads), `Cache-Control: no-store`. It names the host for a page to fill in; it proves nothing, and connecting still runs the proof both ways and needs the page's key accepted.
- **Headers on every answer**: `Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; media-src 'self' blob:; connect-src 'self' URL...; worker-src 'self' blob:; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'none'; frame-ancestors 'none'`, the `connect-src` naming each entry's `url`, then each `connect` source; over HTTPS, to a request naming one of `hosts`, `Strict-Transport-Security: max-age=31536000` (never to `localhost` or an address, which other servers share); `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Date`, `Connection`.
  A file carries `Content-Type` by its extension (`application/octet-stream` when unknown), a strong `ETag` (the first 128 bits of the contents' SHA-256, read once while the file's length and modification time stay as they were; the built-in site's are made at build), `Last-Modified` (a directory's files only), and `Cache-Control: public, max-age=IMMUTABLE_AGE, immutable` when its name holds a hash (a part of 8 or more hex digits after the first, split at `.`, `-`, `_`: `main.3f9a1b2c.js`) or a folder on its path is named for a revision (12 or more hex digits and nothing else), else `no-cache`: a folder such as `canvaskit/` carries no version, so it is asked about each time. `If-None-Match` naming its tag is answered 304 with no body and no `Content-Length`; without one, `If-Modified-Since` no earlier than the file's change is too. No range, no compression. The portal answers the same way for the signed-in site, with `private` in place of `public` (`private, no-cache`, `private, max-age=IMMUTABLE_AGE, immutable`).
- **Connections**: one thread each, `max_connections` at once and `max_connections_per_address` from one address (past either a new one is closed unanswered), each ended after `connection_time` whatever it is doing; kept alive in HTTP/1.1 unless `Connection: close`, for `max_requests` requests; the first head must arrive within `request_time` of the connection (TLS handshake included), each later one within `idle_time` to start and `request_time` from its first byte; a write that makes no progress for `send_time` ends the connection.

## One provider on standard streams (`canoa_host::provider`)

```rust
#[non_exhaustive] pub struct ProviderOptions { pub origin: Origin, pub provider: String, pub settings: Option<Settings>, pub working_roots: Vec<PathBuf>, pub max_sessions: usize }
pub fn ProviderOptions::new(origin: Origin, provider: impl Into<String>) -> ProviderOptions   // no settings, any cwd, the facade's default max_sessions
pub fn serve_stdio(options: &ProviderOptions) -> Result<(), ProviderError>
pub fn serve_connected(options: &ProviderOptions, address: SocketAddr, token: &str) -> Result<(), ProviderError>   // loopback only

#[non_exhaustive] pub struct HostLine { pub source_settings: Option<Settings>, pub settings: Option<Settings>, pub token: Option<String> }   // Default, Eq; Debug shows no value or token
pub fn HostLine::to_line(&self) -> Vec<u8>                                           // one line of JSON, no line break
pub fn HostLine::read(input: &mut impl BufRead, max: usize) -> Result<HostLine, ProviderError>   // one line of at most max bytes
```

`serve_stdio` loads the code, takes the provider, and runs `coqui_acp_provider::AcpFacade` on standard input and output until the client closes them. There, loaded code shares both with the transport: a Python `print()`, or a subprocess that inherits them, writes into the client's ACP stream or takes its messages. `serve_connected` connects to `address`, sends `token` and a line break, then loads the code and runs the facade on that socket, so the process's own standard streams are the provider's alone; it is what `serve` runs.

- **A library** is mapped with Guatiao's default import search. On Windows: the library's own directory, the executable's, the system's; not the working directory or `PATH`. Elsewhere the platform's: `LD_LIBRARY_PATH`, the file's run path (its own directory only through `$ORIGIN`), the system's.
- **A source gets the kinds' descriptions.** Every source is added with its `kinds` setting holding, besides any the entry lists, a file of the descriptions of the kinds a script library may serve (`descriptions.rs`: vendor, store extension and program store, `usage_reader` with its reading and process table, the speech kinds, `acp_harness`, the account kinds, `agent_provider`, `transport` and the objects they name), made from the build's own kinds and kept content-named under the temporary directory. A source built from descriptions (JavaScript) refuses a library with `no description of the kind X was given` without it; Python builds its tables from its own typed modules and ignores it. The Canoa SDKs (`bindings/{python,js}/canoa-sdk`) write libraries against them.
- **A source** is added with `settings` as a Guatiao map, then the registry is refreshed once; a library the source refuses is logged and passed over. On Windows the import search is the entry's `import_search`: an import the source names itself that the default search leaves missing (`python3.dll`, for Python) is mapped from the first of `import_dirs` holding it, and with `ImportSearch::Path` else the Windows directory, else **the working directory (canoa.cfg's, under `serve`) or a directory on `PATH`**, in that order; the source is then opened with the default search, so its other imports come from where they did. An import of an import is not looked for. Elsewhere the search is the platform's (`LD_LIBRARY_PATH`, the file's run path, the system's).
- **The provider**: with no `settings`, its own instance; a provider built only from a configuration is `NeedsConfiguration`. With `settings`, an instance built from them: Guatiao checks them against the schema the provider declares, then the provider may refuse them; a provider that is its own one instance is `TakesNoSettings`.

**Loading runs code** with this process's rights, before any check, and trusts whoever can write any file it reads or the directories holding them. For a library, that is the file. For `guatiao_source_py` it is also: the Python whose shared library the loader finds (on Windows the first `python3.dll` in `import_dirs` or the search above, then the `python3X.dll` it names); `GUATIAO_LIBRARY` in this process's environment, which picks the native library Guatiao's Python binding loads; every directory in `paths`; every manifest in `dirs` and `manifests` and every directory its own `paths` names; every module those import; and what the source's `isolation` lets the interpreter read:

| `isolation` | The interpreter also reads |
| --- | --- |
| `shipped` (the source's default) | the standard library and `site-packages` of `home` or the Python found, with their `.pth` files; a `canoa._pth` or `pyvenv.cfg` beside the `canoa` executable (`CanoaUI._pth` beside the app's, when it hosts), and on Windows that executable's directory, which CPython puts on `sys.path`, so whoever can write that directory chooses where modules come from. Not the `PYTHON*` variables or the user's own site-packages. |
| `isolated` | the standard library of `home` or the Python found, and nothing beside the executable, in `site-packages` or in the environment |
| `inherit` | all of `shipped`'s, the user's own site-packages, and the `PYTHON*` variables this process inherits from the host (`PYTHONPATH`, `PYTHONHOME`). `serve` logs it at `info` as configuration. |

`HostLine::read` reads up to the line break and leaves the rest to the transport. The line is `{"canoa_host": 1, "source_settings": {...}, "settings": {...}, "token": "..."}`; anything else, a client's ACP message included, is `ProviderError::HostLine`.

## A tool entry (`canoa_host::tool`)

A command-line tool with no ACP, served as an ACP agent (version 1) by the rules of its entry. No tool has code here.

```rust
pub const NOTICES_META_KEY: &str = "dev.boriken.canoa/notices";
pub const CANCEL_GRACE: Duration = 10 s;
pub const MAX_TEXT: usize = 1024 * 1024;      // text per update; longer is split, a tool_done output is cut
pub const MAX_LABEL: usize = 4096;            // a title, an id, a failure, after control and format characters go
pub const MAX_ASKS: usize = 16;               // permission requests one process may have waiting
pub const MAX_SPEC: usize = 16 * 1024;        // an entry as JSON, since it goes on a command line

#[non_exhaustive] pub struct ToolSpec { pub program: String, pub args: Vec<String>, pub runs: Runs, pub unasked: String, pub prompt: Option<Value>, pub cancel: Option<Value>, pub resume_args: Vec<String>, pub kinds: BTreeMap<String, String>, pub max_sessions: usize, pub events: Vec<Rule> }   // Clone, Eq, Serialize, Deserialize (deny_unknown_fields)
pub fn ToolSpec::check(&self) -> Result<(), String>          // what serde cannot check; names a setting, never a value. Also refuses an entry over MAX_SPEC or holding a NUL, and in `message` mode an argument that is `{prompt}` alone not right after `--`
pub fn ToolSpec::notices(&self, name: &str) -> Vec<String>   // what session/new lists under NOTICES_META_KEY
#[non_exhaustive] pub enum Runs { Session, Message }
#[non_exhaustive] pub struct Rule { pub when: Map<String, Value>, pub send: Action, pub text, id, title, kind, input, output, error: Option<String>, pub status: Option<ToolStatus>, pub stop: Option<Stop>, pub allow, reject, line: Option<Value> }
#[non_exhaustive] pub enum Action { Text, Thought, Tool, ToolDone, Failure, End, Session, Ask, Reply, Ignore }   // TOML: snake_case
#[non_exhaustive] pub enum ToolStatus { Completed, Failed }
#[non_exhaustive] pub enum Stop { EndTurn, Cancelled, MaxTokens, Refusal }
pub fn serve(spec: ToolSpec, name: &str, input: impl Read, output: impl Write + Send + 'static) -> Result<(), ToolError>
pub fn serve_stdio(spec: ToolSpec, name: &str) -> Result<(), ToolError>
#[non_exhaustive] pub enum ToolError { Spec(String), Transport(io::Error) }
```

- **Rules.** Each JSON line the tool writes is taken by the first rule whose `when` paths all hold their values (JSON equality; an empty `when` takes every line). A path is dotted steps of letters, digits, `_` and `-`; a number indexes a list. A line that is not JSON, or that no rule takes, is passed over, and so is every line of a `message` process that a later prompt replaced.
- **Fields per `send`**, each other field refused: `text`, `thought`, `failure`: `text`. `tool`: `id`, `title`; optional `kind`, `input` (a path, its value as `rawInput`, left out over `MAX_TEXT`). `tool_done`: `id`; optional `status` (`completed`), `output`. `end`: optional `stop` (`end_turn`) or `error`, not both. `session`: `id`. `ask`: `title`, `allow`, `reject`. `reply`: `line`. `ignore`: none.
- **Templates.** In text fields, `{path}` is the line's value there: a string as it is, null or missing as nothing, anything else as compact JSON; a `{` not opening a path is kept. In `prompt`, `cancel`, `allow`, `reject` and `line`, every string value is a template, a string that is one placeholder alone takes the value with its type (null when missing), and keys are kept as written. The prompt's context is `{"prompt": text, "session": the tool's session or ""}`; `args` and `resume_args` (`message` only) take the same context; `allow`, `reject` and `line` take the line that matched. Every line written, to the tool or the client, is one line: U+2028 and U+2029 are escaped as `
` and `
`.
- **`kind`**: the rendered text when it is one of ACP's tool kinds (`read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode`, `other`), else its value in `kinds`, else `other`. `check` refuses a `kinds` value that is not one.
- **ACP.** `initialize` answers version 1, no `loadSession`, no image, audio or embedded context. `session/new` needs an absolute `cwd` on this machine (on Windows a drive path; a share or device path is refused before anything looks at it) that is a directory, and `mcpServers` empty or absent (`-32602`), at most `max_sessions` per connection (`-32600`); it answers `{"sessionId", "_meta": {NOTICES_META_KEY: notices}}`. In `session` mode it starts the process there, `-32603` naming the entry when it cannot. `session/prompt` takes text and `resource_link` blocks (a link as its `uri`), joined by line breaks, anything else `-32602`; one turn at a time per session (`-32600`); it is answered `{"stopReason"}` when the turn ends, or `-32603` with the failure's text as `message`. `session/cancel` as below. Everything else is `-32601`; a notification other than `session/cancel` is dropped.
- **A turn ends** at an `end` rule; a `failure` before an `end_turn` makes it fail with that text. A `session` process that exits ends the turn with `-32603` and the session with it: every later prompt is `-32603`. A `message` process that exits ends its turn: `end_turn` (or its failure) on a success status, `-32603` with the status otherwise. A process that closes its output and has not exited within 2 s counts as failed.
- **Cancel.** A cancelled turn is answered `cancelled` however it ends. `session` with `cancel`: the line is written, and a turn still running `CANCEL_GRACE` later has its process ended and the session with it. Otherwise the process is ended at once; in `session` mode the session with it.
- **`ask`** sends `session/request_permission` (v1: `toolCall` `{"toolCallId": "canoa-ask-N", "title", "status": "pending", "rawInput": {"text": the whole question, cut to MAX_TEXT}}`, options `allow`/`allow_once` and `reject`/`reject_once`) and writes `allow` only for an answer selecting `allow` while the turn that asked runs uncancelled; any other answer and an error write `reject`. A request that comes with no turn running, cancelled, or `MAX_ASKS` waiting is refused at once, without asking. When a turn is cancelled or ends, every question of its session still waiting gets `reject` then and is forgotten, so a later answer reaches nothing; so is one whose process was replaced or ended.
- **Processes** run `program` (with `args`; in `message` mode `resume_args` first once a `session` rule has recorded one) in the session's `cwd`, with this process's environment. A line to one goes through a queue of 64; a full queue ends it. Its standard error goes to this process's, `OUTPUT_LIMIT` bytes per process. A line of output over `serve::MAX_LINE` ends it. On Windows each process is in a job object of its own, ended with it, and runs with `NoDefaultCurrentDirectoryInExePath` set, so a `.cmd` tool does not take a program it names bare from the client's `cwd`; on Unix it stays in this process's group, and ending it ends only it. When `input` ends, each process's input is closed, and it is ended 1 s later; under `serve` that does not happen, since the host ends the whole connection's process tree at once.
