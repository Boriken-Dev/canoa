# `canoa-host` delegation, secrets, store tools, and accounts

## Delegation (`[host.delegate]`)

An agent session hands a task to another source. Each task is an A2A task (`coqui-a2a`, `tasks` feature) of the host's one delegation agent, run as a normal host session of that source opened in process with `Local`, whose only prompt is the task text.

```rust
#[non_exhaustive] pub struct DelegateConfig { pub enabled: bool, pub sources: Option<Vec<String>>, pub max_children: usize, pub max_running: usize, pub max_depth: usize, pub a2a: Vec<PeerId>, pub task_bytes: usize, pub result_bytes: usize, pub history_bytes: usize, pub context_bytes: usize, pub wait_seconds: u64, pub dial_seconds: u64 }   // Default, Clone, Eq: `Config::delegate`
pub const DELEGATE_META: &str = "dev.boriken.canoa/delegate";   // the `_meta` key of `initialize` that asks for the tools
```
- `[host.delegate]` keys (any other is refused): `enabled` (true), `sources` (unset: every entry the delegating connection may use; a list narrows it, an empty one allows none), `max_children` per session (8), `max_running` per host (16), `max_depth` (1: a session hands out tasks, a task hands out none), `a2a` (peer ids granted A2A, none), `task_bytes` (65536), `result_bytes` (65536, the most of a reply one `task_status` carries), `history_bytes` (1048576, a task's updates and reply the host keeps), `context_bytes` (32768, the most of a conversation's turns or of its touched files one task may be handed), `wait_seconds` (300, the longest one `task_status` call waits, whatever its `wait_ms` asks; the bridge waits for an answer as long as the call's `wait_ms` and a minute more), `dial_seconds` (20, how long reaching another machine's agent and proving the key may take). No floor and no ceiling; a value away from its default is logged at start.
- Offered only when the client's `initialize` `_meta` carries `DELEGATE_META: true`, `enabled` is not false, and the agent takes an MCP server: over HTTP when its `initialize` says `mcpCapabilities.http` (`capabilities.session.mcp.http` in version 2), else over stdio through the bridge below (version 1 requires stdio of every agent; version 2 must say `capabilities.session.mcp.stdio`). Then each `session/new`/`load`/`resume` gets an MCP entry named `canoa-delegate` (any client entry of that name is replaced): an HTTP one at `http://127.0.0.1:PORT/mcp` with an `Authorization: Bearer` header, or the bridge's stdio one. The bearer is 32 random bytes as 64 hex digits, minted per session, valid once the session's id is known, revoked when the connection ends, kept only as a digest, never logged. One loopback server per host; it refuses a request with no or another bearer (401), an `Origin` or `Sec-Fetch-*` header or a `Host` other than its own socket (403), any path but `/mcp`, any method but POST,  and a chunked body.
  A connection has 2 seconds to send its head before any bearer is checked and counts against 32 such connections until it has shown one; after that a call counts against its session's 8 (a ninth is 429), so one session's long `task_status` waits cannot crowd out another's.
- **The stdio bridge** is `canoa mcp-bridge` (hidden; `canoa-ffi` runs it as `--canoa-child mcp-bridge`, so an application with no `canoa` on disk has it too): a stdio MCP server that relays each request line to the loopback server and the answer back. The host writes it as the entry `{name, command, args, env}` with `command` and `args` the host's own program (`ServeOptions::provider_program` and `program_args`) then `mcp-bridge`, and `env` holding `CANOA_DELEGATE_URL` and `CANOA_DELEGATE_TOKEN`, so the bearer is never on a command line another user can list; version 2 adds `type: "stdio"`. It reads both variables from its environment and ends with status 2 and a reason (never the token) when the URL is missing, is not `http://` on a loopback address (`127.0.0.0/8`, `::1`, or `localhost` resolving only there), or the token is missing or holds a character a header cannot carry.
  It holds no state: one HTTP request per line, up to 8 at once (answers come as they finish, by id), a notification the server takes gets no answer, a request the server cannot answer (no or revoked bearer, no listener, a busy session) gets a JSON-RPC error with code -32000, a line that is not JSON gets -32700, and it exits 0 when standard input closes (in-flight calls are dropped) and 1 when a line is longer than 16 MiB or reading fails.
  - Tools (JSON answers only): `delegate_targets {source?, account?}` answers `{targets: [{source, title, harness?, host ("this host" or "another machine"), remote, accounts, profiles: [{name, loadouts}], ready, missing?, workspace, models? (with `source`: {account, known, list: [{id, efforts, ...}]}, those of the `account` named, one the source offers, else the source's first)}], default?, maxRunning?, sources? (the person's narrowing), context (the kinds the person let the agent attach), contextBytes, offered: [{source, title}] (every source the connection may use, narrowed or not), from: {default?, sources?, maxRunning?} (`session` for the person's own value, else the profile layer that suggested it), unusedDefault?: {value, layer, why} (a suggested default the connection may not use)}`: the sources the session may name with the entry's account names, never a credential;
  `delegate_task {source?, task, folder?, workspace?, title?, model?, effort?, account?, profile?, loadout?, context?}` answers `{taskId, state}` (`source` may be left out when the person set a default): `account` must be one the source's entry offers, `model` and `effort` one its provider lists (asked before the task starts when the provider can say, else checked against the session's own options, and the task ends `rejected` naming it), `profile` and `loadout` are the entry's own, refused by its host; none is ever replaced by another; `context` is `task` (default), `messages` or `files`: the host keeps the session's turns (the person's prompts and the agent's words) and the files its tool calls named (`locations`, a diff's `path`, `rawInput.file_path`) as it relays them, and an agent's own call is given the newest of either, up to `context_bytes`, after the task text (`Handed over with this task:`), only when the person let the session do it (`_canoa/delegate/setup` `context`); files outside the session's folder and its connection's roots, or not text, are left out and named; a task for or from another machine takes `context` `task` only.
  A source on another machine needs `workspace` (a folder there, refused without it, never this session's folder) and takes no model, effort, account, profile or loadout; the far host keeps it inside its source's working roots and fails the task naming it otherwise, and a `workspace` for a source of this host or a `folder` for another machine's is refused; `task_status {taskId, wait_ms?}` answers `{taskId, state, title, source, message?, result?, truncated?, resultBytes?}` (`state` is `submitted`, `working`, `input_required`, `completed`, `failed`, `canceled` or `rejected`; a wait ends on a state change or a terminal state, and a timeout cancels nothing); `cancel {taskId}`. They are `SendMessage` (`returnImmediately`, `tenant` = source), `GetTask`/`SubscribeToTask` and `CancelTask` with the caller `local:CONNECTION:SESSION`, so a session sees only its own tasks (another's id is `TaskNotFound`).
- Privilege, checked before any process starts: the source is one the connection may use (an entry's `peers` for a key, any for the owner) and in `sources`; the folder is canonicalised (links, `..`) and equal to or inside the session's `cwd` and its entry's working roots; the mode is the session's own only when the task's agent is the same kind (the same `harness` provider, or the same program) and lists it, since a mode id means something only to the agent that named it; otherwise `manual`, else `default`, else the task is `rejected` (no argument sets a mode); `max_children`, `max_running`, `task_bytes`. The task's agent is given no `fs`/`terminal` capability, and its `session/request_permission` goes to the delegating connection on the parent's session id with `toolCallId` `TASKID:ORIGINAL` and `_meta["dev.boriken.canoa/delegate"] = {taskId, title, source}`; the task reads `input_required` until the person answers, and no answer or a closed connection cancels it.
- **A profile's delegation suggestions** (`[delegate]` of a layer, `[harness.ID.delegate]` of an overlay): each session starts with the effective ones for the harness its agent reports in `initialize` (else the entry's name). Only suggestions: the default is used only when the connection may use that source, `sources` only narrows, `max_running` only adds a limit beside `max_children` and `[host.delegate] max_running`. The person's own `_canoa/delegate/setup` replaces each key; clearing it brings the suggestion back.
- **The person's own delegation** (a client that opted in; answered on its stream, never reaching the agent): `_canoa/delegate/targets {sessionId, source?}` answers what `delegate_targets` does; `_canoa/delegate/start {sessionId, requestId?, source?, task, ...}` (the arguments of `delegate_task`) makes the same A2A task in the session's store, so the agent's `task_status` and the host's events show it, and answers `{taskId, state}`, or `-32602` naming the refused choice; a start with a `requestId` the session already made answers that task with `repeated: true` and starts nothing, so a client that lost its answer may send it again. `_canoa/delegate/setup {sessionId, sources?, default?, maxRunning?, context?}` (each key present replaces, `null` clears) narrows the sources the session may name to those listed (never past what its connection may use), sets the source a task with none named goes to, how many tasks of the session run at once, and which of `messages` and `files` the session's agent may attach by its own call.
  `_canoa/delegate/context {sessionId, kind}` (`messages` or `files`) answers `{contextId, kind, text, items: [{name, bytes}], skipped, truncated, bytes}`: exactly what a start naming that `contextId` (and the same `context`) gives the task, so the person reads it first; an unknown id refuses the start. The task's metadata records `context` as `{kind, bytes, items, skipped, truncated}` without the text.
- **To the client** (a client that opted in; a task's own connection is never sent these): the host sends the notification `_canoa/delegate/event` `{sessionId, taskId, event?, update?}`. `event` is A2A's `StreamResponse` for the task (`task` first, with `metadata` `{title, source, folder}`, then `statusUpdate` and `artifactUpdate`, the last status ending the stream; once a task that reported spend has ended, one more `task` event whose `metadata.usage` is `{input?, output?, cacheRead?, cacheWrite?, costMicroUsd?}`, what the task's own session spent, never what it started: a counter the agent never reported is absent, and a task that reported none gets no such event), `update` is one `session/update` of the task's agent as it sent it. Updates beyond 1024 waiting in the outbox are dropped (the history keeps them); states never are.
  The client may ask `_canoa/delegate/history {sessionId, taskId}` for the updates the host kept of a task, a running one or one of the last `max_children` that ended in the session (`{taskId, updates}`, or `-32602` for another id), and `_canoa/delegate/stop {sessionId, taskId?}` to cancel every task of the session or one (`{}`); both are answered on the stream and never reach the agent. The host's own messages in the `_canoa/` namespace pass the scope's filter only while the host is sending them (`scope::host_own`).
- Stop: the parent's `session/cancel` and the `cancel` tool cancel the task (`session/cancel`, then the process is ended after a grace period); a closed connection or a stopped host ends every task and its process.
- Built-in translators: Claude and Codex (the host's `harness` entries) and Grok say `mcpCapabilities.http` and take the entry; Antigravity says none, so gets none.
- **Another machine's agent as a source.** `[agents.NAME] a2a = { url = "ws://HOST:PORT", peer = "PEERID", source = "SOURCE", title = "..." }` (`Config::remote_agents`, `RemoteAgent { name, title, url, peer, source }`; `source` is the skill on the other host's card, left out when it has one) names an A2A agent on another host. It is no session and is listed nowhere; a task may name it only when `[host.delegate] sources` lists it, because the task's text leaves this machine, and only a session of the owner's own may (a paired key's session may not). The host dials `url` with its own identity, proves the key `peer` and no other, and sends the task text addressed to `source`: only the `workspace` the task names there (a `folder` for it is refused), no history, no context. Its task is mirrored as the host's own, with the states, the `result` artifact (the other agent's first artifact is renamed `result`), and `INPUT_REQUIRED` put to the person as an ordinary permission request on the parent's card (`_meta` names the task, title and source); the person's answer goes back as a message of the task.
  Its task's metadata says `remote: true` (a question that comes up through a task of this host's own keeps the mark, and the client is told the outer task is one too), and the app answers such a question for no one: Bypass, a task's allowance and a remembered rule skip it. A question over 16 KiB, or with over 8 options, is cancelled. `AUTH_REQUIRED` ends the task `FAILED`. The other host's `CANCELED`, a lost link, a link that ended without a final state, or a refusal to serve the key ends it `FAILED` (never `COMPLETED`); a stop here is `CancelTask` there. What the other agent may do is the other host's grant and rules to this host's key; nothing here bounds it. Only `ws://` is dialed: the proof seals the link.
- **This host as such an agent.** `[host.delegate] a2a = ["PEERID", ...]` lists the paired keys granted `a2a/1`. A link of streams (the first message starts a mux) is served over the address of an `agent` entry the key may use (a provider, tool or control address refuses it); the link opens a stream for `a2a/1` only for a listed key, so any other paired key is refused (`NotGranted` on the client), and the list is read when the host starts, so a key is added or taken off with a restart. The granted key's card lists the sources whose entry names the key in `peers` (an entry with no `peers` is open to every paired key, and a grant does not extend that: `Principal::Remote`) and has a `working_roots` entry, narrowed by `sources`, and never another machine's agent. Its tasks run on them as sessions of the key, in the first `working_roots` entry of the source (or the `workspace` the task names, which must be inside one), in the mode that asks for everything, within `max_children` and, together with every other granted key's (tasks nested under them included), `max_running` less one, so the person always has a place. The key is told no path of this host (no `folder` in a task's metadata).
  A grant lets the key run tasks on every source it may use and answer their permission questions: grant it as that. A child's permission request is `INPUT_REQUIRED` with the request (`toolCall`, and the `options` that are `allow_once` or `reject_*`, never an "always") as a data part of the status message; the key answers with a `SendMessage` naming the task whose data part is `{"outcome": ...}`; only an option the agent offered reaches it, anything else is a cancel; no answer in 15 minutes is a cancel. When a key's last link ends (it went, or it was unpaired), every task of the key is cancelled and its session dropped, whichever call started them; each such task logs its start and end with the key, source and task id. `ListTasks`, `GetTask`, `CancelTask` and `SubscribeToTask` see the key's own tasks only.
- The tool servers of delegation, secrets and the Store are one implementation (`loopback.rs`); each adds only its bearers, its limits and how a message is answered. Every one refuses, on Linux, a connection whose socket another user owns (asked of the kernel for that one connection, and read from `/proc/net/tcp` where it cannot say), since an agent's command line may carry the bearer; elsewhere every user is taken as this one.

## Secret prompts (`coqui-acp-secrets`)

An agent asks the person for a password or a key, or shows them one, and neither the model, its transcript, the host's history nor its log ever holds the value. There is no setting: a session is given the tools when its client offered them and its agent takes MCP servers over HTTP or over stdio.

- **Offered by the app.** The client's `initialize` carries `clientCapabilities._meta["dev.boriken.coqui.acp/secrets"]` (`capabilities._meta` in ACP v2), `{"version": 1, "methods": ["request", "show"], "bindings": [..]}`. The host reads it on the raw stream, before the scope removes `_meta`. A binding is `ecdsa-p256-sha256` for a host whose key is WebCrypto and `x25519-hmac-sha256` for a Noise one, and `link-hmac-sha256` for the application in the host's own process: an app that does not list the host's binding for its connection gets no tools.
- **Whose identity.** The frontend of a connection is its own proven peer, whose key the host knows from pairing (the trust store), and every answer is bound to it and to the host's key; one signed by any other identity is refused. The application hosting the library through `Local::open` shares the host's process and identity, so neither key proves anything to the other: that link is bound by a 32-byte secret the host mints when it starts (`Local::link_secret`, `canoa_ffi_link_secret`), never sent over any wire and never given to an agent, with `link-hmac-sha256` (an HMAC of the same statement under a key derived from it; `coqui_acp::secret::LinkKey`). Only a connection `Local::open` makes is bound that way; a connection with a key (paired or relayed) never takes the method, whatever it offers, and a task's connection (`open_with` a context) has no person at its other end and gets no tools. The host's key is used in this process as the library's `unprotected` signer does (the process already holds it).
- **The tools.** Each `session/new`, `session/load` or `session/resume` of such a client gets an HTTP MCP entry named `canoa-secrets` (any client entry of that name is replaced) at `http://127.0.0.1:PORT/mcp` with an `Authorization: Bearer` header: 32 random bytes as 64 hex digits, minted per session, kept as a digest, valid once the session's id is known, revoked when the session closes or the connection ends. One loopback server per host, started at the first session; it refuses no or another bearer (401), an `Origin` or `Sec-Fetch-*` header, a `Host` other than its own socket (403), a connection from another user on Linux, any path but `/mcp`, any method but POST, a chunked body, more than 4 calls of one bearer at once (429) and a body over 256 KiB. The tools are `secret_request`, `secret_use` and `secret_show` of `coqui-acp-secrets` (its header says what they take and answer); a session's secrets are cleared with it.
- **Asked of the app.** `_coqui_acp/secret_request`, `secret_show_open` and `secret_show_deliver`, and a use's approval as `session/request_permission` (options `allow-once`, `allow-session`, `reject`; the card shows the command, the program by full path and the notice that the folder's scripts belong to the agent). They are written on the client's own stream with ids `canoa-secret-N-HEX`, and the answers are taken off it: neither passes the scope, the profile, the history or the delegation. An agent's own request or notification whose parsed method starts with `_coqui_acp/secret_` or `_canoa/` is dropped (`scope::dropped`, on every entry), and so is any line of the agent's this host's JSON reader cannot read (a lone surrogate, nesting past 128 levels, a number out of range), which a more lenient reader in the client might take for one (logged once per connection, without the line), so it cannot put a value on the person's card in the host's name.
- **The mode decides a use.** A secret's use is a permission: in a mode the app calls Bypass (`bypass`, `bypassPermissions`, `full_access`, `full-access`, `fullaccess`, `yolo`) it is approved without asking; in any other the person is asked, with allow once and allow for the session. **The person's choice decides, never the agent's word:** only the client's own `session/set_mode` or `session/set_config_option`, answered OK by the agent, for a mode the session listed when it opened, puts a session in Bypass. What the agent says of itself (the mode it starts in, a `current_mode_update` or `config_option_update`, an echo of the options) can only lower it, so an agent that starts in Bypass or moves there itself has the person asked.
- **Stdio agents.** An agent that does not say `mcpCapabilities.http` gets the same tools as a stdio server running `canoa mcp-bridge` (the delegation tools' bridge), the address and bearer in its environment.
- **Not served.** A Noise app whose page does not know the host's static key, and a native app that reaches a host over the network (it has no key of its own to bind with).

## Secret providers (`[secrets]`, `canoa_host::secrets`)

An agent asks for a secret by name, and it is answered from what is held before the person is asked. Where a secret comes from is a `secret_provider` (`canoa::secret_provider`): the host carries the person's form (`form`, which holds nothing and is asked in the app) and the operating system's credential store (`system`, Windows' Credential Manager, the Secret Service or the Keychain, kept under the service `dev.boriken.canoa.secrets`, with an index entry that names what it holds; it also lists the store's other entries, `Names::others`, each by the name the store spells it (Windows' target name, `service/user` elsewhere) with the user name as its summary, from the store's own search (`accounts/store/outside.rs`, no platform call of ours), leaving out every service Canoa makes; `get` of such a name reads that entry (UTF-8 or UTF-16 text, else it says the value is not text), `put` always writes Canoa's own and `forget` of a name that is not Canoa's deletes the other program's entry, which the app confirms; nothing of it is listed for an in-memory store), and a library of `[host.extensions.NAME]` or of an entry adds more, a script's included.
The providers are offered the way profile items and agents are: built-in first, then those the loaded libraries offer, a provider whose id was taken or that cannot be described left out and logged.

```toml
[secrets]
default = "form"                   # the entry that answers a name no line of `names` gives
store = "system"                   # the entry "Remember" keeps a typed secret in; "none" offers no such way
keep = "session"                   # what the form offers first: once, session, close, 15m, 1h, 8h, 1d, ttl:SECONDS
max_wait = 240                     # the most seconds a request waits for the person (default 240, and never more than a sealed question lasts)
accounts = "auto"                  # who keeps the accounts' credentials and the mail accounts' passwords: auto (the system entry when the operating system's store answers, else file), or an entry that keeps what it is given
[secrets.names]
github_token = "work"
[secrets.providers.work]
provider = "bitwarden"             # the provider's id
keep = "close"                     # how long a value this entry gave is kept in memory (default session)
command = "bw"                     # any other key is the provider's own setting, checked against its schema
[secrets.providers.work.from]       # a setting that is another secret, taken from an entry and never asked for
session = { entry = "form", name = "bw_session" }
```

- **Read at each use, hidden from `config/get`.** The section is read from canoa.cfg every time it is needed (a change applies at the next request) and no page edits it through `config/set`. A section that cannot be read is not used, with the reason in the log, and the defaults answer. `form` and `system` exist without being written.
- **Other kinds keep their secrets here.** The accounts' credentials and the mail accounts' passwords are named secrets (`accounts/<id>`) of the provider `[secrets] accounts` names (see "Accounts"): `Vault::get_in`, `put_in` and `forget_in` ask an entry's provider directly and never the cache, and `secrets::handle::HandleStore` is the `SecretStore` the accounts use over them, so there is one way a credential rests and the Secrets section lists it. `Accounts::open(&Config, home)` builds a vault of its own from `Config::secrets` (the `[secrets]` table as the file has it) and the host's home, loading the extensions' libraries only when the entry is not one the host carries. The `file` provider (`directory`, the home's `secrets/` folder when left out) is the sealed files `account_store = "file"` used to be.
- **Asking waits only as long as someone can answer.** `secret_request` takes `wait_seconds`, how long the agent can wait; its schema states the host's longest (`[secrets] max_wait`, never more than the sealed question lasts, 240 s) as the maximum and as what a request that names none waits. The answer's `status` says what happened: `accepted`, `declined`, `cancelled`, `timed_out` (the question is withdrawn: the host sends the app the notification `_coqui_acp/secret_withdraw` `{sessionId, requestId}`, which takes the card away) or `no_one_present`. A session whose person's connection ended while the agent went on is kept a bearer for an hour (at most 256) that answers a `secret_request` `no_one_present` at once and any other tool as an error; what a provider holds is answered as ever. A provider whose `needs_person` is set (the form) is only ever asked through the person's app, so it is never asked when no one is there. A person who is connected but away from the screen is not told apart from one at it: the agent's own limit ends that wait.
- **The request path.** `coqui-acp-secrets`' `secret_request` asks the session's frontend (`Front`) first: `recall(name)` reads the vault (the cache, then the entry that answers the name, then the `store` entry), and answers with handles and no question when every question is a secret one it holds. Otherwise the form goes to the app with one more question, `_keep`, offering the ways below, and the answer is `remember`ed as chosen. A provider whose `needs_person` is set is never asked by `recall`. The agent is never told how a secret was kept.
- **How long.** `once` keeps nothing; `session` keeps it for that ACP session and ends with it (`session/close` or the connection ending); `close` until Canoa closes; `15m`, `1h`, `8h`, `1d` or `ttl:SECONDS` for that time; `store` puts it in the `store` entry's provider for good (the system store), from where it is read afterwards. What a provider gave is kept as its entry's `keep` says. **A value is kept no longer than the shorter of what was chosen and what its provider said** (`Held::expires_in`); an answer of 0 is not given.
- **The script engine is the program's, not the library's.** `canoa_host::bundle_js!()` gives the host the JavaScript source (QuickJS, `guatiao-source-js`) that the program running it links: `canoa` calls it as it starts and `canoa-ffi` before each job, and a lib test carries the engine itself. The library does not link the engine, so a Guatiao library of its own that uses `canoa-host` (an extension) does not export the engine's `guatiao_declares` beside its own; a program that never calls it offers no script providers and refuses `source = "bundled:js"`. An in-process test host (`tests/linked`'s `Hosted`) calls it as `canoa` does, and a test that binds `Serving` itself gives it `with_state_dir`, so the scripts that ship in the host (the speech provider that runs a program, the profile items, the catalog sources) run in it and are kept in its home and never in the person's own. `canoa_ffi` therefore exports `guatiao_declares` and `guatiao_source` (declaring `source=js`) beside the C surface it already exports.
- **Bitwarden is a JavaScript library that ships in the host**, `extensions/bitwarden/` (`bitwarden.js`, its `package.json` and manifest): a `secret_provider` served by the QuickJS source built into the host (`guatiao-source-js`; `source = "bundled:js"` names it in an extension entry of canoa.cfg, with `source_settings` of `dirs`, `kinds` and `limits`). The files are kept in `<home>/bundled/secrets-VERSION-DIGEST/` (`scripts::Bundle`, the same for every script library that ships: its name, the host's version and a digest of the files it carries) and rewritten when they differ from what the host carries, and the provider is offered with the built-in ones whenever the host has a home. QuickJS gives a library no processes, so every program a provider runs starts through the `spawner` each call of the kind is handed (this machine's, with a program the Store installed, such as `bw`, found by its bare name); the provider destroys it. It reads one part of a vault item by name through Bitwarden's own command (`bw get password|username|notes|totp|uri NAME`) and lists the names (`bw list items`, names only kept).
  Settings: `command` (`bw`), `arguments` (what goes before `get`, for a program that runs `bw`), `part` (`password`), `session` (the key `bw unlock --raw` printed; marked `writeOnly`, `x-sensitive` and `x-from-secret`) and `timeout_seconds` (30). The key goes to `bw` in `BW_SESSION`, never on a command line; a vault that is locked, signed out or given a wrong key, a command that is not installed or that does not answer in time is `GONE`, which `recall` reads as nothing held, so the person is asked for the secret itself. An item that is not there is no value. Its items have no end of their own, so no answer carries one. `secrets::script_tests` runs it against a Rust stand-in for `bw` through the QuickJS source; `end_to_end_...` runs the real process spawner against `extensions/bitwarden/tests/bw_standin.py` (set `CANOA_TEST_PYTHON`; without it that test is ignored and a run counts it as not run).
- **A setting that is another secret** is a field the provider's schema marks `x-from-secret` (an annotation guatiao carries and never reads, beside `writeOnly`). An entry gives such a setting in `[secrets.providers.NAME.from]` as `{ entry, name }`: the secret is read from the cache or from the entry (which never asks the person), through at most four providers, and a secret that is not held leaves the provider not asked at all. A secret setting is never written in canoa.cfg, and a setting not marked `x-from-secret` cannot be taken this way. `secrets/configure` writes an entry and checks all of it (see the table above).
- **The application draws a provider's setup from the same documents.** `secrets/providers` serves each provider's `schema` and `form`; the app's schema form (`app/lib/voice/provider_form.dart`, which the speech providers' settings use too) draws a field the schema marks `x-from-secret` as the choice of an entry and a secret name (`from`), never as a box to type the secret in, and saves it through `secrets/configure`. After the Store installs a program of the Secret providers type the setup opens, and a `from` entry that needs the person (the form) opens the sealed form for that name.
- **Nothing prints a value.** The vault's `Debug`, its rows and errors name providers and names only; a provider's error is logged by its message, which holds no value by the kind's contract.
- **Permissions are unchanged.** Recalling a secret gives a session a handle, and every use of it still goes through the session's permission mode. A session in full access can use any secret a provider holds under a name it guesses; no tool lists names to an agent.

## The store tools (`[host.store] tools`)

```rust
pub const STORE_META: &str = "dev.boriken.canoa/store";   // the `_meta` key of `initialize` that asks for the tools
```

An agent can search and read the Store through an MCP server the host adds to its sessions, `canoa-store`, offered the way `canoa-delegate` is: the client sets `_meta["dev.boriken.canoa/store"] = true` in `initialize`, and each `session/new`, `session/load` or `session/resume` then gets one entry named `canoa-store` (any client entry of that name is replaced): HTTP at `http://127.0.0.1:PORT/mcp` with an `Authorization: Bearer` header when the agent takes HTTP servers, else the stdio bridge (`PROGRAM mcp-bridge`, address and bearer in its environment). The bearer is 32 random bytes as 64 hex digits, minted per session request, kept as a digest, revoked when the agent refuses the session or the connection ends. One loopback server per host, started at the first session; it refuses no or another bearer (401), an `Origin` or `Sec-Fetch-*` header or a `Host` other than its own socket (403), a connection from another user on Linux, any path but `/mcp`, any method but POST, a chunked body, more than 4 calls of one bearer at once (429) and a body over 16 KiB.

- **Who gets it.** Only a connection whose key holds `overlay.read` or `store.programs` on the control channel (the owner and this process's own link hold every grant; `[host.control] grants` and, on a portal host, the portal's grants decide a paired key's). A task another agent handed out gets none, since no person is at its end. `[host.store] tools = false` gives none to anyone. A session that gets the tools also gets a built-in skill, `canoa-store`, delivered with its skills the way the person's chosen skills are (a skill of that name the person chose stays theirs), that says when to search and inspect and to treat results as data.
- **The read tools.** `store_search {query?, kind?, installed_only?, refresh?}` -> `{results, total, truncated, sources, note}`: at most 25 entries of `store/index` (`overlay`, `skill`, `program`), each `{id, kind, name, summary, catalog, source, version, pin, tags, installed}` (`installed` is null for a program); `refresh` is honoured only for a key that holds `overlay.write`, and refused in words otherwise. `store_inspect {kind, id, source?, version?}` -> `{entry, plan, note}`: the entry in full with `origin`, `requirements` and `contents`, and `plan`, a dry run from the index (what installing adds: skills, MCP servers, hooks, environment scripts; MCP servers, hooks and environment scripts stay off until the person allows them) with nothing fetched; for a program it is the program store's own `store/plan` (needs `store.read`), asked for no key so no apply can name it. An id is the index's `LABEL:KIND:NAME` or a name, with `source` to choose a catalog when two share it.
- **What an agent reads is data.** Each string a catalog, manifest or program store wrote is cut (400 characters; names 120) and stripped of control, zero-width and direction characters, and every answer carries a note that the text is its author's claim and no instruction. The read tools pass only the grants of `overlay.read`, `overlay.write`, `store.programs` and `store.read` to `store/index` and change nothing.
- **The change tools, each with the person's yes.** `store_install {kind, id, source?, version?}`, `store_update` (the same), `store_remove {kind, id, source?}`, `store_rollback {kind: "program", id}` and `loadout_update {action: enable|disable, kind: overlay|skill, id, scope?: "loadout"}` -> `{changed, applied?, declined?, why?, note}`. An entry is looked up in the index by id or name: the agent never names a repository, a URL or a path, so a source is only one that a catalog the person listed names. The host works the change out first and keeps it under the session that asked (the plan's owner is `canoa-store:SESSION`, so one session's plan is never another's), then puts it to the person as a `session/request_permission` on that client's own stream: plain text with the digest it is bound to last (`Bound to: ...`) and the options Allow and Reject; every line is made inert as the read tools' text is.
  What a plan does to the computer (changes outside the host's folder, steps, notices) and what an overlay says it holds come first and are shown whole: lists of files and downloads are cut and counted, and a card that would still not fit in 80 lines, or has a line over 400 characters, or more than 15 steps or outside changes, is not shown and the change is refused ("too large to show; use the Store"). It applies only on the client's answer `allow-once` to that question's id (`canoa-store-ask-N-RANDOM`): an answer is read off the client's stream, swallowed there and never forwarded to the agent, an id nobody asked is swallowed and approves nothing, and a message of the agent's never answers. A session the person put in a mode that asks for nothing (`session/set_mode` or `session/set_config_option` from the client, answered OK by the agent, naming a mode the agent listed) is not asked, as for any tool, but the host then says so in the session (an `agent_message_chunk` of its own naming the change and its digest), and a change that writes canoa.cfg or the overlays folder while either is on the person's protected list (`[host.store] protected`) is asked about in any mode.
  Any `session/set_mode`, and any `session/set_config_option` of the mode option, from the client lowers that at once, before the agent answers and whatever else is pending; only the agent's OK raises it. The agent saying it is in such a mode only ever lowers it. The host waits 5 minutes; a closed connection, a timeout, an error and any other option refuse. One change at a time for a session (another is refused in words), and the call blocks the agent while the person decides. Working a change out fetches from the catalog's source before anyone is asked (each is logged); a session whose changes end 5 times with nothing to show the person (an error, nothing to do, a card too large) is refused more. An error text reaches the agent inert, with the note. When the session or the connection ends, a program apply under way is told to stop. Before applying, the host finds its own kept plan again and checks its digest against the one shown (an overlay's tree digest, the SHA-256 of a program's plan, the state a removal acts on, the loadout table's); a mismatch or a plan another session made is refused and nothing changes.
  - **Overlays** (`kind: overlay`; need `overlay.write`, `config.write` and `config.write.sessions`): install and update run `overlay/check` for the session and show the commit, the tree digest, the catalog's pin, the files added, changed and removed, what the catalog says it holds, and that hooks, environment scripts and MCP servers stay off until the person allows them at their digest; the pin goes into `[overlays.NAME] source, pin` first (an existing entry's `options` kept; every read and write of canoa.cfg here is under the one lock that all writes take) and `overlay/apply` places the files after; if that fails the entry is put back as it was. An update must come from the catalog the overlay was installed from. An overlay canoa.cfg names by hand or from another source is refused, and a pin the store did not write (one that is not the installed digest) is the person's to move; the store's own pin moves with an update, and the card says so. The skills an overlay names from other catalogs are not fetched by this path. Remove deletes the folder, the fetched history and the entry, only for what the store installed.
  A source on this computer is refused for an agent unless an entry's `peers` lets the session's key use a working root that holds it and the key has `folders`.
  - **Programs** (`kind: program`; install and update need `store.programs` and `store.read`, remove and rollback `store.programs`): the program store's own plan (`plan_for`, under the session) shown with every download and its check, each step it runs, what it changes outside the host's folder and the store's notices; the apply is `apply_store_for` with a sink that cannot ask, so an install that needs a typed answer fails. Remove and rollback act on the copy whose version the card showed, and a rollback's card names the version it goes back to and the digest binds both.
  - **Skills** a catalog offers are installed by the Store in the app (it fetches each against its pin), and `store_install` of one says so. `loadout_update` turns an overlay or a skill the person already chose on or off in the default loadout (`[defaults] loadout`; with none, it writes `Default`, holding every overlay and server the profile lists, as the app does), through `Files::config_update`, and its digest covers `[loadouts]` and `[defaults]`; it reaches new sessions only, since a session's own set is fixed when it starts, which is why `scope` is `loadout` only.
  - No tool changes `[agents.*]`, a hook or environment-script allowance, `[host]`, `[permissions]` or a program's own configuration.

## Accounts

An agent entry with `harness` can offer accounts: logins of the provider's, each its own `[host.accounts.NAME]`. The harness's account provider (an `account_provider`, id `<harness>_accounts`, from the same library: `claude_accounts`, `codex_accounts`, `pi_accounts`, `opencode_accounts`, `grok_accounts`, `antigravity_accounts`) owns how an account is made and kept: its kinds (each saying the standards it provides and whether it renews), its login methods, and the sign-in, renewal, watching and plan limits of what it made. The harness owns how it takes one (its `accounts` catalog: the standards it accepts, the variables it clears); the host owns which accounts exist, where their credentials rest, who holds one and what a renewal does.
The kinds and sign-in methods the host lists, and the only kinds it accepts, are the account provider's `offers()` (Pi offers `pi-oauth` only, OpenCode `opencode-login` and `opencode-provider-key` with three sign-in methods, `provider-key` and `provider-code` (OpenCode's own `auth login` for a provider, driven on plain pipes: a key typed, a code shown) and `api-key`, Antigravity none) with `harness-login` and the kinds that gateways serve (below); a library with no account provider offers nothing to sign in to.

**Gateways.** A library can also offer a `model_gateway` provider (`canoa::gateway`) for an account kind its own `account_provider` makes: a model that runs on this computer, served to the agent for a session. The host holds no word of any such kind: it finds the gateways the bundled libraries offer (`gateways.rs`), joins each gateway's kind and its sign-in method to the catalog of each harness whose `agent_vendor` says how it takes a gateway's address and bearer (`gateway_route`), signs an account in through the library's own account provider (found by the method), and when a session starts on such an account opens the gateway for it (`GatewayRequest`: the account's id and settings, the table of canoa.cfg the gateway names in `GatewayInfo::table`, the host's home and the command line of its `helper` command) and gives the harness its own account kind with the address and bearer the lease holds, and the files its folder needs (`gateway_files`); dropping the grant drops the lease. `providers/list` answers each gateway as `{kind, vendor, provider, title}`. A session's identity variables take `local` and the gateway's vendor for such an account; its plan limits are none.
`canoa helper LIBRARY ARGS` (hidden) runs the helper a library the host carries offers (`bundled::INCLUDED`), which is how a gateway keeps part of itself in a process of its own.

**Account makers.** A library that is no agent can offer an `account_provider` no harness owns (an id that is not `<harness>_accounts` of an `acp_harness` the same library offers): an account maker (`makers.rs`; `bundled::INCLUDED` carries them, `canoa-foundry`'s among them, and so do the libraries and sources of canoa.cfg's `[host.extensions.NAME]` and agent entries, so a gateway or proxy written with the SDKs (`examples/providers/python/gateway`) is offered the same way, with no change to Canoa). `Makers::of(&Config)` is every maker in force for one config: the bundled ones, then those of the registries `control::providers::libraries` opens (an extension verified as the Store verifies it), found once and kept in the `Config` (a copy of a config finds its own); a kind or a sign-in method id a bundled library or an earlier one already offers is not offered again, and the log says so, so a library cannot take another's place; `kind::Harness::new` takes the `Makers` and `Harness::makers()` hands them to what reads or signs in an account, so no list of makers is global. The host holds no word of what one makes.
A provider is no maker when it is `<agent>_accounts` of an `acp_harness` or of an `agent_vendor`'s agent its own library offers. It joins each kind a maker offers, and the sign-in methods that produce it, to the listing of every harness whose catalog accepts a standard the kind provides (a kind a gateway serves joins the harnesses that can be given a gateway, as above; a kind that names the address of its API, a key for that address, joins only a harness whose slot for the standard can be pointed at an address, so Pi and OpenCode, which take a key at their vendor's own, are not offered it and an account that names an address does not fit them), so an account is made through any of them; it signs in through the maker (found by the method), and asks the maker, never the harness the account names, for the account's `usage`, `models` and `renew`.
`harness` stays required on an account (the provider through which it was made and listed, and the group the application shows it under), and no harness's name limits where it runs: an account of a maker's kind is offered to every entry whose harness accepts any standard its kind provides, sits in each pool of each of its standards and in each matching `any-<standard>`, is one credential, one holder and one usage (read once per account and kept for a minute, whichever harness or pool asks, so a used-up bucket stops it in every pool), and `models` is asked of the maker once with every standard the account provides, so one list serves every harness that runs it (a query carries no standard to tell them apart by). A session's identity variables take `gateway` and no provider for such an account.

**A LiteLLM account.** `canoa-litellm` (`bundled::INCLUDED`, `bundled.rs` is the only place the host names it) is an account maker for the kind `litellm`, which provides `openai-api` and `anthropic-api`: Codex, Claude Code and any other harness that accepts either runs on one account, with one key, one holder and one usage. Its settings are the proxy's `base_url` (the root; a trailing `/v1` is dropped); the key is a secret of the account store. Two sign-in methods: `litellm-sso` opens the proxy's own sign-in (the host shows the page as any sign-in's `open_url`, and the key comes back to a loopback address of the host's) and `litellm-key` takes a key typed into the sealed form. A key the sign-in made also holds the `refresh_token` and `client_id` that renew it: the host gives a harness only the credential keys the standard it applies the account as names (`api_key`), and the account's own provider every key (`Held::provider_grant`). `usage` is `/key/info` (a `budget` bucket of spend against `max_budget`, and `rpm`/`tpm` buckets when set; a 401 makes the host renew the key by its refresh token, once, and read again) and `models` is `/v1/models`.
Not run against a real proxy: `canoa-litellm`'s `AGENTS.md` lists what is unconfirmed.

**The generic API-gateway kind, and accounts that name their own standards.** `canoa::api_gateway` (a library every host carries, `bundled::INCLUDED`) offers the account kind `api-gateway`: an address (`base_url`), the standards the address speaks (`standards`, one or several, any id `coqui_acp_api::standard::is_standard` takes) and a key. It covers an OpenRouter-, Portkey- or LiteLLM-style proxy with no crate of its own. The sign-in method `api-gateway` takes `base_url` and `standards` (text, ids separated by commas) as inputs (`canoa accounts add NAME --harness H --method api-gateway --input base_url=... --input standards=openai-api,anthropic-api`), and the key is typed into the sealed form and kept as the secret `accounts/<id>`; canoa.cfg holds the address and the list, never the key.
The kind provides nothing of its own: a property of a kind's settings schema marked `"x-provides": true` says the account provides the standards it names, and `accounts::standards` is the one place the host reads that (so the harnesses an account runs on, its pools, `accounts/list`'s `provides` and the grant a harness is given all agree), handing a harness the settings without that property, since a harness takes only the address (`base_url`) of an account of a standard. A property marked `"x-by-standard": true` (an object keyed by standard id, each value `{base_url, credential}`) says, for each standard, the address a harness that applies the account as that standard is given in place of the account's own (`accounts::standards::applied_as`, put in the settings key the kind's `model_api` endpoint names) and the credential key the account's one credential is given under for it (`Held::grant` renames the credential when the harness is given exactly one, so a standard that takes a bearer token as `auth_token` gets it and one that takes a key as `api_key` gets that); the standard a harness applies is the first of the account's that its catalog accepts (`Runs::standard`).
A property whose schema carries `coqui_acp_api::PROVIDES_BY_VALUE` (`x-provides-by-value`, an object from each value the property takes to a list of standards) makes the account provide what its value lists, the kind's own `provides` for any other value (`accounts::standards::provided`; a Pi provider key whose `variable` is `ANTHROPIC_API_KEY` provides `anthropic-api`, one naming `MISTRAL_API_KEY` provides none), and a harness that is not the kind's own is not given that setting. The maker is given the account as it holds it (`standards::for_maker`: its own address, its `by_standard`, its credential), never the harness's view (`for_harness`), so `models` reads the address the account names for the OpenAI API and a renewal finds its key. The sign-in takes `addresses` and `credentials` as inputs for it (`standard=value` pairs, separated by commas). Such a kind joins the listing of every harness that accepts any standard and can be pointed at an address. The models are the address's `GET /v1/models` (the OpenAI list) when the account provides `openai-api`, for every harness that runs it, and unknown with the reason otherwise; its usage is not offered, which is the answer.
A program adds its own path to the address: Codex adds `/responses` to it and expects `/v1` at its end, Claude Code adds `/v1/messages` and does not, so the account names the address of each standard that differs (`addresses=openai-api=https://llm.example.com/v1`) and `credentials=anthropic-api=auth_token` sends the one key as a bearer token to Claude Code. A key is credential-bearing only for the address: a request follows no redirect and goes through `[host.network]`, and an `http` address is taken only on this computer.

- **Where a credential rests.** In the operating system's credential store (Windows Credential Manager, macOS Keychain, Secret Service) through `keyring-core` and the platform's store crate, never in canoa.cfg, the ledger or a log. A record (the credentials, `revision`, `expires_at`, `needs_sign_in`) is the value of a named secret, `accounts/<id>`, of the provider `[secrets] accounts` names: the `system` entry by default (the service is `dev.boriken.canoa.` and a digest of the home's path, as the accounts' store always had, so two homes never share a secret and a home's Secrets section lists only its own; a vault with no home uses `dev.boriken.canoa.secrets`), through `secrets::handle::HandleStore`; a mail account's password is kept the same way. `[secrets] accounts` is `auto` by default: the `system` entry when a cheap read of one entry answers (a missing entry is an answer), else the `file` entry, with the reason in the log and as the last line of `canoa accounts list` (text); any entry that keeps what it is given (`can_store`) may be named, and one that does not is refused. The host reads it when it starts.
  Windows holds at most 2560 bytes in one credential and a Codex `auth.json` is several kilobytes, so the operating system's store cuts a value into chunks of 2048 bytes, one entry each, under a generation that an index entry names: a write that stops half way leaves the old record whole, one writer at a time per name in the process, an index that cannot be read is never written over, and a removal deletes every generation it can find. On Windows the operating system's credentials are made local to the machine (persistence `Local`) and are not roamed with the profile. **What an earlier host kept is moved, not lost.** `accounts::store::Migrating` reads the provider first and, for an account it lacks, looks in the stores the host used before (the operating system's store under the service `dev.boriken.canoa.` and a digest of the home's path, then the sealed files of `HOME/accounts/`), puts what it finds in the provider (the same per-home service, under the names the secrets use), reads it back, and only then removes the old copy; a removal clears every place.
  The `file` entry is the provider of sealed files: `file` keeps a file per secret in `HOME/secrets/` (or the entry's `directory`), sealed with AES-256-GCM to a key (`store.key`, 32 bytes) beside it, the secret's name in what is authenticated; the key is written whole beside its place and linked in without replacing another's, and each file is written beside its place and renamed over it, with the directory synced; for a host with no credential store (a headless Linux), logged as `non-default: [secrets] accounts is file` since it protects against a copied file and not against anyone who can read the directory. **The accounts directory is the owner's alone**: `HOME/accounts/` (the accounts' state, and what an earlier host sealed there) and everything made inside it are mode 0700 and 0600 on Unix, and on Windows `accounts/` is given a protected ACL naming this user and the system, which what is made inside inherits (an `accounts/` that already exists is left as it is; a directory whose ACL cannot be set is refused).
  One directory per account, named by a digest of its id: `state/` is where the harness runs, `lease` the file lock below, `placed` a note of the credential files placed in `state/`.
- **A session on an account and a model.** A start is an (account, model) pair: the client may also name the model in `initialize`'s `_meta["dev.boriken.canoa/model"]`, and the host asks the account's provider what it lists (as `options/choices` does) before the account is held for the connection; a model it does not list is answered `-32602` naming the account and the model, and the models it does list. A task handed to another agent (`delegate_task` with `model` or `effort`) is checked the same way against the account it names, else the entry's first (the login the program has where it runs for an entry that lists none), and refused by the same words.
- **Pools.** A pool is a set of accounts that provide one standard (`[host.pools.NAME]`), and a session picks an account or a pool the way it picks an account: `initialize`'s `_meta["dev.boriken.canoa/account"]` may name a pool, and the host settles it to one account before anything starts (`kind::Harness::settle`): the members the connection may use (those the entry offers, or with the `accounts` grant any the harness accepts, bar a key that would reach the agent in its environment unless the entry lists it), left out when another connection holds the account, when it does not list the `_meta["dev.boriken.canoa/model"]` named, or when its provider reports a bucket covering the model exhausted, and among the rest the next in turn. The answer's `_meta["dev.boriken.canoa/account"]` is `{name, kind, pool}`; a start no account of the pool can take is refused naming each account and why, and when the soonest allowance refills.
  The host names no standard: for each standard some account provides it makes `any-<standard>` (every account that provides it, `local` first when the login of a harness is that standard; nothing is written for it and it follows the accounts), and the standard a harness's own login provides, for the automatic `local`, is the first standard it accepts that no other harness accepts. An entry offers the pools it names, and any pool of a standard its harness accepts to a key trusted with accounts; a pool named by an entry gives its accounts to every key. An account in the pools of two standards is one account: one credential, one holder, one usage.
- **A pool's turns.** `pools/turn` (below) answers which account the next turn of a session runs on: the accounts are taken in turn at a new session and at a turn that starts after the cache lifetime has passed since the last (none for `off`, about five minutes for `short` and the agent's own, an hour for `long`), so a warm cache is never given up; a session whose account has a bucket exhausted for its model, or whose last turn a limit refused, moves to the next account with usage left (the app carries the conversation with `history/account`), and with none left the turn is refused saying when the soonest allowance refills. A session on one account is never moved: the answer says it ran out and lists the entry's other accounts that could take it, for the person to be offered.
- **A session on an account.** The client names the account in `initialize`'s `_meta["dev.boriken.canoa/account"]` (its name); absent, the entry's first (an entry that lists none runs on `local`, the login the program has where it runs, when its provider offers one); a name the entry does not offer, or an account held, is answered `-32602` before anything starts. A key that holds the `accounts` grant (the host's own application included) may also name any account of the entry's provider the entry does not list, except one whose key reaches the agent in its environment (it has to be listed, so the entry limits the settings files a repository could use to redirect it), and may send `null` for the login the program has where it runs (as `local` is, here with no listing), even on an entry that lists accounts. The answer's `_meta` names `{"name", "kind"}` and never a value. The provider is given the `AccountGrant` (the stored credentials, `revision`, and `state_dir` for a kind that needs one) and a spawner whose file methods serve that directory; the files it places there are taken away once the last connection on the account ends, the harness's own state stays.
  Usage is reported under the account's id. Each start logs the kind's notices, and `non-default: the host's environment sets NAME…` for a credential variable of the host's own that the account takes the place of (the provider removes every one it knows).
- **Standards.** An account kind says the standards it `provides` (`claude-code`, `anthropic-api`, `codex`, `openai-api`, and the others coqui-acp names), a harness's catalog the standards it `accepts`, and an account can run a session on an entry exactly when its own provider is the entry's, or its kind provides a standard the entry's harness accepts (a kind that provides none is taken only by its own provider). So an Anthropic API key made through Claude Code's provider runs a Pi session, and an account a gateway serves runs any harness that can be given one, whichever it was made for: the host gives the harness the account's grant with its `provides`, and the harness applies it by the first standard it accepts, refusing a credential or a `base_url` it cannot use with a reason that names no value. An entry that lists an account that cannot run on it does not start, naming the standards on each side; a key trusted with accounts that names one is answered with the same reason. A standard's kind that keeps a directory (Pi's variables, Codex's home) is given the account's private directory even when the provider that made the account needed none.
- **A key in the environment keeps repository settings out.** An entry with `harness = "claude"` that offers an account whose credential is in the agent's environment (a key or token, a kind that names the model's address and keeps no login directory, or an API standard's account another provider made) starts the provider with `setting_sources = []`, so no user, project or local settings file is loaded: a cloned repository's `.claude/settings.json` cannot set the address the key is sent to. It is logged as `non-default: host.agents.NAME: setting_sources is []`. An entry that names `setting_sources` itself (as an option or in its `settings`) keeps it and logs a warning, since a repository's settings can then move the key; login kinds keep the provider's own choice.
- **One holder.** A kind whose offer says `rotates` is held by one connection from its start until it ends, across processes (an exclusive lock on `lease`); a kind that does not rotate takes a shared lock, so a command that signs in again or removes the account waits for every connection. A second session on a connection that holds a rotating account (`session/new`, `fork`, `load` or `resume`) is answered `-32602` until the first is closed; sessions are counted from the provider's successful answers, so a failed open counts for nothing, and only `session/close` of a session the connection holds frees it. `canoa accounts login|remove` are refused while a connection holds the account; `list` shows `in use` for a rotating one. `harness-login` is never leased or stored.
- **Watching.** While a connection runs on a rotating account of its own provider that keeps its login in a directory, the host holds the account provider's `watch` (begun once the harness has placed the login, since a watch reports a missing login as lost, and ended with a last look when the connection closes); a models call on the account hands the account provider the same keeper, so a login the program renewed during it is stored. Settings: `account_settings` of the entry (`renew_poll_ms`).
- **Renewals.** What the provider reports through the account keeper is stored when it is the next of its chain or newer than the stored copy, and never when it holds no credential, an empty one, or lacks a key the stored login has. A provider's hold names the revision of the grant it began from in every renewal of the hold and counts them, so the next report of a source whose last stored revision is the stored one is accepted whatever revision it names; any other report is stored only if its `from_revision` is not older than the stored `revision`, its `expires_at` (RFC 3339) not earlier, and the credentials differ. The stored `revision` grows by one each time. A sequence a provider instance has already told is ignored. A `lost` login sets `needs_sign_in` and keeps the last copy, which the next start uses; a sign-in (`canoa accounts login`) replaces it and clears the mark. A blank copy is never stored.
- **Signing in.** The account provider's `login` runs the method in a directory made for it under `HOME/accounts/login/`, removed however it ended, with the provider's prompts relayed through the `Front`: `say`, `open_url` (with a device code) and `ask`, which a front without typed input refuses (`Front::ask` answering `None`) and the provider then fails the sign-in. The application hosting the library signs in through the control channel instead (`accounts/add` and `accounts/login`, which put each form to it sealed); a library job (`canoa accounts ...` as a job) has the front that cannot ask, and signs in only by a method that never asks. An `ask` is never answered from anywhere but the front. A sign-in directory is private, locked while the sign-in lives, and removed when it ends however it ended, a cancel included (the process waits up to three seconds for that before it ends); those a crash left, and the credential files a crash left in an account's `state/` (from the `placed` note), are swept when `Accounts` opens and before each sign-in, skipping any a live process holds.
  `--input` is checked against the method's input schema, and a secret input is refused on the command line.
