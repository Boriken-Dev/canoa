# `canoa-host` mail tools

## The mail tools (`[host.mail]`)

```rust
pub struct MailConfig { pub tools: Option<bool>, pub accounts: IndexMap<String, MailAccount> }   // [host.mail]
pub struct MailAccount { pub backend: String, pub id: Option<String>, pub password_env: Option<String>, pub timeout_secs: u64, pub settings: Settings }
```

An agent can use the person's own mail as a source through an MCP server the host adds to its sessions, `canoa-mail`, with a built-in skill of the same name. It is an extra server of the store's link (`store::mcp::Extra`): the same loopback server, bearer per session and stdio bridge as `canoa-store`, and the same way to ask the person. Unlike `canoa-store` it needs no `_meta`: every session of a connection whose key holds the **`mail`** grant gets it, when `[host.mail.accounts]` names an account and `[host.mail] tools` is not false. The application in this process holds `mail`; a paired key only if `[host.control] grants` or `[host.native] control` lists it (it is in no default); the key of the Office pane's page that the host's own web server admitted (`[host.web] office_local`) holds it whenever the file names a mail account and `[host.mail] tools` is not false, so the pane's chat has the tools with no step; a host run for a portal gives it to no key; a task another agent handed out gets none.

- **Backends (`canoa::mail_backend`).** Mail backends are Guatiao `mail_backend` providers discovered from `bundled::INCLUDED` (`canoa-microsoft-mail` provides `"ews"`, `"graph"`, `"outlook"`) and any library or source listed in `[host.extensions]`. `mail/accounts` returns both `accounts` (each with `backend_title` and `details` from the backend's validation) and `backends` (each `BackendInfo` schema and form so Settings draws the add form dynamically).
- **Accounts.** `[host.mail.accounts.NAME]` (name: 1 to 32 lower-case letters, digits, `-`, `_`): `backend` (provider id, e.g. `"ews"`, `"graph"`, `"outlook"`, or an extension backend), `timeout_secs` (seconds, at least 1, no ceiling, default 60), optional `id` (the entry of the host's account store holding its secret), optional `password_env` (read before `id`), plus backend-specific settings validated by `MailBackend::validate`. canoa.cfg holds no inline `password`. `canoa mail list|add|remove` (`mail/commands.rs`) change it: `add NAME --backend ID [--email --server --autodiscover --user --profile --timeout-secs]` checks canoa.cfg, validates through `MailBackend::validate`, asks for a password when `PreparedAccount::needs_secret` is true (no echo at a terminal, a line from standard input otherwise; an empty one is refused), keeps it under a new id, writes the table, and forgets it again if the file cannot be written; `list` prints name, backend, details, and state, `--format json` the same as objects; `remove` takes the table out and forgets the stored password. The backend is opened (`MailBackend::open`) the first time a tool needs it.
- **Tools.** `mail_list {account?}` (accounts, folders with counts), `mail_search {query?, from?, to?, subject?, folder?, after?, before?, has_attachment?, unread?, flagged?, limit?, offset?, account?}` (default 25, at most 100; with no account every account is searched and one that fails is reported in `errors`), `mail_read {id | message_id | item_id, account?, thread?, max_chars?}`, `mail_related {id | message_id | item_id, account?, limit?}` (each result has `related_by`: `conversation`, `subject`, `person`), `mail_draft {to, cc?, bcc?, subject?, body, account?}` or `{reply_to, reply_all?, body}`, `mail_move {ids, folder}`, `mail_archive {ids}`, `mail_update {ids, read?, flag?, add_categories?, remove_categories?}`. A message id is `ACCOUNT:` and the backend's own id; one change names at most 50 ids of one account. `message_id` and `item_id` search across accounts via `Mailbox::find_by_message_id`.
- **Never sends.** There is no tool or `Mailbox` call that sends. A draft is saved in Drafts, and the answer says `"sent": false`.
- **Asked first.** `mail_move`, `mail_archive` and `mail_update` read the named messages from the mailbox, put them and the change to the person as a `session/request_permission` on the client the session belongs to, and change nothing until the answer comes back from that client (`Access::approve`). One change per session waits at a time.
  `canoa mail list|add|remove` (`mail/commands.rs`) change it: `add NAME --backend ews|outlook [--email --server --autodiscover --user --profile --timeout-secs]` checks canoa.cfg would still be read with the table in it, asks for the password through the front (no echo at a terminal, a line from standard input otherwise; an empty one is refused), keeps it under a new id, writes the table, and forgets the password again if the file cannot be written; `list` prints name, backend, server or email and a state (`password stored`, `needs a password`, `password from VAR`, `needs VAR set`, `signs in with the Windows logon`, `signed in by Outlook`), `--format json` the same as objects; `remove` takes the table out and forgets the stored password. The store is the provider `[secrets] accounts` names; a host with no home reads no stored password. An `http` address is accepted only for this computer. `outlook`: `profile`, `command` (the program and arguments that run the helper; it is given the helper script on standard input). The backend is made the first time a tool needs it, so a password set after the host started is used and a server that is down does not stop the host.
  A message a mail program is showing is named without an id from these tools: exactly one of `id`, `message_id` (its Internet message id, `<abc@example.com>`; the server compares it whole, so the brackets are tried both ways) and `item_id` (the server's own item id, an Exchange id in its EWS form) is given, `message_id` and `item_id` are looked for in every account in the file's order, or only in `account`, and the first account that holds it answers (an account that cannot be searched is named in the error when none does); the answer carries the usual `ACCOUNT:` id for every other tool. `Backend::find_by_message_id` is one `FindItem` with a `message:InternetMessageId` restriction over the whole mailbox (Exchange Server), `$filter=internetMessageId eq '...'` on `/me/messages` (Graph) and a DASL restriction on `PR_INTERNET_MESSAGE_ID` over every mail folder of every store (classic Outlook). Results are JSON text with a `note`; an error has `isError`. The shapes follow `kb_*` where they fit: a list of results with ids to read, never the body, and a read by id.
- **Mail is data.** Every string of a message is stripped of control, direction and zero-width characters and cut (subject and names 300 characters, body `max_chars`, default 20000, at most 200000, newlines kept); every answer carries the note and the skill says the same.
- **Related mail** (`canoa::mail_backend::related`) and thread summaries (`default_summaries`, `default_thread`) run over a backend's `Mailbox` methods (`search`, `summaries`, `thread`).
- **Tests.** `cargo test -p canoa-microsoft-mail` runs the EWS/Graph/Outlook connectors and loopback stand-ins (plus `sspi_server.rs` on Windows); `cargo test -p canoa-host --lib -- mail control::mail_setup` and `store::mcp::extra_tests` verify `BackendCatalog`, `Mailboxes`, `canoa mail` commands, `mail/accounts` and `mail/add` control RPCs (including third-party extension backends), and the MCP mail tools.
  `auth = "windows"` is `Transport::post_negotiate`: a `Network::login_agent` with a Negotiate rule for the server's host answers the `401` (Kerberos, then NTLM from the logon session; an NTLM exchange has three legs on one connection and the body goes with the last; a fresh agent and so a fresh exchange per call). A server that offers no scheme the logon can answer is left at its `401`, which `post` reports with the schemes offered (`it accepts Basic`); a login that fails is `MailError::Auth` naming the logon. Off Windows the build has no Negotiate (`coqui-syshttp`'s `negotiate` feature is on for Windows only), so the exchange fails there with that error. The tests' stand-in completes the exchange with the system's own security package (`mail/sspi_server.rs`, Windows test code, the one `unsafe` in the tests of this crate).
  `Tokens` holds a token until five minutes before its `exp` claim (ten minutes' worth when it has none) and asks again once after a 401. Every request has `Prefer: IdType="ImmutableId", outlook.body-content-type="text"`. A search with `text`, `from`, `to` or `subject` is one KQL `$search` (`(words) AND from:"x" AND received>=DAY AND hasattachments:true`; Graph does not combine it with `$filter`, `$orderby` or `$skip`, and gives no count), and `unread`/`flagged` are then applied to the pages returned; any other search is `$filter` (opening with `receivedDateTime ge ...`, since Graph sorts only by a property the filter names first) with `$orderby=receivedDateTime desc` and `$count=true`. Pages are followed through `@odata.nextLink` only at Graph's own origin, until the offset and limit are met. Drafts are `POST /me/messages` (text body) or `createReply`/`createReplyAll` with the text as `comment`; no `send`, `sendMail`, `reply` or `forward` is ever called. `Change::Archive` moves to the well-known `archive`, then to a folder named Archive when Graph says `ErrorFolderNotFound`.
  Not run against a real tenant: the `$search`/`$filter` limits above, the WAM scope and `wam_compat` property, and the registration's redirect URI are from Microsoft's documentation.
