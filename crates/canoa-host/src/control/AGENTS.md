# `canoa-host` control channel, worktrees, and pairing

## The control channel (`canoa_host::control`)

What belongs to no agent entry: the session ledger, the worktrees and, later, the overlay store. One host-level service,
named `@control` (the `@` is not a name an entry can have), speaking JSON-RPC 2.0, one message to a line as ACP does, but not ACP:
no `initialize`, requests and their answers only. Errors: `-32601` no such method, `-32602` bad params, `-32001` **denied** (the
caller has no grant for it), `-32002` **refused** (a limit), `-32003` not found.

**Who reaches it, and as whom**

- *The app*, in this process: `Local::open("@control")` (`canoa_ffi_link_open` with that entry name). The caller is the **owner**: every
  method, every record. Nothing on a network can obtain a `Local`.
- *A paired client*, from the outside: only when `[host.control]` names an address or pipe (`listen`, as an entry has it; default
  none, so no network control) and lists the key under `grants`. The connection proves its key as an entry's does (same method,
  same pairing); a paired key `grants` does not name is turned away after the proof, as an entry's `peers` turns one away. The
  caller is that **peer**: only the methods its grants name.

```toml
[host.control]
listen = "127.0.0.1:0"                              # or a pipe, as an entry has it; without it there is no network control
grants = { "sha256:…" = ["ledger.read", "ledger.write", "worktree", "store.read", "folders", "files", "config.read", "config.write", "config.write.sessions", "upload", "host.restart", "overlay.read", "overlay.write", "store.programs", "accounts", "discover", "usage", "terminal", "state", "workspace.open", "hosting"] }   # per key; a key not here gets nothing
max_records = 10000                                 # ledger records the host keeps, per host; the oldest by `updated` are refused at, not dropped
max_record_bytes = 262144                           # one ledger record
max_upload_bytes = 8388608                          # one uploaded file, sent in chunks of at most 512 KiB
max_upload_total_bytes = 268435456                  # what one key may keep uploaded
max_uploads = 256                                   # files one key may keep uploaded
```

**Speech providers** (`[speech.NAME]`, grants `voice` and `voice.setup`) turn audio a client captured into text on this host, so a page and every platform
reach one. A table names a kind, `provider = "speech_command"` (a program that reads the audio on its standard input and writes text: a script of the Canoa SDK,
`CommandSpeech`, that ships in the host and runs in its JavaScript source) or `"speech_endpoint"` (an HTTP speech-to-text address and model, `canoa::speech::builtin`'s
`EndpointSettings`), and that kind's settings, which are read when a method is called, so a change in the file applies at once. A table may instead name where its
provider's code comes from, as an entry of canoa.cfg does: `library` (a Guatiao library file) or `source` (a Guatiao source file, or `bundled:js` for the host's own QuickJS,
with `source_settings` such as `dirs`, and `import_search`; relative paths are taken from canoa.cfg's folder), and `provider` is then an id that registry offers: the
`[say.NAME]` tables of text to speech take the same keys. Those keys are the host's, not settings of the provider: `speech/providers` lists the table's `settings`
without them and `speech/configure` keeps them when the settings are saved. A library or source runs as this host does, so naming one is the person's, in canoa.cfg; a
table naming both, or an origin without the provider, is listed with `problem`. `speech/providers` answers each kind's JSON Schema and its guatiao-intake form, so a
settings screen draws them as it draws any provider's, and every table with what the provider says of itself or why it cannot be built; a setting the schema marks
a secret (an endpoint's key) is never answered, only listed in `secrets_set`. The table is not a section `config/set` or `config/get` reaches, because it names
programs and holds keys: `speech/configure` writes it (a setting the schema does not name is refused; a secret left out or empty keeps what the table had,
`clear` names the ones to take out; what it saves must build). A recording is `speech/open`, `speech/push` as often as chunks arrive (the call returns when the
provider has taken the chunk, so a slow provider slows the sender), then `speech/finish` (the text and its front matter) or `speech/cancel`. Programs start
through the host's own spawner.

A table may carry `offer = "<offer id>"`, which says Canoa made it from an offer: it is not one of the kind's settings, `speech/providers` answers it as `offer`
(and a client that knows the offer is local prefers it when the person never chose a service), and `speech/configure` keeps it when the settings are saved.
`speech/enable` `{offer, name?, model?}` makes the table of an offer that needs no form. The id of a Store type whose `model_store` offers a `speech` service that is a program (`command`) writes `provider = "speech_command"` with the `program`, `args` and `input` the library's `service` answers for the host's own copy (`ServiceReport::command`; the library is asked with `ServiceQuery::program`, the launch path of the first store's managed copy) and `offer = "<type id>"`: the model is the install's channel, so another model is another install, then `speech/enable` again. The id of a Store type whose `model_store` offers a `speech` service that is a server (`model` required, any name that is text of at most 100 characters) writes `provider = "speech_endpoint"`, `model`, `service = "<type id>"`, `offer = "<type id>"`: no address, which changes with each start of the service, so the host asks the type's library (`ModelStore::service`) for it whenever a recording opens, and calls the route the library names there (with `request = "local_file"` when it says the recording is a file on this computer). `service_address = "http://127.0.0.1:PORT"` in a table names the service instead.
The model is never loaded by Canoa: `speech/providers` answers `problem` (the library's words) while the service is not running, and the service's own words come back when the model is not loaded. A host with no library that offers one has no such offer, and a table that names a service it does not have cannot be built. `SERVICE:NAME` writes an endpoint table for the address the service's description says takes a recording, with `account = "NAME"`, `offer = "SERVICE:NAME"` and the model (the description's first by default); the key is read from the account's store, from the credential the description names, when a recording opens and is never written to canoa.cfg or answered. Only accounts of a kind the description names (it provides the service's standard, and its model API starts from the service's address) whose setting that moves that address (the kind's endpoint slot names it) is unset or the same are usable; any other, a ChatGPT sign-in among them, is listed with that reason, since an account that is not a key for the service was not measured against it. The default name is `SERVICE-NAME`; a table that names a removed account is listed with `problem`.
The services are the `account_speech` providers of the libraries this build carries and of the entries and extensions of canoa.cfg: a build with none offers no account. `account`, `service` (the id of a Store type), `service_address` and `offer` are the host's keys of a table, not settings of its kind, and `speech/configure` keeps them when the settings are saved.
`canoa-whisper`'s offer writes `speech_command` running `whisper-cli -m <model> -f - -of canoa -nt -np -l {language_code|auto} --prompt {vocabulary}` with a WAV
stream on its standard input (`-of` only makes the program print to its standard output, which it does not for a stream otherwise; nothing is written to a
file). A service's model is `speech/open`'s `model`, applied to `speech_endpoint` providers only.

**Speech output** (`[say.NAME]`, grants `voice` and `voice.setup`) is the other direction: the host turns text into audio for a client that has no voices of its own, so a page and every platform can read a reply aloud. A table names a kind, `provider = "speech_say_command"` (a program that reads text and writes audio), `"speech_say_endpoint"` (an HTTP address in the shape of OpenAI's `audio/speech`), `"speech_say_piper"` (Piper over a folder of voices) or `"speech_say_system"` (the operating system's own voices: Windows PowerShell's desktop synthesizer, `say` on macOS, `espeak-ng` elsewhere), and that kind's settings (`canoa::speech::builtin`'s `CommandSaySettings`, `EndpointSaySettings`, `PiperSettings` and `SystemSettings`), read when a method is called. Two providers need no table: `system` is always offered, and `piper` when the Store installed Piper (a `[say.piper]` table whose `program` or `voices_dir` is empty takes the Store's copy and its `voices` folder); a table of the same name replaces either.
`speech/voices` answers each kind's JSON Schema and form, so a settings screen draws them as it draws any provider's, and every provider with what it says of itself (`models`, `styles`, `speed`, which request fields it `uses`), where the text goes (`leaves` `no`, `maybe` or `yes`, the `endpoint` when there is one and `words` saying it in a sentence) and its voices, which are asked of the provider at most every 30 s (`voices_problem` says why they could not be); a setting the schema marks a secret (an endpoint's key) is never answered, only listed in `secrets_set`. `speech/say_configure` writes the table under `voice.setup` as `speech/configure` does. An utterance is `speech/say` (the provider starts; a voice, model or style it does not list is refused `-32002` naming the ones it has), then `speech/audio` for each next piece: the client pulls, the provider holds back at its own buffer, so a player that is behind slows the provider and nothing grows here. The audio is 16-bit little-endian PCM at the `rate` and `channels` `speech/say` answered. `done` ends it; `speech/stop` ends it early; an utterance nobody called for in 120 s is ended. Programs start through the host's own spawner.

**A terminal** (`terminal/*`, grant `terminal`) is a shell the host starts for the person on a pseudo-terminal (ConPTY on Windows 10 1809 and later, `openpt` on Unix), with nothing filtered, restricted or confirmed beyond the grant. It
belongs to the link that opened it and needs one that can carry notifications (a request sent to `handle` alone is refused `-32002`); when the link ends, or on
`terminal/close`, the shell and everything it started end (a job object on Windows, the shell's process group on Unix: a process that left its group on its own is not reached).

- `terminal/open` `{"cols"?, "rows"?, "cwd"?, "shell"?}` (`shell` an id `shell/list` gave, never a program; one this host did not find is refused `-32002` naming `shell/list`; cells 1 to 1000, default 80 by 24; `cwd` an absolute folder that exists, default the user's home) -> `{"id", "shell", "cwd", "notice"?}`; `cwd` may be a folder on a share, answered as `\\server\share\...`, and `notice` says when the shell (`cmd.exe`) cannot start there and opened in its own folder. The shell is the request's `shell`, else `[host] shell` (an id of `shell/list`, else a program), else `$SHELL`, else `/bin/sh` (Windows: `pwsh.exe`, `powershell.exe`, `%COMSPEC%`); a request names an id of the list and never a program. On Windows a bare name is found on `PATH` (absolute folders only) and the shell is started by its absolute path, never from the folder the host is in; a path may hold spaces. At most 8 terminals open on a link (ended ones count until closed, 32 at most) and 32 on a host, refused `-32002` with the limit.
- `terminal/write` `{"id", "data"}`: `data` is base64 of at most 16 KiB of what was typed. It is queued (32 writes) for a thread that writes to the shell, so a shell that is not reading holds up only its own terminal: a full queue is refused `-32002`, and the person sends again.
- `terminal/resize` `{"id", "cols", "rows"}`. `terminal/scrollback` `{"id"}` -> `{"data", "end"}`: the latest 256 KiB the shell printed, base64, and `end`, the number of bytes printed since it started. `terminal/close` `{"id"}` -> `{"closed": true}`.
- Pushed, with no `id` of a request: `{"method":"terminal/output","params":{"id","data","end"}}` as the shell writes (at most 16 KiB of bytes in a message, base64; `end` is the position just after them, so a view that read the scrollback drops what it already has), and `{"method":"terminal/exit","params":{"id","code"}}` once the shell has ended (a signal is 128 plus its number; not sent after `terminal/close`). Nothing is read ahead of the link: the host writes a chunk and waits for the link to take it, so a slow client slows the shell and the host holds no more than the scrollback; a link whose queue is full is waited for, and the shell is ended only when the link has ended.
- Errors: `-32602` a field is not well formed, `-32003` this link has no such terminal, `-32002` a limit, a shell that did not start (the reason names the program) or an ended terminal.

**A page's files** (`fs/list`, `config/*`, `upload/*`, `host/restart`) are what a web page, which cannot touch the disk or run a
program, asks its host to do as the user. Each is behind its own grant, so a key given only the ledger gets none of them.

- `fs/list` `{"path"?: absolute, "hidden"?: bool, "files"?: bool, "offset"?, "limit"?}` -> `{"path", "parent", "entries": [{"name", "path", "dir"}], "more", "next"}`,
  folders only unless `files`, dot names only with `hidden`, folders first then by name. A page is cut from that sorted whole: `limit` entries
  (`DEFAULT_LIST`, 1000, unless the request names another, which has no ceiling) from `offset`, and `next` is the `offset` of the following
  page, null on the last (`more` is `next` is not null), so a folder of any length is listed whole.
  With no `path` it lists the places to start from: for a key the user's home and the working roots of the entries the key may use
  (all keys when an entry has no `peers`); for the owner every drive or `/`. A path must be absolute with no `.` or `..` and, once
  every link is resolved, under one of those places; a path outside them and one that is not there are the same answer (`-32003`).
  An entry whose link leads out of the places is not listed. `parent` is null where the parent is outside them. Every name is
  listed, with each control, direction or invisible character shown as `<U+XXXX>` (`path` is the real one). A key that also holds
  `files` is not kept to those places: it lists whatever the host's account can, anywhere (the places to start from are then the
  home and every drive or `/`), any absolute path, links and network shares included, and `parent` is offered wherever it is.
- `fs/read` `{"path": absolute, "max_bytes"?: positive whole number}` -> `{"path", "name", "size", "kind": "text"|"image"|"binary", "mime": string|null, "truncated", "data": base64|null}`, the start of one regular file, for a preview (grant `files`). It reads what the host's account can read, wherever it is: any drive, a network share or a link the operating system follows. `max_bytes` defaults to `DEFAULT_READ_BYTES` (256 KiB) and an answer carries at most `READ_PAGE_BYTES` (512 KiB), the most a page's transport carries once in base64, which is a page and not a limit on the file: `offset` (default 0) reads the next one, `next` is where it starts (null at the end), `size` is the whole file and `truncated` says the bytes stop short. A page far into a file is told what it is by the file's start. `kind` is `text` (valid UTF-8 with no zero byte; a character cut off by the limit does not make it binary), `image` (PNG, JPEG, GIF or WebP by their first bytes, never SVG; every page of one carries its `data` to be put together, and the answer says nothing of its dimensions, so the client bounds what it decodes) or `binary` (no `data`).
  `name` shows every control, direction and invisible character as `<U+XXXX>`. The only refusals are for what cannot be read as a file, each with its reason in the message: `-32602` for a path that is not absolute, a folder, anything that is not a regular file (a pipe, a socket or a device, which could wait for ever; the file is also opened without waiting, in case the name became one after it was looked at) and `max_bytes` that is not a positive whole number or an `offset` that is not a whole number; `-32003` when there is no such file or the account cannot see it; `-32002` with the operating system's own words when it cannot open or read it.

- `fs/info` `{"path"?: absolute, "paths"?: [absolute]}` (at most 64 in all) -> `{"folders": [{"path", "exists", "folder", "repository", "root": string|null, "why"?}]}` (grant `folders`): each place as asked, whether it is there and a folder, and whether it is in a git repository (it or a folder above it holds `.git`, a folder or a file) with that folder as `root` (null for a key when the root is outside the places it may browse). A place the key may not see is `exists: false` with `why`.
- `fs/mentions` `{"path": absolute, "max_entries"?: 5000 (at most 20000), "max_depth"?: 8 (at most 32)}` -> `{"path", "entries": ["a.txt", "src/", "src/main.rs"]}` (grant `folders`, the places `fs/list` keeps to): what an `@` offers inside a session's folder, relative with `/`, a folder ending in `/`, nearest first. In a git repository the files git lists (`ls-files --cached --others --exclude-standard`, 10 seconds, 16 MiB, run with every `GIT_*` variable removed and `core.fsmonitor` off, so nothing from the repository runs), else the folder is walked to `max_depth`. Links are neither followed nor listed; a name with a control, direction or invisible character is left out; a path that is not a folder is `-32003`.
- `fs/resolve` `{"path": absolute folder, "name": relative}` -> `{"path", "folder", "size"}` (grant `folders`): the file or folder `name` names inside the folder. A name that climbs (`..`), is absolute, has a drive, a backslash or a control character, is not there, or is or leads through a link out of the folder is `-32003`.
- `fs/realpath` `{"path"?: absolute, "paths"?: [absolute]}` (at most 64 in all) -> `{"paths": [{"path", "real": string|null, "why"?}]}` (grant `folders`): each path with the links followed in the deepest part of it that exists and what is not there yet after it as written, the way the app judges where a remembered rule for a path reaches. `real` is null, with `why`, for a path that is not absolute or has `.`, `..` or a control character, a link that cannot be followed (a dangling one), nothing of it found, and for a key not holding `files`, a place outside the home and the working roots of its entries, or one a link inside them leads out of.
- `fs/repo_root` `{"path"?, "paths"?: [absolute folders]}` (at most 64) -> `{"folders": [{"path", "root": string|null}]}` (grant `folders`): the nearest folder at or above each (which need not exist) that holds `.git`. A linked worktree or a submodule, whose `.git` is a file naming `<main>/.git/worktrees/<name>`, answers `<main>`, so worktrees of one repository have one root. Null for none, and for a key not holding `files` when the root is outside its places.
- `fs/guards` `{}` -> `{"home": string|null, "config": string|null}` (grant `folders`): this user's home folder and the folder holding canoa.cfg, which no remembered rule for a path may reach.
- `fs/scratch` `{"session", "source"?, "handler"?, "now"?}` -> `{"path", "made"}` (grant `folders`) makes the folder the person's own `[sessions] workspace` (canoa.cfg; `${documents}/Canoa/scratch/${session}` when it has none) names for a chat, private to the user on Unix; `fs/scratch_remove` takes the same and removes that folder only when it is empty (`{"path", "removed"}`); `fs/scratch_preview` `{"template", "session"?, ...}` -> `{"path"}` only works out what a template being edited would make and makes nothing. `session` is letters, digits and hyphens, at most 36; `source` and `handler` are each made one safe path segment; `now` is the person's local time as `2026-11-17T10:30:05` (this clock's UTC when absent). A template needs `${session}` and only the variables `documents home session date time datetime handler source host fqdn`.
- `profile/canonical` `{"path"}` -> `{"directory": string|null}` (grant `overlay.read`): the folder with its links resolved, when it is an overlay's (under the overlays folder, or one `[overlays]` names with `dir`; a relative path is read from the folder holding canoa.cfg) or a place `fs/list` shows this key. `profile/tree` `{"directory"}` -> `{"directory", "files": {path: base64}}` (grant `overlay.read`): an overlay's folder read whole as its tree digest counts it (no link followed, `.git` and the like left out, at most 4096 files and 64 MiB, and 24 MiB in one answer); any other folder is refused. `profile/project` `{"directory"}` -> `{"directory", "profile": base64|null}` (grant `folders`, the places `fs/list` keeps to): the folder's resolved name and its `.canoa/profile.toml`, which is null when it has none (at most 1 MiB).
- `providers/list` -> `{"providers": [row], "usage_readers": [{id, origin}], "gateways": [{kind, vendor, provider, title}], "agent_entry": {schema, form}, "local_agent": {schema, form}}` (grant `config.read`): the agents the host has loaded, as the providers it loaded say of them. The bundled agents come first, in the order their crates are listed, then the others as they were found. `usage_readers` are the `usage_reader` providers the same libraries and sources offer (the ids an agent entry's `usage` may name), each with its `origin` as a row's, the bundled ones first and an id once, as the first registry that offers it; the app's Add an agent lists them.
  `agent_entry` and `local_agent` describe what an entry of `[host.agents]` and of `[agents]` takes, each a guatiao schema and a guatiao-intake form (a member's widget hint `harness` or `usage_reader` asks for a pick of the harnesses and the readers listed here), which the app draws its Add an agent forms from; every member is a key of the entry the host reads, and `name` is the table's key.
- `profile_items/list` -> `{"items": [item]}` (grant `config.read`): the things a profile may set, as the providers the host loaded say of them: the `profile_item` providers the host carries (`origin` `built-in`: the model, effort, mode, starting instructions and access; `bundled`: a proxy and an identity, JavaScript libraries written with the Canoa SDK (`extensions/profile_items/`, run by the QuickJS the host carries): the proxy item only says which network its values ask for, the proxy is the host's; the files of the items and the sources are kept under the user's own home, `<home>/bundled/NAME-VERSION-DIGEST/`, by `scripts::Bundle` and `scripts::root()`, a temporary folder in this crate's own tests) and those the libraries and sources of canoa.cfg's agent entries and extensions offer (`origin` is the entry's or extension's name).
  An item: `{id, title, help, origin, stored, harnesses, schema, form}`, the schema a JSON Schema of the values it takes (`null` for none) and the form the guatiao-intake document that shows it (`null` for none); `stored` is `setting` for one of the session's own settings, which a profile keeps under its own key (`model = ...`, `access = {...}`), and `item` for the others, kept at `[profiles.NAME.items.ID]`. An item whose id an earlier provider took, or whose description is unusable, is not listed. An item a profile holds values for that nothing offers is kept and not applied.
- `settings/sections` -> `{"sections": [section]}` (no grant: the application's own pages are the person's own preferences, so any key reads them; a key without `config.read` is listed only the `built-in` ones, and the pages a provider adds, whose forms hold what the host keeps, need `config.read`): the pages and groups of Settings, as `settings_section` providers say of them: first the sections the application draws itself (`origin` `built-in`: General, Appearance, Notifications, Voice, Shortcuts, Sources, Profiles, MCP servers, Permissions, Accounts, Mail, Shells, Usage, Store, Extensions and About, in that order, each with a heading, icon and search words and no schema: the app picks the widget by the id, and leaves out one whose controller its build or key lacks), then the bundled libraries' and those of canoa.cfg's entries and extensions (`origin` is `bundled` or the entry's or extension's name).
  The app shows the `built-in` pages from `app/lib/settings/built_in_sections.dart` (what the host lists of its own, written and checked by `CANOA_WRITE_SECTIONS=1 cargo test -p canoa-host --lib settings_sections`) until the host answers and for good when it cannot or refuses, so Settings is never empty. A section: `{id, title, help, icon, group, under, keywords, origin, stored, schema, form}`; `stored` is `config` (the host keeps the values in `[settings.ID]` of canoa.cfg) or `provider`; `schema` and `form` are the guatiao schema and guatiao-intake form the app draws.   For a section kept in `config` the host keeps each sensitive member as the named secret `settings/ID/MEMBER` in the provider `[secrets] accounts` names (the operating system's store by default, as for the accounts' credentials), never in canoa.cfg: a secret an earlier host left in `[settings.ID]` is moved there the first time the section is read or saved (and one that cannot be moved stays and refuses the save, rather than being dropped); a `provider` section is handed its secrets, which it keeps itself. `settings/section_set` `{id, values, clear?}` -> `{id, saved: true}` (grant `config.write`): checks `values` (an object, at most 64 KiB, members the schema names, each of its type, the required ones there) and keeps them, replacing the section's values; a sensitive member left out or empty keeps what was kept unless `clear` names it (a secret kept as above is checked against the schema with its kept value, and a provider that cannot answer leaves it out of the check). The grant `config.write` is as much as the app's own preferences: a `provider` section's `write` runs the provider's code, which the host's own extensions already do.
- `panel_tabs/list` -> `{"tabs": [tab]}` (grant `config.read`): the kinds of tab the application's panel can open, as the `panel_tab` providers the host carries (`origin` `built-in`: `terminal`, a shell on the host, and `logs`, the host's own log) and those the libraries and sources of canoa.cfg's entries and extensions offer (`origin` is the entry's or extension's name) say of them. A tab: `{id, title, help, icon, shows, shell, url, origin}`, `shows` `terminal`, `log` or `page` (`url` is the page's loopback address; the app offers a page only when its host runs on the same computer, and opens it in the person's browser). The built-in log is `canoa_host::host_log`, the last 2000 lines the `canoa` program or the application's log routing wrote, without colour codes.
- `looks/list` -> `{"looks": [document]}` (grant `config.read`): the colour-token documents the loaded agents carry (an `agent_vendor` provider's `look`), the bundled agents' in their order. A document is `{id, label, vendor, light, dark}`; `id` is the family the app names (`claude`, `chatgpt`), `vendor` the provider whose conversations it draws (`claude`, `codex`), and each brightness holds `#RRGGBB` strings for `page`, `rail`, `bar`, `selected`, `surface`, `raised`, `text`, `muted`, `accent`, `onAccent`, `success`, `warning`, `danger` (optional `border`), the numbers `radius`, `controlRadius`, `railWidth`, and a `chat` table of `user`, `notice`, `added`, `removed`, `code`. Nothing in them is secret. A client ignores a token it does not know and takes its own default for one that is missing.
- `trust/list` -> `{"projects": [{"directory", "sha256", "trusted"?}]}` (grant `config.read`), `trust/set` `{"directory", "sha256"}` (grant `config.write.sessions`) and `trust/revoke` `{"directory"}` (grant `config.write`) -> the same list: the projects whose profiles the person trusts, kept in `trust.json` beside canoa.cfg. `trust/set` reads the profile now and refuses one whose SHA-256 is not the one named, so what is trusted is what was shown; a folder with no profile cannot be trusted; revoking needs no folder to be there.
- `config/get` `{"section"}` -> `{"section", "value": object|null, "restart": false}` and `config/set` `{"section", "value": object|null}` (the app this host runs in, the owner link, alone also reaches `agents`, `desktop`, `profile`, `skill_pins`; no paired key does)
  -> `{"section", "restart"}` read and write one table of the person's own canoa.cfg (the file `--config` lists last), in the format
  it is in (a `.yaml`/`.json` name or a `#!` first line, else TOML). A TOML file is edited in place with `toml_edit` (`cfg_edit.rs`): the one table is set or removed and every other byte, comment, order and spelling stays; YAML and JSON have no layout of their own and are written whole. Only `SECTIONS` are named
  (`appearance attachments connections defaults loadouts network notifications overlays permissions profiles sessions store usage voice`); any other, `host`,
  `agents`, `profile`, `desktop` and `skill_pins` among them, is `-32001`, since those name programs to run or what may run. `value` is
  an object of at most `MAX_SECTION_BYTES` (256 KiB) or null, which removes the table. The text that would result is read by the host's

  true for the sections the host itself reads at start (`permissions usage`): they apply after `host/restart`; `[overlays]`, `[profile]`, `[loadouts]` and `[defaults]` reach the next session of an entry that is the host's own or names no profile, with no restart. A host not
  started with a canoa.cfg refuses both (`-32002`).
- `upload/put` `{"name", "data": base64, "done"?: bool}` -> `{"id", "path", "name", "size", "done"}` keeps a file in
  `control/uploads/<digest of the key's id>/` (`0700`; the file `0600`) as `<12 hex digits>-<name>`, the name cut to its last
  component and to 100 bytes with anything but letters, digits and `.-_ ` made `_`. A chunk is at most `MAX_CHUNK` (512 KiB), since a
  page's transport carries no message over a mebibyte: a larger file starts with `done: false`, which answers an `id`, and goes on
  with `{"id", "offset": the size so far, "data", "done"?}` until `done` is true or absent; an `offset` that is not where the upload
  stands, or an `id` that is not this key's, is `-32002`. Until it is done the file is in the folder `.partial`, so a file called `x.part` is only a name. One upload step runs at a time, so the limits are checked and spent together. `max_upload_bytes` (one file;

Only the person running the host (this process's own app) asks for it: a key is refused whatever it holds. The peer proof the remote host requires is still end to end inside the WebSocket; the TLS ends at this host.

A skill whose name is not a skill name or not its folder's carries a `problem`; a `SKILL.md` that is no skill (front matter that does not name and describe it), one with `metadata.internal: true` and a repeated name are left out and counted in `skipped`; at most 1024 are listed (`truncated`).

It starts the programs it asks the version of, so a key needs `overlay.read` and `store.programs`.

A step that fails is `-32002` naming it with the end of what it printed. The person's own package-manager settings (`PIP_*`, `.npmrc` of the user) apply. A key needs `overlay.write` and `store.programs`. `overlay/remove` runs setup as `remove` first and deletes the environments, state and record. `store/read_ahead`'s `contents` gain `prepares`, the lines of what installing the entry would run.
- `host/which` `{"names": [..]}` (at most 32, each 1 to 64 of letters, digits, `.`, `_`, `+`, `-`) -> `{"found": {name: path|null}}`: the first runnable file of that name in an absolute directory of the host's `PATH` (Windows: with a `PATHEXT` extension); it starts nothing. The folders of the runtimes the Store installed (Node, Python), when their copy is as it was installed, are searched after `PATH`, so the person's own copy comes first. Needs `store.read`.
- `store/contents` `{"label"}` -> `{"document": text|null}` and `store/contents_put` `{"label", "document"}`: the JSON object the app keeps for a catalog (what each entry provides), under the host's `cache/contents/`, one folder for the person and one for each key, so a key never reads another's; a document is at most 8 MiB, a folder holds 256. Needs `overlay.read`.

Needs `overlay.write`.

- **Git** runs as this user from an absolute directory of `PATH` with every `GIT_` variable of the host's removed, `protocol.allow=never` and
  only `https`, `http`, `ssh`, `git` and `file` allowed, no hooks, no fsmonitor, no prompts, 5 minutes at most, and a fetch ended once its
  cache holds 256 MiB. A source on this computer (`file://` or a path) is named by a key only with the `folders` grant, under a working root of an
  entry the key may use (not the home), never in the host's own folders (canoa.cfg's, the overlays', the home it keeps state in) and
  only a repository whose `.git` is a folder; the owner names any. A source on a network share is a place like any other: the owner names it as the file explorer opens it, and a key needs a working root that holds it.
  Git runs from the overlays folder with `GIT_CEILING_DIRECTORIES`
  set to it. At most 64 fetched caches, and 1 GiB in the overlays folder; the history fetched for a check whose plan expired with
  nothing installed is removed. A fetch locks its own overlay or catalog only. A failure says git's first 300 characters, controls made spaces.
- Skills fetched from elsewhere are not part of this: a page gets none, and an overlay that names one reports it as not delivered.

**The ledger** is the list of the person's sessions, kept by the host in its home (`control/ledger.json`, written whole, atomically)
as opaque JSON objects the host never reads into: it keeps an `id`, the record, who put it and when.

- Every record has an **owner**: `"local"` for the app, else the peer's id. A peer sees and changes only the records it owns, and
  `put` makes it the owner whatever the request says; the owner (the app) sees and changes all.
- **Quotas.** `max_records` and 64 MiB of records are each owner's own (the app's, and each key's), the whole ledger holds 256 MiB, and the last 64 MiB are the app's alone, so a full ledger never refuses the app. A bad `ledger.json` is moved to `ledger.json.bad-<ms>` and an empty ledger begins (logged at `warn`); the file is written, synced and renamed, and `control/` and the file are `0700`/`0600` on Unix. A key's connection silent for 15 minutes is ended.
- `ledger/list` returns the caller's own records only; the owner (the app) asks for every owner's with `"all": true`, which a key's request cannot do. The app reads only its own, so nothing a key put is ever taken for a session. `{"after"?: id, "limit"?: 1..=500, default 100}` -> `{"records": [{"id", "updated", "owner", "record"}], "next"?: id}`,
  newest `updated` first; `next` is the `after` of the following page.
- `ledger/put` `{"id": text of 1 to 128 characters with no control character, "record": object}` -> `{"id", "updated"}`; replaces the
  record of that id (a peer cannot replace another owner's: `-32001`); `updated` is the host's clock, in milliseconds. Refused
  `-32002` past `max_record_bytes`, or past `max_records` for a new id.
- `peer/forget` `{}` -> `{"removed": bool}`: a paired key takes its own pairing out of the trust store, the real revoke (its links end within about a second). It needs no grant, and the owner's link, which holds no key, is refused.
- `ledger/remove` `{"id"}` -> `{"removed": bool}`; `ledger/clear` `{}` -> `{"removed": n}`, the caller's own records.
- A request over 16 MiB, or not JSON, ends the connection; `-32700` first when it can be answered.

**Usage records.** The host keeps what its agents spend in its home, `usage/` (files only this user reads): one line a turn and
model appended to `YYYY-MM.jsonl` with `time` (Unix seconds), `account`, `harness`, `model`?, `session_id`, `parent_session_id`?,
`input`?, `output`?, `cache_read`?, `cache_write`?, `cost_micro_usd`?. An agent reports running totals for a session; the host
keeps the last total it saw for each account, session and model (`seen.json`) and writes the difference when the turn ends (a
report with no turn open, at once), so a reconnect, a session loaded again or a restart counts nothing twice. A total that falls
is a counter that started over. A counter the agent never moved, a cost it never gave and an agent that reports no spend leave no
field and no line. The model is the report's own per-model split, else the model the session opened or was set to. Only what
reaches the host from an agent that reports usage is seen, whether or not the client asked notices (the host asks the agent for them whenever it keeps the log and hides them from a client that did not ask). `parent_session_id` is
set on what a delegated task's own session spends: the id of the session that started it, so a parent and its children are each their own lines and a sum over the log counts each once (the parent's figures never hold a Canoa child's).
The allowances an agent reports are kept as the latest for each account (`limits.json`), not appended. Answered by
the `usage` grant (above).

```toml
[host.usage]
keep_days = 400                     # a month's file is removed at start once all of it is older; at least 1
```

**Session history.** The host records each session it serves in the session-history format (`coqui-acp-history`) in its home,
`history/`, one `<sha256 of entry and session id>.jsonl` a session in a directory and files only this user reads (`0700`/`0600`
on Unix). A turn is written when it ends, and a connection that ends inside one writes it as ended with an error, so a stop
loses at most the turn in flight. It records what reaches the agent and what the agent says, after the host's own checks, and
never a message over the limit: a session that passes a limit keeps what it had and nothing more.

```toml
[host.worktrees]                    # no floor above 1 and no ceiling
max_per_repository = 32             # worktrees one repository may hold beside it from the host
git_seconds = 120                   # how long one git command may run before it is ended
```

```toml
[host.history]
record = true                       # false records nothing
max_session_bytes = 16777216        # one session's history; no ceiling (a history is read whole to be moved, so a large one costs memory then)
max_sessions = 1000                 # sessions with a history; a new one past it is not recorded
max_total_bytes = 1073741824        # every history together
```

- Every history method is the owner's alone, over the app's own link: a recorded session holds what the person and the agent said,
  tool output included, which a paired key has no grant to read.

**`worktree/*`** takes the params and answers the results of `_canoa/worktree/*` ("Worktrees" below), with every check of
theirs unchanged (branch names, repositories led out by links or share paths, no hooks, `[host.worktrees] max_per_repository`). The owner (the app)
may name any absolute path on this computer; a key with the `worktree` grant only paths under the `working_roots` of the entries

**Store extensions** (`[host.extensions.NAME]`, `canoa::store::extension`): a `store_extension` provider, loaded from a library or a
source like any other, whose `describe` names the types it adds (`id`: 1 to 32 lower-case letters and digits, not `overlays`,
`skills`, `agents`, `mcps` or `runtimes`; `title`; `icon`?; `stores`: the `program_store` provider ids the same library offers). The
host loads each into a registry of its own, lists its types in `store/extensions`, and plans, applies, reports and removes through the
same `store/*` methods and the same plan the person confirms, so an extension writes no installer. One that does not load, names a
type already taken, or a store it does not offer (or one of the built-in ones) is skipped and logged; the others stay. The app lists
Runtimes and each type after the built-in ones; an installed item the host holds its own copy of has a Remove that shows the plan for
`store/remove`'s uninstall as an install's. The app's Settings, Extensions (for a key that holds `hosting`) lists `[host.extensions]` from
`config/get` `host`, adds, edits and removes one by writing `[host]` back with `config/check` then `config/set` (the host reads it only when
it starts, so the page offers to restart it). `icon` is an app icon's name or a small `data:image/png;base64,` or `data:image/webp;base64,`
picture. `examples/sample_extension.rs` is a stand-in library; `tests/extension_stores.rs` runs it.

**Extensions catalogs** (`[store.extensions.catalogs]`, `store/extension_catalog.rs`, `control/extension_install.rs`). A table of label to git source (`<repository>@<ref>#<file>`), none until the person adds one and never mixed with `[store.overlays.catalogs]`; the file is Canoa's own TOML format, written down in `docs/configuration.md`: `[extensions.NAME]` entries, each pinned (a git or relative `source` by the `pin` tree digest, an `http` or `https` URL by its `sha256`), with `provider`, `load` (or `runtime`), `needs` and informational fields. The reader is `store::extension_catalog` (an entry is refused alone, with a class: `invalid-name`, `duplicate-name`, `invalid-entry`, `invalid-source`, `invalid-pin`, `unpinned`, `ref-not-allowed`, `leaves-repository`; where a source is, and what it needs to reach it (a path, `file:`, `ssh`, credentials, a query, `http`), is never a reason), and `StoreIndex` keeps each catalog under `extensions:LABEL`, a key no overlay catalog's label can take, fetched into `.catalogs/.extensions/LABEL.git`.
The catalog is fetched with the person's own git settings; a source an entry names is fetched with none of them unless it is in the catalog's own repository. `extension/catalogs` answers like `store/index` (`kind: "extension_catalog"` sources and `kind: "extension"` entries with `extension: {provider, pin | sha256, load?, needs}` beside `origin`). This host loads one library file: a tree entry names it with `load`, a URL is the library; or a package of scripts: `runtime = "js"` (or `python`) names no file, the folder is the library, and the install writes `source = "bundled:js"`, `source_settings = { dirs }`, `pin` and `root` instead of `library` (`runtime = "python"` is refused at the plan, the host carries no Python source). `extension/catalogs` entries carry `runtime` in `extension`. The same bytes install on every platform; `tests/extension_install.rs` installs a package from a local catalog on two hosts and lists it after a restart.
Nothing of an extension is kept before its digest has been computed over what was fetched; the host records `pin` and `root` (or `sha256`) in canoa.cfg and checks them again, before the file is opened, each time it loads the extension, and an extension whose bytes changed is skipped and logged. An extension named by hand has no digest and is loaded as it always was. `tests/extension_install.rs` installs the sample extension from a local catalog and loads it after a restart.

(agents, their MCP servers, tools), after the person's own `PATH` entries so their own copy wins; a program started with no `PATH` gets none.

one normalized list, so a client reads cards from one call and not one fetch an entry. `store/index` `{"refresh"?: bool, "icons"?: bool}`
-> `{"schema": 1, "sources": [...], "entries": [...]}`. A source is `{"id": "catalog:LABEL" | "programs", "kind", "label"?, "spec"?,
"commit"?, "checked" (ms), "stale", "refreshing", "name"?, "description"?, "problem"?, "entries"}`; an entry is `{"id", "kind": "overlay" |
"skill" | "program", "catalog", "name", "summary", "source", "origin": {"kind", "location", "ref", "path"} | null (the source in parts, null for a refused entry), "version", "tags", "requirements", "pin", "icon", "contents": {"skills",
"hooks", "env_scripts", "mcp_servers"} | null, "problem"?}` plus `homepage`, `repository`, `license` and `authors` where the catalog
says them (a program entry also carries `program`, `provider` and `channels`). The sources are canoa.cfg's, never a key's: a key names
none, so the host fetches only places its owner chose. `contents` and `requirements` are read from the manifest of an entry that lives in
the catalog's own repository; one elsewhere is the catalog's claim only. Nothing runs: no hook, setup or install.

Every type's catalogs are `[store.TYPE.catalogs.LABEL]`, one reader (`store::catalogs::read`): a bare string is `{ provider = "read", source = string }`, a table is `{ provider?, ...fields }` with `read` the default provider, `false` takes a default away. The reader never mixes types: `table_of(store, "skills")` is the Skills table only. A catalog is read by a `catalog_source` provider (`canoa::store::source`): `read` (the type's own reader; for overlays and extensions the git path of `store/index`) and `command` (`fields`: `command` list, `cwd`, `file`, `timeout` seconds, default 60) are JavaScript libraries that ship in the host (`extensions/catalog_sources/`, written with the Canoa SDK, kept as files by `scripts::Bundle`) found through a registry as an extension's would be, and the `catalog_source` providers of each `[host.extensions]` library are added beside them (`Sources::add`; an id already offered refuses the whole extension).
A catalog whose provider is not `read` is asked for its text, by `StoreIndex::refresh_read`, each time its index is refreshed (when the time to live ends or a refresh is asked): the provider's text is indexed as a fetched catalog is (no repository, so a relative source or icon in it is refused), keyed by its SHA-256, and a failure keeps the last good index with the provider's reason as `problem`. `command` starts its program through the spawner each `read` is handed (`Reach`: this machine's, with the person's own reach, whose `read_file` reads any absolute path and which keeps and removes no file) and closes its standard input, keeps the end (2 KiB) of what it wrote on standard error for the reason, reads at most 4 MiB of standard output and stops after `timeout` seconds, ending the program's tree; it serves every type (`SourceInfo::types` empty; an extension's source lists the types it serves). Writing a `[store]` that names a provider other than `read` it did not hold takes `hosting` (`config/set` and `config/check`, `Control::guard_sources`).

**Models of a Store type** (`control/stores/models.rs`, `store/sources.rs`'s `Reach`). A Store type an extension adds (`ExtensionType`) may name a `model_store` provider of the same library (`models`): `Stores::with_included_extensions` and `Stores::extended` describe it, refuse the type when the provider is not offered, its description's `problem` says so (a title, a catalog, a table that is not a word or is one the host keeps) or it cannot be described, and keep it with the registry it came from (`ModelStores`); `store/extensions` answers `models: {provider, title}` for such a type. `store/models`, `store/model` and `store/model_setting` call the provider with `Reach`, this machine's spawner with the person's own reach (the one catalog sources get), the type's program (`Stores::type_program`: the managed copy `Programs::launch` verified, else the first copy `Programs::report` finds without running anything) and `Stores::home` (the person's home; `with_home` names another in a test).
The host reads the provider's answers as data: rows are written to JSON as `canoa::store::models` models and each gets `values` from `Files::model_settings(table)`; `model_setting` checks the values against the schema (`forms::check`) before the provider settles them and again after, and writes `[<table>.models."<id>"]` (`Files::set_model_settings`), removing an empty one and an emptied table. The host names no vendor's model, program or table: what a library says is what is drawn, and the speech offers (`control/speech_offers.rs`) are one for each type whose provider has a `speech` service, its address and models asked of `ModelStore::service` each time. Tests copy `examples/foundry_standin` under the program's own name into the only folder of a `PATH` (it keeps its state beside itself) and give the Store a home of its own.

**Skills and MCP servers catalogs through the same sources** (`control/catalog_read.rs`, `store/listings.rs`). `store/catalog` `{"type": "skills" | "mcps", "label", "search"?, "cursor"?}` reads one catalog of canoa.cfg (the label names it; a key never names a place) and answers `{"type", "label", "provider", ...}`; it needs `overlay.write`, as `skill/scan` and `registry/fetch` do, and `overlays` and `extensions` are refused (they are read through `store/index`). `store/catalogs` lists the MCP servers type's official registry first as `{"label": "official", "default": true, "fixed": true}`: it is not in canoa.cfg, cannot be removed, and a table row of that label is a `problem`. For the `read` provider the host reads the type itself:
- Skills: the `source` is parsed as `npx skills add` takes one (`store::listings::SkillSpec`: `owner/repo[/folder]`, `github:`/`gitlab:`, a tree address, a git address, a folder, `#ref` or `@version`, `@name` for one skill) and scanned as `skill/scan` scans (`own` unless the label is `anthropics` with Canoa's own default source), answering `{"commit", "skills": [{"name", "description", "source", "path", "problem"?}], "skipped", "truncated"}`.
- MCP servers: `source` is a registry's address (read as `registry/fetch` reads one, `<address>/v0.1/servers?limit=30` with `cursor` and `search` percent-encoded) or `<repository>@<ref>#<file>` (a file in the list shape, fetched into `.catalogs/registry-<16 hex of the source's SHA-256>.git`), answering the registry's list shape `{"servers": [...], "metadata": {"nextCursor"}}`.
Any other provider is asked for its text (`ReadRequest` with the type's id and the label) every time, and the host reads the text as data: Skills as a listing `{"skills": [{"name", "description"?, "source", "path"?, "ref"?}]}` (answered as above with `commit: null` and `ref`; an entry with no name or source or a repeated name is counted in `skipped`, one with an invalid name or source carries a `problem`, at most 1024), MCP servers as one page of the list shape (items with no `server.name` or marked not latest dropped, `search` words matched against name, title and description, at most 2000). A provider that fails or answers in another form is `-32002` with its reason. What a listed skill's `source` names is fetched with none of the person's git settings, as a `skill/search` hit's is.

## Worktrees

No public API: what `serve` answers on an agent or tool entry with `working_roots` and `worktrees` on (the default), before its agent starts. Off, or with no root, each is `-32602`.

| Method | Params | Result |
| --- | --- | --- |
| `_canoa/worktree/new` | `cwd`, `branch` | `{"path", "branch", "repo"}`: `path` and `repo` written under the root as configured |
| `_canoa/worktree/status` | `path` | `{"exists": false}`, or `{"exists": true, "branch" (null when detached), "detached", "changed", "commits", "listing"}` |
| `_canoa/worktree/remove` | `path`, `discard` (bool, default false) | `{"removed": true, "branch", "branchKept", "commits"}` |
| `_canoa/worktree/diff` | `path`, `base` (a commit's hex id; HEAD when absent) | `{"exists": false}`, or `{"exists": true, "head", "branch", "base", "added", "removed", "files", "more"}`; a file is `{"path", "status" (`A`, `M`, `D`), "added", "removed", "binary", "patch", "cut", "print"}` |

- **A branch** is `canoa/` then runs of `a-z0-9` joined by single hyphens, 70 bytes at most; any other is `-32602` before git runs.
- **A path** (`cwd`, `path`) must be plain absolute, on a drive on Windows (a share or device path is refused unlooked at), under a root as written, and, resolved by `canonicalize`, under a root resolved the same way. A missing `path` is `{"exists": false}` for `status`.
- **Every request** first refuses a repository (`-32602`) when a `.git` file from the directory up to the roots, or its `commondir`, names a share or device; when `git config --local` or `--worktree` holds a key matching `^(filter|include|includeif)\.|^core\.attributesfile$`; when `rev-parse --git-common-dir` resolved is not the main worktree's `.git` (a submodule, `--separate-git-dir`) or is outside the roots; or when it has `objects/info/alternates`.
- **`new`**: the repository's main worktree (`git worktree list --porcelain -z`, its first entry; a bare one refused) resolved must be under a resolved root, and so must its parent; the worktree goes in `<parent>/<name>.worktrees/<branch less canoa/>`. An existing `.worktrees` that is a link or not a directory, a worktree already there, or `[host.worktrees] max_per_repository` (32 unless set) worktrees of the repository already in it, is refused. Then `git worktree add -b BRANCH -- PATH HEAD` from `cwd`; a result whose resolved path is not itself is removed again and refused.
- **`status` and `remove`** take only a worktree `new` would have made: its own top level (`rev-parse --show-toplevel`), not the main worktree, where `new` puts the branch `canoa/<its directory's name>`, whatever its HEAD is now; else `-32602`. `changed` counts what `git status --porcelain=v1 -z --untracked-files=all --ignored=matching --ignore-submodules=all` lists, and `listing` is the SHA-256 of that output in hexadecimal; `commits` counts `rev-list HEAD [refs/heads/BRANCH] --not --exclude=BRANCH --branches --remotes --tags`.
- **`diff`** is read only and takes any repository the checks above accept, not only a worktree `new` made. It lists what differs from `base` in the folder `path` names (paths relative to it): tracked files by `git diff` with no external diff program and no text conversion, and untracked files that are small text, shown as added lines. `patch` holds the hunks with no file header, cut at 96 KiB (`cut`); a binary file, or one over 20,000 changed lines, has none. `print` stands for the file's change, so two reads with one print show it changed the same way. At most 300 files are listed (`more`), the totals count all. Git runs with `--no-optional-locks`, so it never rewrites the index. A `base` that is not a commit of the repository is `-32602`.
- **`remove`** refuses a detached HEAD reaching any commit no branch, tag or remote has, whatever `discard` says, and anything `changed` counts without `discard` (git itself would remove ignored files). Then `git worktree remove [--force] -- PATH` (`--force` only with `discard`), and, when the branch exists and holds no commit of its own, `git update-ref -d refs/heads/BRANCH TIP` at the tip counted: a branch that moved meanwhile stays (`branchKept`).
- **Git** is `git` on the host's `PATH`, run as `git -C DIR -c core.hooksPath=NUL|/dev/null -c core.fsmonitor=false ...` with every `GIT_` variable of the host's removed, `GIT_TERMINAL_PROMPT=0` and `GIT_CEILING_DIRECTORIES` the roots' parents, ended after `[host.worktrees] git_seconds` (120 unless set); a failure is `-32603` `git failed: ` and up to 1 KiB of git's own words, control characters made spaces.
- A request is refused, never forwarded, once the agent runs (`-32600`), and a notification of one is dropped.

## Pairing (`canoa_host::peers`)

```rust
#[non_exhaustive] pub struct Peer { pub id: PeerId, pub state: PeerState }
#[non_exhaustive] pub enum PeerState { Accepted, Waiting { source: Option<SocketAddr> } }
pub fn list(store: &TrustStore) -> Result<Vec<Peer>, PeersError>     // accepted, then waiting, each by id
pub fn accept(store: &TrustStore, id: &str) -> Result<PeerId, PeersError>
pub fn revoke(store: &TrustStore, id: &str) -> Result<bool, PeersError>   // false: the store did not know it
```

A key is paired when the store accepts it. `accept` takes only a key that is waiting, so a person pairs a client by connecting with it once, then accepting the id the client shows.
