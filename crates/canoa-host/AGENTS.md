# `canoa-host` — API header

Header-file-style reference for the `canoa-host` crate, whose command-line program is `canoa`: every public item with its signature, contract and gotchas, so the crate can be used without reading its source. It ships inside the package and is self-contained. Development documentation lives with the source at <https://github.com/Boriken-Dev/canoa>.

MSRV Rust 1.89. Version `0.0.0-alpha.0`, not published (`publish = false`): its git dependencies are not released. It depends on `anycfg` (`bf71f70`, from its repository), `canoa`, `clap`, `coqui-acp`, `coqui-acp-api`, `coqui-acp-bridge`, `canoa-antigravity`, `canoa-claude`, `canoa-codex`, `canoa-foundry` (Foundry Local as a library the host carries: an account provider, a model gateway, a Store program and type, and the SDK engine's helper), `canoa-litellm` (a LiteLLM proxy as an account kind, offered through its library), `canoa-microsoft-mail` (Exchange Server, Microsoft Graph, and classic Outlook `mail_backend` providers, offered through its library), `canoa-sqlite` (the default `history_store`: sessions, their turns and the session list in `sessions.sqlite3`, offered through its library), `canoa-grok`, `canoa-pi` (each agent's source preset, Store recipe and, for Claude, Codex and Pi, coqui-acp provider), `coqui-acp-harness` (`kind`), `coqui-acp-history` and `coqui-acp-provider` and `coqui-acp-secrets` (coqui-acp `34de3e9`), `coqui-aos` (`815aa3c`), `cabuya` (`40123baa`, features `sealed` and `forward`; it brings `coqui-peer-noise`), `coqui-agentic-peer` (`161307f9`), `coqui-peer`, `coqui-peer-webcrypto`, `coqui-transport-pipe` (`1bf161f`), `coqui-transport-guatiao` (`f09bf2d`; `pipe`, `websocket`), `coqui-transport` and `coqui-transport-web` (`websocket`),

`CANOA_OFFICE_JS` is `bundled` (the default) or `cdn`. ## Session services (`src/services.rs`)

The host's seam for `session_service` providers (`canoa::session_service`), the libraries that give a host's sessions something beyond the agent (each is an extension). The host knows no service by name: `Services::new(host)` lists the providers the loaded registries offer (valid and unique by id) and hands each to the places that use it.

- **Its MCP server.** `Services::extras()` gives one `store::mcp::Extra` for each service that has a server: offered to a connection whose key holds `services` when the service says `offered`, listed from its `ServiceInfo::tools`, and called through `SessionService::call`. A call that answers a question is put to the person on the client the session belongs to (`Access::approve`, one change per session at a time) and goes on through `resume`; the outcome's note is said in the session. The skill the service names is delivered with its server (`attach_connection_tools`).
- **Its control methods.** A method `ID/METHOD` no route names goes to the service `ID` for a key holding `services.setup` (`control::dispatch`), and the service's refusals map to `-32602`, `-32003` and `-32002`; a host with no such service answers `-32601`. `canoa service ID METHOD` is the same call from the command line.
- **What it reaches.** `HostServices` is the `ServiceHost` of a host: `[host.services.ID]` of canoa.cfg (`Config::services`, each table as JSON text in the file's order; changed in place through `accounts::commands::set_table`, the file checked to be read again), the secrets of the host's account store (`Accounts`) and the loaded registries. A host with no canoa.cfg on disk (a test's) keeps the tables in memory. The host registers it (`canoa::session_service::register`) and every provider call carries the handle.
- **Pages.** An admitted Office page holds `services` when any service has something to give (`serve::admission::page_grants`); a host run for a portal gives no key `services` or `services.setup`.

## `assist`: the host's own model work (`src/assist.rs`)

One service the host's consumers ask for an operation (`complete`, `embed`, `rerank`; `transcribe` and `speak` come with Voice), which it fulfils from a backend. Knowledge search (`kb_mcp`) is the first consumer; none calls an account's API, an agent or a program itself.

- **Backends** (`trait Backend`): an `sdk_provider` on one of the person's accounts (`ID:ACCOUNT`, `openai:work`: every account whose kind provides a standard the provider serves, at the address the kind's `model_api` setting says, the key read from the account store when a request is made) and one for each `[sdk.NAME]` (the provider named, at `address`, the key from the variable `key_env` names, the provider's operations narrowed by the table's `capabilities`); the `server` provider is the host's own. The key is written onto the request by `assist::http::HostHttp`, which is all a provider is given: bound to one address, a path is the only thing a provider names, redirects are refused, the credential headers are the host's.
- **Choosing** (`Assist::chain`): a backend id asks that one alone; `default` asks `[assist.OPERATION] use` then its `fallback`, or every backend that can when the table names none. An operation no backend can serve fails with the reason; a backend that failed is left alone for `[host.kb] retry_seconds` (60).
- **The harness backend** (`assist/harness.rs`, `[assist_harness.NAME]`, id `harness:NAME`, `complete` only): an agent the person has (Claude Code, Codex) under its own login, for when no API key is at hand. It opens the entry `source` the way a delegated task does (`delegate::Host::open`, which the host hands the service once its agents are served: a request before that fails with the reason), asks `initialize` with the account, the profile and the **empty loadout** (`LOADOUT_META` = `""`: no overlay, skill or server of the person's, whatever `[defaults] loadout` says) and no client capability, runs each request in a **new `session/new`** of an empty private folder (so no request sees another's text), puts the session in the mode of the agent that asks for the least (`plan`, `dont_ask`, ...), sets the model and effort asked (refused by name when the agent does not list them) and refuses every `session/request_permission` and every other request of the agent's. The request's instructions go first in the user turn: an agent's own system prompt cannot be replaced.

  Sessions are kept in one `Pool` for all the harness backends, keyed by source, account and profile: started on the first request, reused by the next, ended by `Assist::reap` (every few seconds, from a thread that lives as long as the service) after `[assist_pool] idle_seconds` unasked, never more than `max_sessions` (a request for another key ends the session idle longest; with every session busy it waits for the request's own time and then says so), and ended by `Assist::close` when the host stops. A session that errors on a prompt, times out, ends its turn with anything but `end_turn`, answers nothing or whose process died is ended and the next request starts another (a warm session found dead is replaced once within the same request); an agent that refuses only the model or effort asked leaves its session as it was.

  `kb/offers` and `kb/test` build a service of their own from canoa.cfg as it is now (`Assist::fresh`), which opens agents through the same host and ends with the call.
- **The seam for state.** A `Backend` has `&self` methods, `reap` (called to end what has been idle too long) and `close`, so a backend that holds sessions open can be one, as the harness backend is.
- **`assist::testing::StandIn`** answers deterministically with no network (a vector of how much a text says of four topics) and can be told to fail.

## Errors

- `ConfigError` (`#[non_exhaustive]`): `Read { path, source }`; `Parse { line, column, what }`, 1-based, `what` in the schema's words; `Invalid { entry, what }`. No variant quotes a value from the file; an entry's name is quoted.
- `ProviderError` (`#[non_exhaustive]`): `Load(String)`, `Source(String)`, `Missing`, `WrongKind`, `NeedsConfiguration`, `TakesNoSettings`, `Settings(String)` (names a setting, never its value, unless the provider's own words do), `HostLine(&'static str)`, `Transport(io::Error)`, `Facade(String)`.
- `PeersError` (`#[non_exhaustive]`): `NotAnId`, `NotWaiting`, `AlreadyAccepted`, `Store(String)`.
- `WebError` (`#[non_exhaustive]`): see "The web app". `source()` is the `io::Error` of `Listen`.

- `agent ID` serves the `acp_harness` provider `ID` of the bundled agents' libraries (`claude` and `codex` are two; an id nothing offers is a usage error) as an ACP agent (version 1 or 2, whichever the client asks, up to `--max-acp-version`) on standard input and output, through the same in-process connection a harness entry runs, with no Node; notices are logged at `info` (`CANOA_LOG`), as an entry's are. `--executable` defaults to the variable `COQUI_ACP_` and the id in upper case (`-` as `_`) then `_EXECUTABLE`, else the copy the Store installed, else the agent's own name. `--setting KEY=VALUE` (JSON when it parses as JSON, else text) gives the provider a setting that has no flag of its own (`setting_sources`, `allow_client_plugins`, ...), and the provider refuses a key its schema does not declare; the flags every agent takes the same way (`--model`, `--effort`, `--max-acp-version`, `--max-sessions`, `--no-client-mcp-servers`, the access, `--cache-lifetime`) are given to it as its own settings, where it declares them, and a flag nobody gave leaves the provider's own default. Every mode the agent has is offered, Bypass included, as for an entry.
- `service ID METHOD` calls the control method `ID/METHOD` of a session service the host's libraries offer (`canoa service ID accounts`), as the application does, over the canoa.cfg and home the other commands use: `--params` is the method's JSON object, or `-` to read it from standard input, where a password goes and never on the command line. It prints the answer as JSON. A service no library offers is a usage error.
  A `--working-root` holds a session's `cwd`, more directories and plugins, and a resumed Codex thread's own directory. It takes the process's standard streams, so `canoa-ffi` runs it only through `--canoa-child`, as `provider`, `tool`, `launch` and `mcp-bridge`. The command line reads its own variables (`CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, `CODEX_HOME`, ...) from the environment it runs in. Exit 0 when the client closes, 1 when reading it failed, 2 for a wrong invocation.
- `options` prints what a source offers before a session starts, asked of the `account_provider` of the entry's account (`models`, the automatic `local` account when none is named) with no session and no model turn (`canoa_host::options`). A bundled agent's id runs as `canoa agent` runs it (`--executable`, else the variable `COQUI_ACP_ID_EXECUTABLE`, else the agent's own name); with `--entry`, `NAME` is a `[host.agents]` entry of canoa.cfg (`--config`): a `harness` entry is asked through its own provider and settings, an entry that runs a program on standard streams is asked through a probe session: it starts as a session would, answers `initialize` and `session/new` in a temporary directory, its model option (category `model`, else the older `models` block) and effort option (category `thought_level`) become the models and their efforts, `session/close` is sent when `sessionCapabilities.close` is offered, and the process ends; no prompt is ever sent, it is bounded by `--wait SECONDS` (default 20, `options::PROBE_WAIT`) and its answer is kept in the process by entry, program, arguments and the program's `--version` line (no version, no cache).
  A program that cannot be started is `failed`, one that is not there `not_installed`, one whose session lists nothing is `known: false` with that said plainly; a provider or tool entry still answers `known: false`. `--account NAME` (with `--entry`) asks a harness entry as one of its accounts, so a signed-in account lists what it may use; `options::entry_with` and `options::Asking` are the library's form.
  `--format json` prints one object: `{"known", "unknown_because"?, "unknown_kind"?, "signed_out"?, "program"?, "program_version"?, "cache_lifetime"?, "cache_choices"? ([{"id", "label"}]: the lifetimes beyond default the provider honours, labelled by `cache_lifetime_label`, the host's own words; absent when none), "cache_lifetime_setting"?, "modes"? ([{"id", "name"}], with "default_mode"?: the modes a probe session listed, its `mode` option else the older `modes` block; absent for a harness), "models": [{"id", "name"?, "description"?, "resolved"?, "version"?, "efforts": [..], "default_effort"?, "is_default"?}]}`, `program_version` being the first line of the program's `--version` when it answers within 10 s; `unknown_kind` says why a provider could not list, `not_installed` (the program is not found) or `failed` (it is there and could not be asked; `unknown_because` has the text), and is absent for a source that lists only in its session; `signed_out: true` marks a provider that listed its models and says nobody is signed in on the machine's own login (Claude Code and Codex both list signed out; the first prompt is what fails), which says nothing of an account the host applies;
  `text` prints one `ID<TAB>NAME<TAB>EFFORTS` line per model. Claude Code lists `default`, `opus`, `fable`, `sonnet` and `haiku` with the model each resolves to and the efforts each takes; Codex lists its models with each one's own efforts. It uses the machine's own login and takes the process's usual streams, so `canoa-ffi` runs it as an in-process job; the app caches the answer; the host keeps a probe session's answer for the process, by program version. Exit 2 for a source that is neither built in nor an entry.
- The automatic `local` account of a harness is listed (`accounts list`, `accounts/list`, pools, usage) only while its login exists, as the harness's account provider answers (`AccountProvider::signed_in`, asked when needed and each time, with the host's environment and the variables the entry's shell adds; no program is started, no network is reached, and no secret or path is in the answer). `signed_in` lists it (a key of the environment that signs the program in is the same account, its row's `via` saying `environment key (VARIABLE)`, never the value); `signed_out` hides it everywhere and refuses a session that would run on it; `unknown` (a keyring that did not answer, a place the provider cannot look at, a provider that fails) lists it with the reason as the row's `note`, shown on the Usage page, and starts the session. A provider with no `local` account answers `UNSUPPORTED`. A session that names no account, or `local`, or whose entry's first account is `local`, on a harness that answers `signed_out` is refused with "nobody is signed in to NAME on this computer", the reason and where to sign in, with or without accounts in canoa.cfg. A key a profile's `[profile.env]` sets is not the host's environment and is not seen.
- `accounts` (see "Accounts"): `providers` lists the account providers this host carries, each with its own ways to sign in; `add` signs in through one of them (`--provider`, an id `providers` prints) by one of its own login methods (`--method` naming none or an unknown one lists them, status 2) and appends `[host.accounts.NAME]` to canoa.cfg, made if absent; `login` signs in again to an account (`--method` only when its kind has several); `remove` forgets the stored credential and the account's directory and takes the block `add` wrote out of canoa.cfg (an account written some other way is for its writer to remove; an entry that offers it keeps it, status 2); `list` prints `NAME PROVIDER KIND STATE` or `{"name", "provider", "kind", "id", "state", "revision", "expires_at", "types", "fits"}`, `state` being `signed in`, `needs sign-in`, `in use` or `signed in where it runs` (harness-login), never a credential. `add` refuses the name `local`. A page to open or a code to confirm is said on standard error (`Open this page: URL`, `Confirm this code there: CODE`), or with `--format json` printed as `{"say": TEXT}` and `{"open_url": {"url", "user_code", "expires_ms"}}`, then `{"account": {"name", "provider", "kind", "id", "label", "checked"}}` when `add` is done.
  A secret the method asks for is typed without echo at a terminal, or one line of standard input when that is not a terminal; it is never read from the command line. `--until-stdin-closes` cancels the sign-in when the front's input closes (the process-level `canoa` ends at once instead, so do not use it with a piped secret).
- `launch` is what `serve` runs for an agent entry with profiles: the environment (and any extra arguments) on the first line of standard input, the rest to `PROGRAM`, whose status it exits with; a first line of another form is status 2.

- `--method` names the proof: this user's identity of that method, made when absent, and the home then records that method in `method`. Without it, the method the home records (the one named last, or its first identity's), or a new identity of the default method, Noise. An identity never changes method. A client of the other method is logged as `a client was refused: … the peer proves by X, and this endpoint only by Y`, with no word of `accept`: its key has to be paired again under this host's method. `--key-limit` and `--no-rekey` set the session, each method's default otherwise, and a non-default one is logged at `info`.
- **A running host keeps its home's method.** `id --method X` and `pair --method X`, with another method than the one the home records while a host holds the home (`Home::probe`, which takes nothing and writes nothing), are refused with status 3: `NAME (process PID) is running on this home, which proves by Y: already-paired clients would be refused after its next restart if the method became X. Stop it first, or add --force to change it anyway`. `--force` changes it and logs at `info` `--force: method is X while NAME (process PID) runs on this home, which proves by Y: …`; it is the person's own flag, and what it risks is a lockout of paired clients, not a looser proof. The method the home already records, no `--method`, and a home no host holds are never refused. `serve --method` is not guarded: it holds the home itself.
- `serve` prints one JSON object per entry on standard output, `{"name", "kind", "url", "harness"?, "title"?, "peer", "method"}`, `harness` being a harness entry's provider id (absent for any other entry) and `title` the entry's title (absent when it has none), `peer` this host's id and `method` its proof's, once every entry is bound, and then `{"ready": true, "peer", "method"}`, a line with no `name`; then it serves until stopped. It logs on standard error.
- **One host on a home.** `serve` takes the home's lock (see "One host on a home") before anything else of the home, or any address: a second one, the app's or another `canoa serve`, says `canoa: NAME (process PID) already hosts this home, DIR: ...`, binds nothing and ends with status 3. A holder that died holds nothing. `check`, `peers`, `accept`, `revoke`, `id` and `pair` take no lock, and `serve --program` takes none either.
- `pair` takes its PIN back however it ends, so a connection still pairing on its own thread when it is given up pairs nobody: in an application's process such a thread outlives the command.
- **The host's own sources** (`serve --local-sources`, `ServeOptions::with_local_sources`): `Claude` and `Codex` (built-in harness entries with Bypass offered), `Antigravity` (`agy acp`, usage read, also found in `%LOCALAPPDATA%/agy/bin`), `Grok` (`grok agent stdio`, also in `~/.grok/bin`), `OpenCode` (a built-in `opencode` harness entry: coqui-acp's `opencode` provider runs `opencode acp` in this process, with the `opencode_accounts` provider beside it; also found in `~/.opencode/bin`, the found program is its `executable`) and `Pi` (a built-in `pi` harness entry: coqui-acp-pi's provider drives `pi --mode rpc` in this process, with no Node and no adapter; it is ready exactly when the Store's Pi extension finds `pi`, that is a managed copy, `PATH`, `~/.pi/agent/bin` or `~/.local/bin`; `missing` is `["pi"]` and nothing else). A managed copy (`current.json` the host wrote, every file as installed, its Node and script inside the copy) runs as the provider's `node` and `script` settings, never a `.cmd` shim; otherwise the `pi` found is its `executable`.
- **How an agent receives the overlays' context** is its preset's `SourcePreset::context` (`canoa::preset::ContextDelivery`, found by `bundled::context_delivery`): ACP's `systemPrompt` when the agent's `initialize` says it takes one (at the standard's place, or at the path the preset names), else a file at the preset's `instruction_file` in a directory the session is given through `additionalDirectories` (the context item is `refused` when that file cannot be written, and no directory is given then), else the context prepended once to the session's first `session/prompt` (the working directory of a session comes from its `session/new` or `session/load`; a session's record ends with its `session/close`). An MCP server left out because the same tools reach the agent through `[scripts]` and a skill, and a skill left out because its MCP server is started, are reported `off` with that reason. `AGENTS_PYTHON` and `AGENTS_HOME` are set for a session and for overlay preparation only when the environment they would join has none.
  `[permissions] protected`, when canoa.cfg has it, is the provider's `protected` setting, so the person's list replaces the provider's recommended one for this source (it is the one list the person already edits for what a session may not touch); absent, the provider's recommended list stands. The launch's `PI_SKIP_VERSION_CHECK` is not passed on yet: no environment reaches a source's provider but a profile's. Each is an entry with `Entry::local` set: no listener, no `/canoa.json` line, reachable through `Local::open` only. `serve` prints a line for each, `{"name", "kind": "agent", "local": true, "missing": [...], "harness"?, "title", "peer", "method"}` with no `url`; `missing` names the programs not found (on Windows only `.exe`, `.cmd`, `.bat` and `.com` count, so `npx` is `npx.cmd`), and the entry is served either way so a client can say what to install. A name canoa.cfg already uses is left to canoa.cfg.
- **The default profile: canoa.cfg's top level launches every agent entry that names no profile**, a source of the host's own, a hand-written `[host.agents.NAME]` program or harness entry and a library's harness alike (the host owns a session's profile). An entry that names `profiles` gets those and nothing of the top level; one that should run bare names an empty `[host.profiles.NAME]`. The report's `profile` item, and `canoa check`'s `profile:` on each entry, say which profile applied and why.
  It is built, through the machinery of `[host.profiles]` ("An agent entry with `profiles`"), with one profile named `default`: `Config::local_profiles` holds `[profile]` (the person's layer), the names in `[overlays]` (read from `overlays/NAME` beside canoa.cfg, as for `[host.profiles]`, so a source that is a directory is not applied here), and for each agent `[agents.NAME.profile]` (a layer above the person's, `agent:NAME`), `[agents.NAME.hooks]` (an overlay's name and the tree digest its hooks run at: `allow_hooks`) and `[agents.NAME.mcp]`: `true` leaves a server of the person's on, `false` turns any server off, a `sha256:` digest allows an overlay's server at that definition (`allow_mcp`). `LocalProfiles::for_agent` is `None` when nothing in canoa.cfg is for that agent, which starts it with no profile. With `ServeOptions::layers` set (`serve` sets it) the offer is built again from the layered files, through `Config::load_layers`, when each connection reaches its first message, so an install reaches the next session and ends none; a file that no longer loads is logged at `warn` and the last good offer stays.
  A session starts with a named loadout: `[loadouts.NAME]` holds `description`, `overlays` (names from `[overlays]`), `skills` (the ones the person chose) and `mcp` (servers of `[profile.mcp]`), and `[defaults] loadout` names the one a session that names none starts with. `initialize`'s `_meta["dev.boriken.canoa/loadout"]` (`LOADOUT_META`) names it; a name `[loadouts]` does not hold is refused as invalid params, with the name (the empty name is the loadout that holds nothing: every overlay, skill and server of the person's is off, whatever `[defaults] loadout` says, and it is no role to a template), and with neither a name nor a default the session starts with every overlay the profile lists and no loadout's narrowing. The connection resolves it once (`HostProfile::resolve_loadout`, `Connection::prepare_with`), so a later edit reaches new sessions only: its overlays apply whole in the order `[overlays]` composes them (a loadout cannot reorder them; an overlay it names that `[overlays]` lacks is reported, not applied), `OVERLAYS_META`'s list wins over the loadout's overlays, and the person's own `[profile.mcp]` servers the loadout does not name are off (a name it gives that the profile does not define is reported).
  A skill the loadout names is on for the session (`HostProfile::chosen_skills`, set at that resolution): each connection reads its record in `overlays/.skills/NAME.json` with the checks of an overlay's fetched skill (the record says `chosen`, its files have its digest and `[skill_pins]`' pin and pass `read_fetched_skill`) and delivers it in the person's layer; one that fails is reported as `skills.NAME` and left out. Only the profile tables are re-read: entries, `[host]` and `[agents.NAME] program` change at a restart. Entries with `Entry::local` and every entry that names no `profiles` get this; an entry that names `profiles` offers only those. An item for `model`, `effort` and `mode` carries `"value"`, since the host cannot set them and the session's options do. A project's profile (`.canoa/profile.toml`) is not read.
  A session may also start with a named profile: `[profiles.NAME]` (the name is 1 to 64 of ASCII letters, digits, spaces, `-`, `_` and `.`, no space at either end) holds `source`, `model`, `effort`, `mode`, `context` (the starting instructions, text), `cache_lifetime` (`default`, `off`, `short` or `long`) and `loadout`, all optional and nothing else (`Config::local_profiles.presets`, `Preset`). `initialize`'s `_meta["dev.boriken.canoa/preset"]` (`PRESET_META`) names it; a name `[profiles]` does not hold is refused as invalid params, with the name. The connection makes its model, effort and mode the session layer above the agent's (`HostProfile::session`, `Preset::session_layer`) and its context an addition to the initial context after every other layer's, reported with the layer `session`; its loadout is the connection's unless `LOADOUT_META` names one, and a loadout canoa.cfg no longer holds is reported as `loadout` and the default applies. `source` and `cache_lifetime` are the client's to apply. `[profile]` stays the person's layer every session gets; a profile sits above it, and the account and permissions are never part of one.
  An entry that offers only `[host.profiles]` holds no presets and refuses the name.
- **Approvals** (`profile::APPROVE_METHOD`, `_canoa/profile/approve`): a client that is this process's own link (`Local::open`, never a paired key) and whose `initialize` carries `_meta["dev.boriken.canoa/approve"] = true` (`profile::APPROVE_META`) is asked, before each `session/new`, `session/load` or `session/resume` is forwarded, which MCP servers of an overlay that the configuration does not allow this session may start: the request `{"profile", "harness", "servers": [{"name", "layer", "digest"}]}` with an unguessable text id (`canoa-approve-N-<24 hex>`), answered `{"allow": [names]}` (names it did not list are ignored). Those names are added to that session's `mcpServers` and shown `applied` in its report; nothing else changes, and nothing is kept: keeping a choice is `[agents.NAME.mcp]` in canoa.cfg. A paired key, however it opts in, and a link that does not opt in, answers with an error, takes over two minutes, or goes away gets the configuration's behaviour (off). Its other messages wait until the answer. A server the person turned off with `false` is never asked about. The scope removes a client's `_meta`, so the opt-in is read before it.
- **Listing a session's MCP tools and resources** (`mcp_list::METHOD`, `_canoa/mcp/list`): outermost around `ToolsLayer`, it reads the `mcpServers` of each session request (`session/new`, `session/load`, `session/resume`, `session/fork`) as they leave for the agent and forgets them on `session/close`. On `_canoa/mcp/list {sessionId, cursor?, limit?, server?}`, answered on the stream on a worker thread, it asks each server (`initialize`, cursor-paged `tools/list`, and `resources/list` when advertised). An HTTP server is asked directly, as are the host's own (`canoa-store`, `canoa-kb`, `canoa-delegate`, `canoa-<provider>`, whose bridge entry names a loopback address). A stdio server the host did not give (a client may hand a session none, so none is expected) is not started: it is `"pending"`, listed when the agent reports its tools; a server the agent reads from its own settings is not in the request and is not listed.
  A stdio server the host's profile gave the session (`Hosted::given` records its name) is started once more, in the session's `cwd` and the agent's environment, asked and ended. The answer is `{"tools": [{"server", "name", "title"?, "description"?, "inputSchema"?}], "resources": [{"server", "uri", "name", "title"?, "description"?, "mimeType"?}], "servers": [{"name", "status" ("ok" | "error" | "pending"), "tools", "resources", "error"? | "note"?}], "nextCursor"?}`, paged deterministically across tools then resources (`limit` default 100, no ceiling), keeping failed servers in `servers` with their reason, and refusing unknown sessions or stale cursors with `-32602`. `[host.mcp_list]` (`Config::mcp_list`, `McpListConfig`) holds `query_seconds` (5, all of one server's lists), `max_items_per_server` (1000) and `max_reply_bytes` (4 MiB, an HTTP body or a line of output), each at least 1 and with no ceiling of its own.
  An agent's own request or notification whose method starts with `_canoa/` or `_coqui_acp/secret_` is dropped before the client sees it (`scope::is_host_only`), on every entry.
- `serve --allow-empty`: a canoa.cfg with no entry, or none at all at that path, runs with nothing to serve, printing only the `ready` line, where without it that is status 2. It writes no file. A canoa.cfg that exists and cannot be read or parsed is still status 2.
- `serve --web [DIR]` serves the web app too (see "The web app"): from `DIR` (made absolute from the working directory), else `[host.web]`'s `dir`, else the site built in; on `[host.web]`'s settings, or the defaults without the table. `--web-listen` replaces `listen`, and needs `--web` or `[host.web]` (status 2). After the entries' lines it prints `{"web": URL}`, a line with no `name`. A site that cannot be served, no site, plain HTTP beyond loopback, a zero limit or an unusable certificate is status 2; an address that cannot be bound, status 1.
- **A link from inside** (`Local::open`) is served as a paired key's connection is: the entry's agent, scope, worktrees (`_canoa/worktree/*` before the first ACP message) and `max_peers`. It skips the proof, the trust store and the entry's `peers` list, since whoever holds a `Local` is this process; no network peer can obtain one. `Stopper::stop` closes every link. The peer it is logged as is the host's own id.
- `portal` (feature `portal`, Unix) reads its settings from `--config` (a TOML file, see "The portal"; no file is the defaults), `--site`, `--listen` and `--socket` replacing `site`, `listen` and `socket`, prints `{"portal": {"socket", "listen"}}` once bound, and serves until killed. Status 2 for a settings file or site that does not work, 1 for an address that cannot be bound.
- `serve --portal DIR --portal-user USER` runs the host for a portal (see "The portal"); `--portal-user` is required with it `--portal-group` (one or more) and `--portal-min-uid` (default 1000) go with it, and a name that is not in `/etc/passwd` is status 2. `--web` and `[host.web]` are ignored with it.
- `serve --until-stdin-closes`: once every entry is bound, standard input is read and discarded; when it closes, every listener and agent is ended (`Stopper::stop`) and the host exits 0. For a parent that runs the host as its child: the host ends with it, however the parent ends. Without the flag the input is never read.
- `pair` (`--listen` default `127.0.0.1:0`, another address logged at `info` as `non-default: pair --listen is ADDRESS, default loopback`; `--timeout-seconds` default 300) prints `{"pin", "peer", "method", "url"}`, a six-digit PIN, this host's id, its method and the address to dial, and pairs by that method; a native client joins with `cabuya::pairing::join` (`canoa pair --join URL`). The joiner's key is accepted in the store once the PIN confirms both keys, and `pair` prints `{"paired": ID}` and exits 0. One wrong try ends it (status 1), as does the timeout, and with `--until-stdin-closes` its input closing. A pairing connection serves no agent. A WebSocket upgrade that carries an `Origin` header, which every browser sends, is refused (403) before the handshake, so a web page cannot spend the PIN's one try, unless `--origin ORIGIN` (one, `scheme://host[:port]`, never `null`) names it, as an extension's page or the web app's origin is named, and the key it pairs is recorded as that origin's; a browser may instead pair by connecting to `serve` once and being accepted.
  `pair --join URL` is the other end: it joins a waiting `pair` under this host's identity (the PIN from `--pin-file`, else standard input; `--ca-file` a PEM bundle the server's certificate must chain to) and prints the waiting side's peer id.
- On `serve --until-stdin-closes` and `pair --until-stdin-closes`, nothing is logged between the input closing and the exit, and the process exits within 5 s whatever is left: a parent that died can leave standard error a pipe a write to which never returns (seen on Windows under a Dart parent).
- `accept` and `revoke` take `--` before the id.
- `tool` serves one tool entry on standard input and output, `JSON` being the entry as `ToolSpec` serializes it (without `listen`, `working_roots`, `peers`, `max_peers`): what `serve` runs per connection. A `JSON` that is not one, or that `check` refuses, is status 2.
- `check` prints `NAME KIND LISTEN` per entry, or `{"name", "kind", "listen"}` with `--format json`, and serves nothing.
- `layers` prints the canoa.cfg files in the order they are read, lowest first, whether or not they exist (the installed, system and user files, or the ones `--config` or `CANOA_CONFIG` list), then the one that is written: a JSON object `{"files", "own"}` with `--format json`, one path a line and `own PATH` otherwise. A listed file that is missing, or an empty entry, is refused.
- `control` answers one request of the control channel as the owner over canoa.cfg's files, with no host serving, and prints the answer, one JSON-RPC line: how an application reads (`config/layers`: every layer with its document, the one written, the store's revision) and changes (`config/change` `{ops: [{path, value?}], check?, revision?}`) its configuration before its host is up or when none starts. It goes through the same `FileStore` as a serving host, so a file that is not there yet is read empty and made by the first change, and a `Canoa.cfg` from before the rename is taken over as for every command.
- `peers` prints `accepted ID` and `waiting ID [from ADDRESS]`, or `{"peer", "state", "source"}`.
- canoa.cfg is read as layers, lowest first: `canoa.cfg` beside the program (or in `CANOA_INSTALLED_DIR`), the system's (`%PROGRAMDATA%\Canoa\canoa.cfg`, else `/etc/Canoa/canoa.cfg`) and the user's (`%APPDATA%\Canoa\canoa.cfg`, else `$XDG_CONFIG_HOME/Canoa/canoa.cfg`, else `~/.config/Canoa/canoa.cfg`, macOS included), each in the format its first line names, merged by `canoa_host::merge_into` (tables key by key; arrays and the `ENTRIES` named entries whole). `--config`, else `CANOA_CONFIG`, is a list of files split at `;` on Windows and `:` elsewhere, the last highest and the one `accounts` writes: without a leading `+` it replaces the three layers, with one it goes over them; an empty entry or a missing file is refused naming the entry. The app reads and writes the same files.
- `provider` takes `--library` and `--source` from where it was started, then runs in `--directory`; with `--settings-on-stdin` it reads a `HostLine` first, as `serve` writes it; with `--connect` it serves on that loopback socket after sending the line's token, rather than on standard input and output.
- Exit status: 0 success; 1 the operation failed; 2 the invocation or canoa.cfg was wrong, `serve` with nothing to serve, or a text that is not a peer id; 3 another host holds this home.

### A webpage's session folder

A client that is a webpage has no file system and names no path. Its `session/new` carries `_meta["dev.boriken.canoa/site"] = {"site": "<host name>"}`; the host ignores any `cwd` it sent and gives the agent `<Documents>/Canoa/scratch/<site>/<new UUID>` instead, made (`create_dir_all`, mode 0700 on Unix) only after the scope has passed the request, so a request that is refused makes nothing. The answer to `session/new` carries `_meta["dev.boriken.canoa/site"] = {"site", "id", "folder"}` (the host removes the key from any other answer, an agent's own included). The site is taken only as written, in the form a browser gives it: lower-case ASCII labels (an international name as `xn--` punycode), no trailing dot, port, separator, colon or IPv6, a label of 1 to 63 letters, digits and inner hyphens, 253 characters at most, a first label that is not a Windows device name (`con`, `prn`, `aux`, `nul`, `com1`..`com9`, `lpt1`..`lpt9`), and a name made of numbers only an IPv4 address; anything else fails the request with `-32602`.
`session/load` and `session/resume` with the same key must carry the recorded folder as `cwd`: it is taken only when it is `<Documents>/Canoa/scratch/<site>/<id>` with `<id>` one segment of letters, digits and hyphens, and is made again when gone; anything else is `-32602`. An entry with `working_roots` refuses a folder outside them. The Documents folder is `XDG_DOCUMENTS_DIR`, else the system's; a host with none fails the request. The host makes no other folder for a client.

A site names no directories of its own: `additionalDirectories` is removed from its `session/new`, `session/load` and `session/resume` (the profile's skills folders are added after this check), and a session the host placed for a site, or reopened for one, is refused `session/set_mode` and `session/set_config_option` (an option the agent did not give the category `model` or `thought_level`) to anything but `plan`, `manual`, `default`, `accept_edits`, `acceptEdits` or `dontAsk` (`-32602`), unless the message carries `_meta["dev.boriken.canoa/approval"]`, the token the host put in this connection's answer to `initialize` (`APPROVAL_META`; it is a different string on each connection, so one seen on another is refused, and the host removes the key from every answer but the one to `initialize`). A client marks its sessions as its own with `{"site": ..., "own": true}` in `_meta["dev.boriken.canoa/site"]` (the web app, and the browser extension for its own pages), and those are held to neither this nor the removal of `additionalDirectories`; the host does not echo the mark.

## Gotchas

- **`[host.disabled]`** (`canoa_host::disabled`, `Disabled`, `install`, `is_off`, `off::<Kind>(id)`): provider ids by kind name that the host neither lists nor starts (a service that loads providers itself asks `ServiceHost::is_off` and leaves out the ids named there); `serve` installs it once at start (the host reads `[host]` then) and each list the host builds from a registry (account makers, `acp_harness`, `agent_vendor`, `program_store`, `store_extension`, `catalog_source`, session services, settings sections, panel tabs, profile items, secret providers, the speech kinds scripts offer) asks it. A Guatiao registry cannot hide an offer, so a provider is skipped where the host builds from it. The accounts of an off account provider stay in `[host.accounts]` and `accounts/list` marks them `disabled`. A kind or id no loaded library offers is a warning. Catalogs of the Store scopes (`store::catalogs`, `store::catalog_run`, `store::catalog_view`) are described in `docs/configuration.md` and `src/control/AGENTS.md`.
- **Tests never touch the operating system's credential store, bar the ones about it.** In this crate's own unit tests every `KeyringStore::new` is the process's memory (`keyring_core::mock`); a test about the real store makes an `accounts::store::real_store::RealStore`, a service named for the process (`dev.boriken.canoa.test.<pid>.<n>`) whose every entry is removed when it drops, a panic included, and `no_entry_of_this_run_is_left_in_the_operating_systems_store` checks the store (Windows: `cmdkey /list`) afterwards. The integration tests set `CANOA_CREDENTIAL_STORE=memory` in `tests/support` before they start a host, and the C ABI's tests in `canoa-ffi/tests/common`, so the hosts they run and the ones they start in process keep credentials in memory; a test that needs a credential to outlive one process uses `[secrets] accounts = "file"` in a directory of its own. A new test that puts something in the real store takes a `RealStore`, never a service of its own.
- Under Noise a client's handshake ends before the host decides, so a client the host refuses sees its link end rather than a failed proof.
- `serve --program --paired` proves by this home's identity and admits the keys of its trust store, except a key canoa.cfg limits to entries with `peers` (read when it starts: a key an entry names is that entry's and is not served the program, whatever the store says, and a canoa.cfg that cannot be read is an error). `canoa revoke` removes a key from the store it serves. The servers this host dials (`pair --join`, then `dial --paired` and `forward --paired`) are kept apart in `<home>/dialed`, which no entry reads: joining a server does not let it in. The library's commands run in a job of an application's process only as a process of their own (`is_a_hosts_own`).
- **The library's commands** (`serve --program`, `dial`, `forward`, `grant`, `discover`, `mcp-config`, `mcp-shim`, `agent-guard`, `id --identity`, `pair --join`) are calls into `coqui-acp-bridge`'s modules, which hold their logic and their flags: `cli/bridge.rs` gives them this host's home (identity, trust store and grants are the host's own, not the library's default folder) and the program that runs `agent-guard` and `mcp-shim` (`Front::program`), and ends the process with the status the library returns, saying nothing for an agent's. `serve --program` serves one program after `--` with no canoa.cfg, by the library's proofs, TLS, WebTransport, linger, services, forwarding, offers and advertising; `--method`, `--key-limit` and `--no-rekey` are both forms' own, and the library's other flags without `--program` are refused. `--web`, `--web-listen`, `--portal`, `--local-sources`, `--allow-empty`, `--supervised` and `--until-stdin-closes` belong to a serve of canoa.cfg and are refused with it. `id --identity FILE` prints the peer id of the key in FILE, made when absent.
- A stdio agent inherits the host's environment and working directory. An agent can still start whatever its own tools start when the client allows them; the host stops only what a client could start without the agent asking.
- A profile's variable and MCP server values never reach the client from the host, but they reach the agent, which acts for that client and may show them: give a profile only what that entry's clients may use.
- A paired key reaches every session an agent keeps for this user: `session/list` and `session/load` pass to a stdio agent unchanged.
- `program = "canoa"`, `args = ["agent", "claude"]` with a profile that has skills needs `"--setting", "allow_client_plugins=true"` in `args`: without it Claude Code's translator refuses every session the host adds its plugin to. A `harness` entry needs nothing.
- On Windows the translators start `claude.exe` and `codex.exe`, as the native installers put them; an npm-installed `claude.cmd` or `codex.cmd` is untested, and a profile's context goes on the command line it is started with. Name the executable by its full path if it is elsewhere.
- `working_roots` compare paths as written: a link inside a root that points outside it is followed by the agent. Worktrees are made, read and removed only where every link is resolved, inside the roots resolved too.
- If the host itself is killed, on Windows the system ends its agents with it (each is in a job object closed with the host); on Unix each sees its standard input close, and most then exit. `serve --until-stdin-closes` ends them on every platform when the parent goes. A host inside an application has no parent to watch: on Unix, an agent that ignores its input closing outlives an application that crashes.
- Each connection is a fresh process, so a turn in progress ends with its link; a later connection resumes a session only if the agent kept it.
- `peers` is read when the host starts; a key removed from the trust store loses its link within about a second without a restart.
- A provider's process inherits the host's environment. For a Python source that includes, on Windows, `PATH`, which decides which `python3.dll` loads under `import_search = "path"` unless `import_dirs` holds one; and with `isolation = "inherit"`, `PYTHONPATH` and `PYTHONHOME`.
- Settings come from canoa.cfg only. A client reaches a provider through ACP, never through its settings; `check` does not load the provider, so a setting its schema refuses shows only when a connection loads it, on the host's standard error.
- A tool runs with the host's rights and does unasked whatever its rules do not turn into `ask`: the host shows its tool calls as they run, never before. `unasked` is the entry writer's account of that, shown, not checked.
- On Unix, ending one tool process (its session's cancel, a replaced `message` run) does not end what it started; that stays in the connection's process group and ends with the connection, unless it left the group.
- On Windows `program = "pi"` does not find npm's `pi.cmd`: name `node` with the script's absolute path, which keeps `cmd.exe` out, or `pi.cmd`.
- A tool entry is on `canoa tool`'s command line as JSON, which other users may read: nothing secret belongs in one.
- On Unix, what a tool starts in a session of its own (Node's `detached`) leaves the connection's process group and outlives it.
- Plain WebSocket carries only the proof and sealed records. Anyone who can reach the address can connect and make a proven key wait; only an accepted key gets further. On loopback, the default, that is anyone on this machine.
- The web app's page connects to the entries' addresses, which are loopback: a browser on another machine, opening it over HTTPS beyond loopback, reaches the page but not the entries until a proxy carries them. A non-empty `origins` must list the page's own origin for its connections to be let in.
- The site's files are served with this user's rights from what the directory holds when asked: whoever can write it chooses the page, and a link swapped in between the check and the open is followed (the check resolves the path, then opens it). Give it a directory only you can write. `serve` refuses a site holding canoa.cfg's directory or the identity home.
- The page's key lives in the browser under the page's origin, `http://127.0.0.1:7800` by default. While the host is not running, any program of any user on this machine that binds that port serves its own page in that origin, which can use the key paired with this host. On a machine others use, serve over HTTPS with a certificate the browser trusts and a key only you can read, or use the extension.
- The policy allows `'wasm-unsafe-eval'` and inline styles, which Flutter's web build needs, and no inline or evaluated script: build the app with `flutter build web --csp --no-web-resources-cdn`, or its code and CanvasKit are refused. The app carries its Roboto font (`app/assets/fonts`) and points the engine's fallback fonts at the site (`app/web/flutter_bootstrap.js`), so that build fetches nothing from outside the site. `python app/tool/build.py` puts the fallback fonts the engine asks for (every script, CJK and emoji: 724 files, 20.7 MiB) in `assets/fonts/fallback/` from the deps mirror and deletes `flutter_service_worker.js`: a build made with `flutter build web` alone has neither, and a symbol Roboto lacks then draws as a box. The app registers no service worker (the ETag and 304 answers below are its cache), and `splash.js` unregisters one an earlier build left, which Flutter's loader would otherwise register again and wait for up to 4 seconds.
  `app/web/index.html` shows a loading screen (the mark and "Loading Canoa…", light or dark by `prefers-color-scheme`) from `app/web/splash.css` and takes it away on Flutter's first frame in `app/web/splash.js`: both are files of the site's own origin, so the policy needs nothing added.
