# `canoa-litellm` — API header

Header-file-style reference for `canoa-litellm`: the account kind of a LiteLLM proxy (one address and one virtual key for the OpenAI API and the Anthropic Messages API), the sign-in that makes it, and what the account reports, so it can be used without reading its source. It ships inside the package and is self-contained. Development documentation lives with the source at <https://github.com/Boriken-Dev/canoa>.

MSRV Rust 1.89. Version `0.0.0-alpha.0`, not published (`publish = false`). `#![forbid(unsafe_code)]`. Depends on `canoa` (feature `api-gateway`, which brings `network`), `coqui-acp-api`, `guatiao-serde`, `getrandom`, `percent-encoding`, `serde_json`, `sha2` and `time`. No Cargo features.

What a host loads is `library` (below); the host names none of it: it joins the kind and its sign-in methods to the listing of every harness that accepts a standard the kind provides, and asks this library, whichever harness the account names, for the account's usage, models and renewal.

## The account

Settings: `base_url` (required), the proxy's root address. Credentials: `api_key` (what a program sends), and for a key the proxy's sign-in made also `refresh_token` and `client_id`, which no harness is given (the host gives a harness only the keys the standard it applies the account as names). The kind provides `openai-api` and `anthropic-api`, so Codex runs on `<base_url>` with the key as an OpenAI key and Claude Code with the key as an Anthropic one, on one account and one budget.

Two ways in (`LiteLlmAccounts::login`; the address is the method's input, the key the sealed form's):

- **`litellm-sso`** opens the proxy's own sign-in. It reads the proxy's discovery document, registers a client with a loopback redirect (an address the system picks on `127.0.0.1`, path `/callback`), asks the person to open the proxy's `/authorize` page (`OpenUrl`), waits for the redirect (a request whose `state` is not this sign-in's is answered and ignored), exchanges the code at `/token` with the PKCE verifier, and answers the key, the refresh token, the client and when the key ends (`expires_in`). The person cancelling or `timeout_ms` passing is `GONE` (`login cancelled`, `login timed out`); a proxy that refuses is `BAD_VALUE` (`login refused: ...`); a proxy without the sign-in is `INTERNAL` saying so and to use a key.
- **`litellm-key`** asks for a key in the form only the person's application reads. Nothing is asked of the proxy: the key is read when it is used.

## What it reports

- `models`: `GET <base_url>/v1/models` with the key; the proxy's list for either API (a query carries no standard to tell them apart by). The proxy not answering or refusing the key is an unknown with the reason, never a guess.
- `usage`: `GET <base_url>/key/info` with the key. The buckets are `coqui_acp_api::key_usage::gateway_buckets`'s, source `gateway`: a bucket `budget` (`spend` against `max_budget`, millionths of a dollar, every model, `FixedWindow` at `budget_reset_at` for `budget_duration` when the proxy says them, else `Never`; exhausted once spend reaches the budget; with no `max_budget` the spend alone, status unknown), and a bucket `rpm` and one `tpm` (`Requests`, `Tokens`, the limit, a one-minute `FixedWindow`, status unknown: the proxy reports the limit and not what is left) when `rpm_limit` and `tpm_limit` are set. The request itself goes through the host's HTTP client. A 401 is `GONE` (the key expired or was revoked), so the host renews it; a 403, 404 or 405 is "not offered".
- `renew`: for a signed-in key, the refresh grant at `/token`, which the proxy rotates, so the answer holds the next refresh token and when the new key ends; a refused token is `GONE` saying to sign in again. A key someone gave has nothing to renew it with and the report says so.
- `watch`: not offered, a key at a proxy is in no file a program renews.

## Gotchas

- Written from LiteLLM's published documentation and tried against a stand-in; **not run against a real proxy**. Unconfirmed there: the exact fields of the discovery document (only `resource` is read, and the documented paths `/register`, `/authorize`, `/token` and `/revoke` are used rather than ones the document names); the loopback redirect's path (`/callback`); whether `/key/info` without a `key` parameter answers for the key sent as its bearer (the documented example passes `?key=` and a master key) and which of `max_budget`, `budget_reset_at`, `budget_duration`, `rpm_limit` and `tpm_limit` it returns; whether a key made by the sign-in may call `/key/info`; and the classic (non-PKCE) `litellm-proxy login`, whose poll endpoint is documented but not its start, which is not implemented.
- One address is what both programs take: Codex adds `/responses` to it, Claude Code adds `/v1/messages`. LiteLLM serves `/v1/responses` and `/v1/messages`; that it also answers `/responses` without `/v1` (which is where Codex goes with a root address) is unconfirmed.
- The proxy's sign-in is a LiteLLM beta that has to be turned on (`EXPERIMENTAL_UI_LOGIN`) and is recent enough to offer `--pkce`; `litellm-key` needs neither.
- A key never leaves for any address but the proxy's, a request follows no redirect and goes through the host's network settings, and no refusal, log or answer holds a key, a code or a token.
